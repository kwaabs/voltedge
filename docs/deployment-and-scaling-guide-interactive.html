Scale out.
Without breaking the database.

Sized for ~1,000 concurrent users, with every smaller deployment comfortable. The Go tier is already stateless; the ceilings are Postgres and the tile path. This edition lets you do the arithmetic: connection pools, queueing, HPA, tile load, worker drain times, rate limits, migrations — and see which parts of the manual are already in the code and which are still work to do.

Use As in the top bar. Olu (on-call) can scale workloads and operate workers. Priya (platform admin) can also change infrastructure config and run migrations. Dev ships code (read routing, the concurrency gate) but cannot scale or migrate. Ada (auditor) only reads. Buttons you may not press are marked with what you need.

Who this is for

Whoever deploys and runs VoltEdge: Docker, a container orchestrator, Postgres replication and load balancing are assumed. This guide is the why and how far; the step-by-step companions are the Production Setup Runbook (single-host Compose) and Deploying on Kubernetes & Coolify. This guide tells you which knob to turn when load rises; chapter 13 is that table.

Read the pre-flight checklist (chapter 9) before scaling out. A current default — an unbounded DB connection pool, verified in api/cmd/server/main.go:93 — makes scaling out actively worse until fixed.

Reality check. Verified in the repo: stateless API; /healthz; PgBouncer and nginx in docker-compose.prod.yml; SKIP LOCKED queues; a per-pod 60 s access cache. Not in the code: a bounded pool (and the DATABASE_MAX_OPEN_CONNS env var), /readyz, read/write split, tile caching headers, an analysis concurrency gate, a metadata cache. 01

The API tier is stateless

The one fact that makes scaling easy.

VoltEdge’s API holds no authoritative in-memory state. Sessions are database-backed: a login mints an opaque token and only its SHA-256 is stored in Postgres; every request re-loads the session (auth/session.go, middleware.go). Attachments and exports go to object storage (RustFS via presigned URLs), so no pod needs a shared volume. Heavy background jobs run as separate worker processes draining Postgres queues with SKIP LOCKED.

Consequence: run N identical API copies behind a plain, non-sticky load balancer. No session affinity, no shared filesystem. The ceilings are therefore Postgres and the tile path; the rest of the guide is mostly about those two. Pick an action and see where its state lives:

Three footnotes to “stateless”

Prove it on your deployment

docker compose -f docker-compose.prod.yml up -d --build --scale api=4
for i in $(seq 1 20); do curl -s -o /dev/null -b cookies.txt http://localhost:3710/api/auth/me; done
docker compose -f docker-compose.prod.yml logs nginx | grep 'auth/me' | grep -o 'upstream=[^ ]*' | sort | uniq -c

Requests spread over several upstream= addresses, all succeeding with one cookie, is statelessness in practice (nginx’s log_format prints upstream=$upstream_addr).

03

Edge / load balancer

TLS, non-sticky, health, and where the real rate limit lives.

  • TLS termination at the ingress (nginx-ingress, Traefik, HAProxy or a cloud L7 LB).
  • Non-sticky, round-robin. The API needs no affinity — enabling it defeats even load distribution.
  • Health checks. GET /healthz checks Postgres reachability, so it doubles as readiness: a replica that can’t reach the DB leaves rotation. A separate /readyz (liveness vs readiness split) is a proposal; it does not exist.
  • Edge rate-limiting. The built-in limiter is per-instance (process-local token buckets). Across N replicas it enforces no global limit — put the real limit at the LB/WAF (per-IP, per-route for /auth/login and webhook ingress) and keep the in-app limiter as a second line.
  • Timeouts and body size. The API caps bodies at 32 MB (httpx.MaxBytes(32<<20)); nginx mirrors it with client_max_body_size 32m, proxy_read_timeout 60s, proxy_connect_timeout 5s.
  • CDN for static SPA assets now (nginx serves /assets/ with a one-year immutable cache), and for cacheable tiles later (chapter 6).

Watch out. The in-app key is the TCP peer (RemoteAddr), deliberately ignoring X-Forwarded-For, and the server mounts no RealIP middleware. Behind nginx or a cloud LB, every user shares one bucket per pod — the LB’s address. A shift-start login wave is throttled by your own limiter. Try it:

3.2 Health-check timing

/healthz pings Postgres with a 3-second context timeout and returns 200 {"status":"ok"} or 503 {"status":"db unreachable: …"}. The Compose api check runs every 10 s (timeout 5 s, 3 retries, 20 s start period); the Kubernetes guide’s probes use periodSeconds 5 (readiness) and 10 (liveness) with failureThreshold: 3.

Both probe kinds pull every replica when the database is what is down — correct, but a DB outage reads as a total API outage. Serve a friendly 503 at the LB, and alert on the DB, not on pod health.

04

API tier

Stateless Go replicas — the tier an autoscaler grows and shrinks.

Resources per pod (starting point; tune against load tests): CPU request 500m, limit 2 cores — analysis and trace are CPU-bound and run in-process, so headroom matters. Memory request 256Mi, limit 1Gi — the engines aren’t memory-hungry, but large traces and exports spike.

Probes: liveness and readiness both point at /healthz today (the earlier skeleton’s /readyz does not exist). Autoscaling: CPU target ~60 % and, better, a custom metric (p95 latency, or in-flight heavy analyses — which needs the gate from chapter 7). Band minReplicas 3, maxReplicas 30; three is the HA floor (survive a node loss and a rolling deploy). PodDisruptionBudget minAvailable: 2. Config: DSN, object-storage creds and OIDC via Secret/ConfigMap; every replica identical.

The HPA computes desired = ceil(current × observed ÷ target) inside its 10 % tolerance and clamps to [min, max]. Utilisation is measured against the request, not the limit.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: voltedge-api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: voltedge-api }
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }

The full Deployment skeleton (image, DATABASE_URL from a Secret, DOCS_DIR, probes, resources) is in the manual; note DATABASE_MAX_OPEN_CONNS there is a proposed variable — no code reads it.

05

Database tier — the real ceiling

Reads scale out; writes do not.

A single Postgres primary is your ultimate write ceiling. The whole game: keep writes on the primary, push the read flood to replicas, and never exhaust connections.

5.1 Connection pooling — do this first

The server opens an unbounded database/sql pool (sql.OpenDB(pgdriver.NewConnector(…)), no SetMaxOpenConns). Go’s defaults then mean unlimited open connections and only 2 kept idle: a burst opens as many as there are in-flight queries. Two mandatory fixes: bound the pool per pod (10–25; expose via an env var and call SetMaxOpenConns/SetConnMaxIdleTime/SetConnMaxLifetime — not implemented today) and put PgBouncer in transaction mode in front.

Size max_connections for PgBouncer’s pool + replication slots + admin headroom (e.g. 200), not the raw client count. The shipped Compose file uses DEFAULT_POOL_SIZE 25, RESERVE_POOL_SIZE 5, MIN_POOL_SIZE 5, MAX_CLIENT_CONN 1000 and Postgres max_connections=200. Play with the numbers — start with the “code today” preset:

How big should the server pool be? By Little’s law busy backends ≈ queries/s × mean query time: 600 q/s at 8 ms is ~5 busy; at 80 ms (a tile storm) it is ~48. Past a few connections per core, extra backends only add contention. The queue that forms when the pool is too small is an M/M/c queue:

Transaction-pooling caveat. No session-level state across transactions: prepared statements held across transactions, persistent SET, LISTEN/NOTIFY, cross-statement advisory locks. Code review: pgdriver v1.2.18 formats arguments client-side, and the API contains no LISTEN/NOTIFY or advisory locks. Migrations bypass the pooler on purpose. Test under load before trusting it — the Compose file has not been run in CI and its header lists the SCRAM auth check as the first thing to verify.

5.2 Read replicas and the read/write split

Run 2–3 streaming replicas via an operator (CloudNativePG or Zalando) — don’t hand-roll replication. Routing reads to them is code work: the app has one pool today. The highest-value single step is a read-only handle for the tiles package. Mind lag (usually <1 s): read-your-own-write paths (re-reading a feature you just edited) stay on the primary.

WorkloadRoute to
Tiles, trace reads, metadatareplica (tiles: mind the private-draft overlay)
Feature get/listreplica, except right after the user’s own write
Sessions, enforcement flag, writes, queue claims, migrationsprimary

5.3 PostGIS specifics

  • GiST indexes on every geom: the compiler emits CREATE INDEX … USING GIST (geom) (compiler.go:65) and a btree on territory_id. Confirm with EXPLAIN (ANALYZE, BUFFERS) on a real tile query.
  • Replicas inherit indexes.
  • Tune shared_buffers, work_mem, effective_cache_size; ST_AsMVT is memory-sensitive under concurrency.
06

The tile path

The hardest, highest-volume problem.

Every map tile is a live ST_AsMVT query, rendered per user, scoped to their territory and private-draft overlay, with no caching (api/internal/tiles/tiles.go; only Content-Type is set — no Cache-Control, no ETag). Reading tileHandler, one tile costs ~7 round trips — session + user, class lookup, the territory-enforcement flag, an information_schema column introspection (per tile!), the draft-overlay check, and finally the MVT query. Martin is still in the Compose file (started with --cache-size 0) but is superseded as the map origin.

Order of magnitude: 150–200 users panning is ~300–600 ST_AsMVT/s at 10–40 ms of Postgres CPU each — multiple cores. The fix is layered: 1) route tile queries to replicas; 2) make tiles cacheable by scope class, not per user — key (scope_group, has_drafts, z, x, y) when access is coarse; 3) split base vs overlay (shared published network from cache or pmtiles; thin per-user draft layer composited client-side); 4) add cache headers so browsers revalidate. 07

Keeping responsiveness under load

Three code-level changes; none is large.

7.1 Concurrency gate on analysis/trace not implemented

Load-flow, fault, contingency, nodal, arc-flash and trace run synchronously in the HTTP handler with no limit. A few concurrent heavy solves can pin every core on a pod and starve viewers. A weighted semaphore (at most k heavy solves per pod, 429 or queue beyond) turns silent collapse into back-pressure; for sustained analyst load, later move studies to a worker pool with the same SKIP LOCKED pattern.

7.2 TTL cache for metadata not implemented

metadata.Load runs five queries per call (class, fields, subtypes, terminals, plus subtype rules and domain lookups) and is called from ~66 sites. A 30–60 s per-pod cache removes a large slice of baseline DB load; accept ≤60 s staleness after a metadata edit.

7.3 The per-instance access cache exists

Territory/subordinate scope is cached per pod for 60 s (effectiveCacheTTL). A grant or revoke is instant only on the pod that handled it. If instant revocation is a security requirement, drop the TTL or add cross-instance invalidation (Redis pub/sub or NOTIFY). Otherwise accept and document the bound.

// illustrative, NOT in the repo: k heavy solves per pod, shed the rest
var heavy = semaphore.NewWeighted(k)
func gate(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !heavy.TryAcquire(1) { http.Error(w, "busy, retry shortly", 429); return }
        defer heavy.Release(1)
        next.ServeHTTP(w, r)
    })
}
08

Worker fleet

Compute-heavy work is already off the request path.

Separate processes drain Postgres queues with FOR UPDATE SKIP LOCKED, so they scale horizontally by replica count with no coordination. Scale export/import/webhook workers on queue depth (rows pending), not CPU.

WorkerScales howConcurrency / lease env (defaults 2 / 60 s)
exportworkerN replicasEXPORT_WORKER_CONCURRENCY, EXPORT_JOB_LEASE
importworkerN replicas; burstyIMPORT_WORKER_CONCURRENCY, IMPORT_JOB_LEASE

mcpserverN replicas (stateless); Compose pins a container name + port—

The claim is one statement: an UPDATE … WHERE id = (SELECT … WHERE status='queued' OR (status='running' AND lease_expires_at < now() AND attempts < N) ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1). Two workers get different rows; a dead worker’s job returns after its lease; attempts cap the loop. Watch it happen — crash worker 1:

fieldsync caveat. The maintenance loop (shared-pack scheduling + retention) runs in every replica, so a scheduled rebuild can be double-enqueued on a tick race — harmless, retention reaps the extra. The Kubernetes guide currently shows fieldsync as a replicas: 1 singleton; this guide and the code say replicas are safe.

Build less: shared packs

The field-pack builder is the most expensive thing to scale (CPU-heavy tippecanoe). The highest-leverage move for a large fleet is to build less: 60 crews on one depot is 60 identical builds. Shared packs pre-build a common area once as a reusable cell, overnight, and every crew whose access covers it downloads that build. It is the pack-side analogue of the scope-class tile cache. The knobs (FIELDSYNC_BUILD_WINDOW, FIELDSYNC_MAINTENANCE_INTERVAL, FIELDSYNC_KEEP_VERSIONS) live on fieldsync; see the Field Tool Admin Guide §6.

09

Pre-flight checklist

Before you scale out. The first two are not optional.

  1. Bound the DB pool per pod (10–25) — mandatory. Unbounded + N replicas = instant max_connections exhaustion.
  2. PgBouncer (transaction mode) — mandatory at N > ~10 pods.
  3. Health checks wired to /healthz.
  4. Concurrency gate on analysis/trace.
  5. Read replicas + route read-only queries to them — the capacity multiplier.
  6. Decide the tile caching story (coarse scope → shared cache; bespoke → replicas + horsepower).
  7. Metadata TTL cache.
  8. Edge rate-limiting at the LB (the in-app limiter is per-pod).
  9. Object storage (RustFS/S3) provisioned, replicated, backed up.
  10. Observability (Vector → Loki → Grafana) with the chapter 11 alerts.
  11. Postgres operator (CloudNativePG/Zalando) for replicas, failover, PITR.
  12. Load test at target concurrency on a production-shaped dataset before go-live.

10

Schema migrations & the compiler

Zero-downtime changes with live replicas.

VoltEdge compiles metadata into physical gis.<class> tables (task compile, task compile-all) and runs SQL migrations. With N live replicas, changes must be backward-compatible.

  • Additive, nullable first. The compiler only creates tables and ADD COLUMNs and never drops or alters an existing column; “disabling” a field is a status flip. But a non-nullable field is added as ADD COLUMN … NOT NULL in one step, which Postgres rejects on a populated table — so the nullable-first discipline is the metadata author’s, not automatic.
  • Run migrations once, as a pre-deploy Job or the Compose bootstrap sidecar. migrations/apply.sh takes no lock (it checks ops.migration_log, then applies), so concurrent runs race. Gate readiness on the schema version.
  • Breaking change order: expand → deploy code writing both → backfill → deploy code reading new → contract in a later release. Never expand and contract in one release.
  • A compile that rewrites a table takes a lock — schedule it off-peak and verify it is additive. Each compile also refreshes the Martin tile function and rebuilds CHECK constraints.

The Compose → Kubernetes path

You can stage this.

  1. Compose, scaled — docker-compose.prod.yml + infra/nginx/nginx.conf: nginx (non-sticky) → N API replicas → PgBouncer → Postgres, workers scaled by replica count, replication-ready primary (streaming replica a commented opt-in).     docker compose -f docker-compose.prod.yml up -d --build --scale api=4
  2. Managed Postgres + Kubernetes — operator or managed service for replicas/failover/PITR; API and workers as Deployments + HPA. The ~1,000-user shape of chapter 2.
  3. Add the tile caching tier and the analysis worker pool when chapter 11’s metrics say so — not before.

Default replica counts come from API_REPLICAS (3) and the *WORKER_REPLICAS variables (1). fieldsync and mcpserver run as single instances there by choice (fixed name + published port). Don’t skip to full Kubernetes on day one, but do the chapter 9 fixes regardless of rung — they are about the application, not the orchestrator.

Recipe cheat sheet

Bottom line

VoltEdge is architecturally ready to scale: stateless API, separated workers, externalised storage. Reaching 1,000 concurrent users is a tuning pass plus one design decision. The must-fixes are small: bound the pool, add PgBouncer, gate analysis concurrency, cache metadata. The capacity multipliers are infrastructure: read replicas, a non-sticky LB, autoscaled API replicas, edge rate-limiting. The one genuine design decision is tile caching, and its answer depends on how coarse your territory-access model is.

Bound the pool. Pool before pods. Reads to replicas, writes stay home. Everything else in this guide is a consequence.
