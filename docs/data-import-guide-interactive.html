Someone else's data.
Your network model.

Import reads from files or live databases, checks every row against the same rules a hand-entered feature obeys, and writes through VoltEdge's normal create/update engine. This edition is a working one — poke a transform, run a dry-run, flip a write mode, and watch what the real engine would do.

Use As in the top bar. Ada holds metadata:write — she authors import profiles. Omar holds features:write — he runs them. Val holds features:read — she watches jobs but can't start one. Dana has neither. Action buttons lock to what the persona may do.

Who this is for

Administrators who author the reusable mapping once (metadata:write), and operators who run it against new files or databases (features:write). You don't need both roles. The full manual (data-import-guide.md) carries every table and the honest-limits list; this edition keeps all ten ideas and makes each one something you can try.

One promise up front, because it's the whole design: there is no import shortcut that skips validation. Every imported row runs the identical checks a feature you draw on the map runs — and lands through the same engine, so it gets territory, write-scope and history too.

Three moving parts

An admin authors a profile; an operator runs it; a background worker applies every row.

In plain terms

Think of a profile as a saved recipe: "a file shaped like this becomes this kind of feature, this way." An admin writes the recipe once. After that, any operator can point it at a new file and press go — the mapping is already decided.

  1. Profile (admin, once) — the reusable mapping: target class, source format, how to match rows, how geometry is built, and one row per source column → target field.
  2. Run (operator, each time) — choose the profile, point it at a source, dry-run to catch problems, then start the job. You get a job id back immediately.
  3. Worker (automatic) — a separate background process claims the job and applies every row, one transaction at a time, so you don't keep a page open.
Under the hood

Authoring lives under /admin/import-profiles (metadata:write); running lives under /imports (features:write); the worker is cmd/importworker. Rows are applied through crud.CreateFeature/UpdateFeature — the same validated path the REST API and field-pack sync use. Nothing about import is a bulk back-door.

Authoring a profile

Admin → Data import. The reusable recipe, keyed by a code, targeting one feature class.

In plain terms

A profile answers five questions: what class am I making, how do I decide new-vs-existing, where does geometry come from, and (for a live database) which connection. Set those, then map the columns (Chapter 4).

Mapping the columns

One row per source column → target field, each with a transform.

Four transforms turn a source cell into a field value. Try each one — change the input and watch the output (and the errors).

Try it

Transform playground

Result
TransformWhat it does
directCopy the source cell as-is.
constantWrite a fixed literal — no source column. Stamp every row the same value.
scaleMultiply a numeric source value by a factor (metres → millimetres).
domain_mapTranslate via a lookup. A value with no entry in the map is a per-row error — a stray code is caught, not guessed.
Under the hood

There's no auto-map — each mapping is explicit, which is what makes a profile reusable and auditable. A blank source cell leaves the field unset (blank ≠ empty string). A mapping to a field that was later removed is silently dropped. Domain membership, subtype validity, ranges and geometry type aren't checked here — they're checked per row by the validator in Chapter 6.

Tip — Geometry is not a field mapping. It's the profile's geometry mode + columns (Chapter 8). And subtype is pinned on the profile, not mapped per column.

  1. Pick a profile — only active profiles you may run appear.
  2. Point it at the source — choose the file (browser-parsed formats preview; GeoPackage/SpatiaLite upload raw, pick a layer); live-DB needs no upload.
  3. Dry-run — validate a sample, write nothing (Chapter 6). Fix and repeat until clean.
  4. Start — enqueue; you get a job id back at once.
  5. Watch — the job shows live tallies (total / inserted / updated / skipped / errored) and a per-row error report. Terminal states: succeeded, failed, cancelled.
Under the hood

Your territory scope is snapshotted when you start the run and applied by the worker — so an import writes only where you are allowed to write, even though a background process does the work.

The dry-run

Validation without writes — the same checks a hand-created feature runs.

In plain terms

The dry-run runs your sample through the real pipeline — apply the mapping, build the geometry, validate — and tells you, row by row, whether each one would go in. It writes nothing. Fix the profile or the data and run it again.

Under the hood

Each sampled row runs BuildAttributes → AssembleGeometry → crud.ValidateFeature — required fields, coded-domain membership, ranges, geometry type. For upsert it also checks every match field has a value. It's deliberately create-shaped: it tells you a row would validate, not whether it matches an existing feature. The sample is capped (a few hundred rows); the committed load validates the whole file the same way.

The load

Per-row transactions, the normal CRUD path, upsert, and safe re-runs.

The load is not all-or-nothing. One transaction per row — a bad row rolls back only itself, and the stream keeps going.

For upsert, each row matches on your match fields. Set the match count to see the decision.

Try it

Write-mode decision

Write mode
Existing matches
GuaranteeHow
Partial success is normalOne transaction per row; failures are isolated and reported with their row number.
Imported features behave like hand-made onesWritten through CreateFeature/UpdateFeature — territory assignment, Phase-58 write-scope, and full history all apply.
Re-running is safeInsert ids are deterministic (job id + row number) with ON CONFLICT DO NOTHING — a re-run is a no-op for rows already in, not a duplicate; upsert rows re-match and update.
Ambiguous matches are skippedTwo+ existing matches → the row is skipped and reported, never applied to a guess.
Connectivity isn't auto-built. An import brings the features in; wiring them (connectivity) is a separate step afterward, on the map or via the connect tools.
8

Geometry & reprojection

Nominate the mode; VoltEdge lands it in the class's coordinate system.

none

Attribute-only — no geometry.

native

The source's own geometry (GeoPackage/SpatiaLite/PostGIS/MSSQL blobs, inline GeoJSON), decoded per row.

lonlat

A Point built from two numeric columns you name.

wkt

Geometry parsed from a WKT text column.

Whatever the source CRS, geometry is reprojected to the target feature class's SRID (usually EPSG:4326) on the way in — so you don't pre-project your data. MSSQL geography columns even get their lat/lon axis order corrected automatically.

Tip — Geometry length matters for electrical classes: a conductor's impedance scales by its real length (ST_Length). A zero-length or missing line simply resolves no impedance — it won't error, but it won't carry R/X either.
