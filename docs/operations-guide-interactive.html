Device Operations

The record of what the network's protective and switching devices actually did — every trip, lockout, reclose and open/close, with a cause, a time, and where the report came from. This is the working, in-browser copy: the widgets below run the real model on sample data.

1

What it is — and what it isn't

Three records sit close together. Keep them straight and everything else follows.

A device's state is only where it stands right now. The operations log is the history of how it got there. An outage is the customer consequence — a device operation is the electrical event that often causes one.

RecordAnswersWhere
device_state"Is this breaker open or closed now?"a column on the feature — current value only
Device operation"What has this device done, and how often?"the operations log — this guide
Fault"What electrical fault did it clear?"Faults module
Outage / incident"Who lost supply?"Outage Management (OMS)

An operation is append-only: it's a thing that happened, so it's never edited or deleted — the record of a trip stands. Each one carries a device, an operation type, a source, a time, an optional cause, and optional links to the fault / incident / switching step it relates to.

The outage board tells you who is off supply. The operations log tells you what the devices did — to get there, and to restore it.
2

The four reports

One page, four lenses. Flip between them — the sample log below is live.

Timeline is the live "what just happened" board. By device is the trip-count rollup — the reliability signal (which recloser operates most). Devices is the inventory: every operable device, its current state, and its last operation (or never). Abnormal is the off-normal report: every switching device whose live position contradicts its declared normal position — a normally-open tie left closed, or a normally-closed device left open. Try it: two devices in the sample are off normal (an isolated switch and a closed tie).

Logging appends to the sample log and updates every view at once — exactly what the real POST /operations does. The device list in Devices is discovered from the classes that model a device_state, so it includes devices that have never operated.

Abnormal is a report, not an alarm VoltEdge doesn't page anyone or auto-correct a position — it lists the off-normal devices so you can see at a glance whether the network is in its normal configuration, and decide. The report is discovered automatically: the engine finds every class that models both device_state and normal_state and reads the rows where the two disagree (api/internal/deviceops/abnormal.go:38–88, GET /operations/abnormal), so a fuse — no declared normal posture — is simply out of scope.

4

Switching — planned programs

The third tab. Author an open/verify/earth/close program for planned work, then tick it off.

The Switching tab is where an operator authors and runs a planned switching program — an ordered open / verify / earth / close list — for planned work (a maintenance isolation, a construction cut-over) that is not tied to any outage. It's the standalone sibling of the switching order OMS generates for an incident: it writes to the same tables and uses the same execution, so ticking a step off here flips the device's live device_state and logs the operation (source switching_order) exactly as an incident order does (web/src/routes/switching.tsx, api/internal/oms/planned_switching.go).

StepWhat you do
Createa program with a title and an optional booked window — empty, or seeded from a target device (pick a device and VoltEdge pre-fills the standard open → verify → earth → close program to isolate and restore it).
Edit the stepsadd, edit, delete, reorder (move up/down). Each step is a phase (isolate / restore), an action (open / close / earth / verify / note), an instruction, and — for an open/close — the device.
Issuedraft → issued, when it's ready for the field.
Run ittick each step as the crew performs it. open sets the device OPEN, close sets CLOSED, un-ticking restores the opposite — each through the validated, history-logged, safety-interlocked path (a blocking tag refuses it), and each a logged operation. Status: draft → issued → in_progress → completed.
Edit the program, operate the device You can only edit, delete or reorder a step that hasn't been executed — once a step has flipped a device it's part of the record. To undo an operation, un-tick the step; to abandon a program, Cancel it (the steps are kept).
The deep model behind switching — what each device is, what opening one does to the network, barriers, isolation boundaries, and how an incident switching order is generated — lives in the Switching & Protection guide. This tab is the operator's authoring-and-execution surface for it.

Endpoints: GET/POST /oms/planned-switching, PATCH /oms/switching-orders/{id} (retitle / issue), POST /oms/switching-orders/{id}/steps, POST /oms/switching-orders/{id}/reorder, PATCH/DELETE /oms/switching-steps/{id}, reusing the shared .../execute and .../cancel (api/internal/oms/http.go:115–126). View needs oms:read; build and run need oms:write.

5

Feeding it from SCADA

An external system pushes operations straight in — through the same hardened webhook pipeline that feeds features, readings, work orders and faults.

  1. Set up (admin): create a webhook endpoint with Target = "Device operation", and give it a system_code so VoltEdge knows which external system the ids belong to.
  2. Name the device: send VoltEdge's own device_class+device_id, or just the device_external_id — VoltEdge resolves it to the right feature through the device's external_ref (the SCADA id you tagged it with). The external side never needs VoltEdge uuids.
  3. Push the event to the endpoint. Each carries the sender's own external_id — the dedup key.
Live widget

SCADA delivery & idempotency

SCADA re-sends A re-delivered batch records nothing the second time — the external_id → source_event_id dedup means a trip is never double-logged, no matter how many times the event arrives.

Links & access

Where operations sit in the operational family, and who can see and log them.

The operation → fault → outage chain

device operates (TRIP)→ clears a FAULT→ customers lose supply (OUTAGE)
SWITCHING ORDER restores them→ executing an open/close step logs an operation

An operation can carry a fault_id and an incident_id; an executed switching step logs its own operation. The operations log is the electrical ground truth beneath the outage story — which is why it lives beside Faults and Outage Management, not merged into them.
