The Feature Catalog describes every class in the VoltEdge data model. This is the same catalog as a working tool: the dataset below was extracted from the seeds and migrations (not typed in), the manual's prose is attached to each class, and the widgets run the real create-validation, import-coercion, connection-matching and compile rules against it. A coverage dashboard shows where the manual and the seeds disagreed, and what was corrected.

Use As in the top bar. Data entry holds the editor role (features:write, connectivity:commit, trace:run); Modeller holds admin (adds metadata:write — the only role that may change classes, fields and domains); Analyst holds analyst (read + trace:run); Auditor holds viewer (read-only, incl. metadata:read). Reading is open to everyone; the persona only gates the actions that would write or run something.

Who this is for

People entering data (what does this class need? why does my import reject?), modellers (what exists before I add a class? what will compile?), analysts (what can a trace walk through?) and auditors (is the documentation true?). If you want a narrative of building a substation, read the Substation Guide; this is the reference you keep open on the second monitor.

Everything here is read from one embedded dataset: classes, fields, domains, connectivity rules, relationship classes. Nothing talks to a server.

01

Orientation

Five ideas, one search box, and the whole manual on tap.

VoltEdge is metadata-driven: the network is not a set of hard-coded tables but a catalog of feature classes defined in data (metadata.feature_classes and its companions, loaded by the files in seed/). Every entry in the manual is written to the same seven headings — what it is, what it does, how it's specified, network role, terminals, relates to, where it's drawn — and every one of those facets is a tab in the class browser below.

1 · Geometry type

point, line, polygon or none. A none class has no map location at all — it can only be a diagram placement or an attribute record. Half the control room is like this.

2 · Network role

junction (a node with terminals), edge (a conductor), container (a grouping), none (off the network). Traces and load flow walk only junctions and edges, alternating node → edge → node.

3 · Terminals

Only junctions have them: named ports (T1, HV, LINE …) that network_rules use to say which side of a device a connection may land on.

4 · Two graphs

Connectivity (terminals + rules, walked by every electrical analysis) and containment / composite (relationship classes, read by CIM export). A transformer is connected to a busbar and contained by a substation — stored and traversed independently.

5 · Render context

A class can carry a map and/or a diagram symbology rule. The diagram falls back to map — and a none-geometry class has no map rule, so it must have a diagram rule or it draws as nothing.

Rule of thumb “A subtype is for differences the network can see; everything else is a field.” Construction the network can see (overhead vs underground, two- vs three-winding) is a subtype; functional role it cannot see (main vs service, a panel's type, an IED's role) is a field. The field names are also an API: a node carrying primary_voltage + secondary_voltage is treated as a transformer by the load flow whatever its class.

One box over classes, subtypes, fields, domains, domain values (codes and labels), terminals and the manual's own text. Try 33KV, device_state, T3, tertiary or metering.

03

Fields, domains & data entry

What a value must look like — and how the create endpoint decides.

A field has a data type (text, numeric, integer, boolean, date, timestamp, uuid, jsonb), optionally a domain that constrains it, and a nullable flag. Three rules explain almost every rejected edit:

  1. Coded values are codes, not labels. A coded domain such as VOLTAGE_CLASS holds a code (33KV) and a label (33 kV). The check is an exact, case-sensitive match on the code.
  2. “Required” is enforced in two places. Most required fields are both a NOT NULL column and a subtype_field_rules row (93 of the 101 in the seeds): the API checks the rule first and gives a clean message, the column is the backstop. A few — fields added later to a populated class, like METER.ct_ratio — are nullable columns made required for one subtype only (8 in the seeds). Classes with no subtypes can only rely on NOT NULL.
  3. Validation is fail-fast and ordered: subtype → geometry → required-by-subtype → unknown/computed/hidden fields → each value's type, domain and range. You see the first failure only.

Data-entry form

Worked example A 33/11 kV power transformer: class POWER_XFMR, subtype 1 (two_winding). Required for both subtypes: primary_voltage (coded VOLTAGE_CLASS — send 33KV) and condition_rating (GOOD). secondary_voltage is a plain number in volts (11000) and its presence is what makes the load flow treat the node as a transformer. The three-winding extras (tertiary_voltage, z_hv_tv_pct…) stay optional even for three_winding, so a survey without tertiary nameplate data is still enterable.

3.3 Will my import be accepted?

The import engine maps each source column to a field with a transform (direct, scale, constant, domain_map), coerces the cell to the field's type — a blank cell means “unset”, true/t/1/yes/y are booleans — and then hands the row to the same create validation as the form. Paste a CSV below; columns are matched to fields by name (case-insensitive, spaces and hyphens read as underscores), and each cell is checked as the engine would. Real profiles are authored in /admin/imports and may map differently; this checker assumes “column name = field name”.

04

Network: connectivity, traces & relationships

What may connect to what, what a trace walks, and what is merely attached.

A feature participates in two graphs that never touch. Connectivity is built from terminals and network_rules (a directed allow-list) and stored per connection; relationships (containment, composite, spatial support, sensing, routing …) are stored separately and read mainly by CIM export and the relationship screens. The widgets below let you probe each graph and see where a class sits on one, both, or neither.

4.1 Connectivity and terminals

Choose a class to see its terminals and every rule that touches it. Then test a connection: name the two ends, optionally their subtypes and phases, and get the verdict the connect endpoint would give (matchRule: null pins are wildcards, the most specific rule wins, a rule with is_valid = false is reported as disabled, and a rule authorizes either end naming first).

Interactive · 9

Connectivity & terminal explorer

Common mistake Connecting a conductor to MV_ARRESTER T2 or MV_VT T2: the ground terminal has no rule (there is no “earth” class), so the zero-trust default rejects it. Likewise EV_CHARGER, PROTECTIVE_RELAY and every none-role class have no terminals — they attach by relationship, never by connection.

4.2 What a trace walks, and where it stops

A walk crosses only junctions and edges, alternating node → edge → node. It halts at any class carrying a barrier rule: every class that has a device_state field with an OPEN value gets an OPEN barrier on every barrier-respecting configuration (seed/trace_barrier_resync.sql), and operational_state ISOLATED / RETIRED are barriers on the downstream and upstream configurations. A tier guard (migration 0126) stops a downstream walk from stepping to a strictly lower trace_tier. Build a small feeder out of legal connections, flip devices OPEN and run the trace; or switch to the class-level view to see which classes a start class can reach at all. (The live engine walks individual features; this shows how the metadata shapes the walk.)

05

Drawing, axes & the compiled table

Map or diagram? Which taxonomy puts it where? What does compile produce?

Where a feature can be drawn is decided by four independent facts: its geometry_type, whether it is geometry_optional (a feature may exist without a map position), whether it is is_diagram_placeable, and which symbology rules exist. A diagram renders the diagram rule and falls back to the map rule — and a none-geometry class has nothing to fall back to.

5.3 What “compile” produces

A class is metadata until it is compiled: the compiler (api/internal/compiler/ddl.go) turns the class, its subtypes, fields and domains into gis.<table>. Every table gets the same system columns, then one column per active field with NOT NULL when the field is not nullable and a CHECK when it is coded or ranged. The preview below is generated by the compiler's own rules. Adding a field or value is additive (ALTER TABLE … ADD COLUMN, nullable fields only on a populated table); the admin API commands for each change are shown for the Modeller.

06

Is the manual true?

The manual-versus-seeds audit, what it found, and what was fixed.

A reference is only worth keeping open if it is right. For this edition the manual was parsed with a script and every class entry was cross-checked against a database built from the migrations and the seeds (the metadata phase of task seed-all, plus the symbology, ownership, boundary-role and trace-tier seeds that seed-all does not run): class inventory, role and geometry, subtypes and codes, fields, types, domains and required flags, terminals and roles, connectivity rules, relationship classes, colours and placement. The dashboard compares the earlier edition with the corrected edition; the ledger lists each correction with its evidence.

Reading the numbers

“Named in the entry” counts what the class's own prose mentions: a field, a rule neighbour, a relationship partner, a subtype or a terminal. A low number is not an error — the entries are written to explain, not to enumerate — which is why the appendices (C: fields, D: every connectivity rule, E: every relationship class) now carry the complete, generated lists. Drift is different: a statement that the seeds contradict. Those are the ledger.
