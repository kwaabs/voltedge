01

The asset-tag mental model

An identity label over a feature that already exists — with a lifecycle that mirrors the field.

This chapter builds the vocabulary the rest of the guide assumes. Read it once. If you take only three ideas away, take these: an asset tag is an identity label over a feature that already exists, not a new record about it; a feature can carry many codes but exactly one is primary (the one that gets printed); and a code has a lifecycle — it can be active, retired, or replaced — that mirrors the messy reality of labels in the field.

1.1 What an asset tag is

▶ Operator

An asset tag is a short, scannable code — something like VE-7Q3KA — minted for a feature in your network, printed on a small label as a QR code, a Code128 barcode, and human-readable text, and physically stuck on the plant: the transformer tank, the pole, the switch cubicle, the pillar door.

Its entire job is to close the loop between the thing in the field and the record in VoltEdge. A field worker standing in front of TX-Feeder7-014 with a phone points the camera at the label, and VoltEdge opens that exact transformer — ready to read its details, attach an inspection, book a defect, or raise a fault. No hunting on a map, no keying an ID, no ambiguity about which of three transformers on the pole you meant.

That is the whole promise, and it is worth stating what makes it trustworthy: every feature has one. You never have to wonder whether an asset was tagged — the system mints a tag for a feature the instant that feature exists, by any path it could have been created (Chapter 2). Tagging is not a project you run; it is a property of the data.

1.2 What an asset tag is not

∑ Model

The distinction that keeps the model clean is this: an asset tag is not a GIS feature and not an operational record. VoltEdge has three families of thing, and a tag is none of them — it is a thin fourth layer that points at the first:

  • A feature is a row in the network model — TX-Feeder7-014 is a DIST_XFMR with a location, terminals, a rated kVA, upstream and downstream connections. It shows up in traces and load flow.
  • An operational record — a defect on that transformer, an outage that de-energised it, a fault event — is a thing that happened to the asset. These earn their own database schemas (wam, faults, and OMS) because each is new information about the asset.
  • An asset tag is the opposite of an operational record. It carries no new information about the transformer — no condition, no event, no measurement. It is purely an index entry: “this code means that feature.” It is keyed by the asset rather than being a record about it.

That single design decision — tags are an identity layer, not a record — is why they don't get their own schema and why a tag has no independent life. A tag with no feature behind it is meaningless, so when a feature is truly purged, its tags are cleaned up automatically (Chapter 2). A defect survives its asset for the audit trail; a tag does not, because a code that resolves to nothing is just a dead end.

Features and records are nouns with a story; a tag is just a name you can scan.

1.3 One feature, many codes, one primary

▶ Operator

Here is the idea that surprises people first: a single feature can carry several tags at once. That is not a bug — it is the model bending to fit reality. Real plant already has numbers on it. TX-Feeder7-014 was surveyed years ago and someone painted OLD-4471 on the tank. When VoltEdge was rolled out it minted its own code, VE-7Q3KA, for that transformer. Both are legitimate ways to name the same asset, and a field worker might read either one. So the transformer carries both:

   TX-Feeder7-014  (a DIST_XFMR)
     ├── VE-7Q3KA   generated,  PRIMARY     ← the VoltEdge-minted code, printed on the new label
     └── OLD-4471   external                ← the legacy number, registered so it still resolves

Every code on a feature falls into one of two sources:

  • generated — minted by VoltEdge itself. Every feature gets exactly one of these at birth, and its code always begins VE-.
  • external — a pre-existing number (a legacy asset ID, a manufacturer serial, a code from the system VoltEdge replaced) that someone registered against the feature so that scanning or searching it lands on the right record. VoltEdge does not invent these — a person types them in (Chapter 3).

Among all the codes on a feature, exactly one is marked primary. The primary is “the code that gets printed” — the one that goes on the official VoltEdge label affixed to the plant. A feature has at most one primary at any moment (the database enforces this literally — §2.5), and by default it is the generated code, because that is the one VoltEdge controls and can reissue if the label is damaged.

Caution You can make a registered external code the primary if your organisation would rather print the legacy number people already know — but there is still only ever one primary. Promoting a new primary automatically demotes the old one; the two never coexist.

1.4 The three lifecycle states

∑ Model

The second surprising idea: a code does not simply exist or not-exist. Labels live in the physical world, where you cannot un-print a sticker or guarantee that the damaged one was peeled off. So a code has a status that models what is true in the field, and there are exactly three:

statusResolves on scan?What it means
active✅ yesThe code is live and correct. The normal state.
superseded✅ yesThe code was replaced by a reissue, but it still resolves — because an old label may still be stuck on the asset in the field, and a scan of it should still find the right feature.
void❌ noThe code was retired as wrong and deliberately does not resolve — scanning it returns “not found” (the message says retired), because it should never have pointed anywhere.

The difference between superseded and void is the crux, and it is entirely about what you want a scan of the old sticker to do:

  • Dana reissues TX-Feeder7-014's label because the printed QR was scratched illegible. The system mints a fresh code and marks the old one superseded. If a colleague later scans a surviving old label, it still opens the transformer — the old number was never wrong, just replaced. (Chapter 3 covers reissue.)
  • By contrast, if a code was minted against the wrong feature, or an external number was keyed in against the wrong asset, you void it. A voided code is a dead end forever — and critically, a voided code is never reused; the code space only ever moves forward, so an old label that resurfaces can never silently resolve to some unrelated new asset.

There is one guard rail that ties status back to §1.3: you cannot void the primary code. The primary is by definition the one that is printed and in service, so voiding it would leave the asset with no printable identity. If you need to retire the primary, you reissue it (which supersedes it and mints a replacement that becomes the new primary) — you never simply void it. Chapter 3 walks this.

Tip One-line summary of the trio: active = use it; superseded = old-but-still-valid; void = wrong, dead, and never recycled.
Code-verified quirk The server's Reissue refuses only a superseded code (tag "…" has already been reissued). It does not refuse a void one: reissuing a void code flips it to superseded — i.e. it starts resolving again — and mints a fresh non-primary code. The web console hides the reissue button on superseded rows only, so it will offer reissue on a void row. Treat that as a correction path of last resort, not a normal move. (assettag/store.go:472)

1.5 Where tags live, and who can touch them

∑ Model

Tags occupy a deliberately small footprint:

  • Storage. Every code is one row in a single table, runtime.asset_tags — the runtime schema, alongside the cross-class feature index it depends on, not a schema of its own (Chapter 2 explains why that is the right call). A row records the code, which feature it points at (by class and id), its source, whether it is primary, its status, and how many times its label has been printed.
  • The API surface. A small set of endpoints mounted at /tags handles resolving, listing, registering, and the lifecycle actions. There is deliberately no “create a generated tag” endpoint — minting is automatic and belongs to the database, not to a caller (Chapter 2). The same router is also mounted a second time under the field-sync API, so a device can resolve online and a tags:write user can manage tags from the field.
  • Two permissions gate everything (method-aware: GET needs read, every POST needs write):
    • tags:read 🔒 — the viewer / field-technician tier. It lets you scan and resolve a code, list a feature's tags, and print a label. Femi and Priya hold it. Seeded to the roles viewer, analyst, editor, admin, break-glass-admin and field-technician.
    • tags:write 🔒 — the editor tier. It lets you register a legacy code, set the primary, void, reissue, and record a print. Dana holds it; Ada holds it through the admin role. Seeded to editor, admin and break-glass-admin only (migration 0115).

🗺️ Crucially, reading a tag is territory- and visibility-aware. Holding tags:read does not let you resolve any code in the system — only codes on features you can already see. If TX-Feeder7-014 is outside your assigned territory, scanning its label returns “not found,” exactly as if the transformer did not exist for you. This is not a special rule bolted onto tags; a resolve runs through the very same read-scope and private-draft checks that govern every other way you might reach a feature (Chapter 5 shows how, and why “not found” — rather than “forbidden” — is the deliberate answer).

Code-verified addition: the territory exemption is real — users holding territories:unscoped (admin, break-glass) skip territory and draft scoping entirely, and territory scoping can be switched off for the whole system (“enforcement off”). Geometry-less feature classes carry no territory and are never territory-scoped; a geometry feature with no territory is hidden from every scoped user (fail closed).

Anatomy of a tag & how minting works

A code scheme with a check character, one trigger, one partial unique index.

This is the one chapter written mostly in the ∑ lane. It answers a question a careful administrator eventually asks: can I trust that every asset really has a tag, that no two assets share one, and that a mis-read label won't silently open the wrong transformer? The answer rests on three small pieces of machinery — a code scheme with a built-in check character, a single database trigger, and one partial unique index. If you only ever use tags you can skip to Chapter 3; nothing here changes what you press. If you own the system, this is the chapter that lets you sign off on it — including a few places where the code is narrower than the folklore, flagged code-verified below.

2.1 Opening up VE-7Q3KA

▶ Operator

Take the code VoltEdge minted for the running-example transformer and pull it apart:

   VE-7Q3KA
   ─┬ ──┬─ ┬
    │   │  └── check character   (A)  — a guard digit computed from the body
    │   └───── body              (7Q3K) — a counter, rendered in Crockford base32
    └───────── prefix            (VE-) — "this is a VoltEdge-minted code"

Three parts, each with a job:

  • The VE- prefix announces the code's origin. Every code the system mints starts this way, so a human — or a parser — can tell a VoltEdge-generated code from a registered legacy number (OLD-4471) at a glance.
  • The body (7Q3K) is the actual identity: a number from a single global counter, written in a compact, human-friendly alphabet.
  • The check character (A) is not part of the identity at all. It is derived from the body, and its only purpose is to catch a typo before it can do harm.

2.2 Why Crockford base32 — the alphabet that avoids 1/I/0/O

∑ Model

The body is a value from the global sequence runtime.asset_tag_seq, rendered by runtime.encode_base32_crockford(bigint). Base32 means each character carries five bits, so codes stay short — a body of four characters already addresses over a million assets (32⁴ = 1,048,576), six covers a billion — while remaining all-caps alphanumeric, which prints crisply and reads aloud cleanly over a crackly radio.

The specific alphabet matters. Crockford base32 is:

0123456789ABCDEFGHJKMNPQRSTVWXYZ

Look at what is missing: there is no I, no L, no O, and no U. That is deliberate. On a scuffed label under a head-torch, I and 1, O and 0, L and 1 are exactly the pairs a tired eye confuses; U is dropped to dodge accidental profanity in generated codes. By simply never emitting those four letters, the scheme removes the most common misreads by construction — you cannot mis-key an O for a 0 in a code that can never contain an O.

Code-verified: the body is not zero-padded — sequence value 1 is VE-11, 32 is VE-101 — so codes grow by one character each time the counter crosses a power of 32. And nextval is non-transactional, so a rolled-back insert leaves a gap: the codes are unique and increasing, not gap-free.

Tip This is why you will never see one of those letters in a VE- code, and why, if someone reads you a code containing an L, you know immediately they've misread a 1 — or they're reading a legacy number, not a VoltEdge code.

2.3 The check character — catching a mis-read

∑ Model

The last character, runtime.asset_tag_check_char(body), is a position-weighted sum of the body's digit values (weight = 1-based position), taken mod 32, and mapped back through the same 32-character Crockford alphabet. Worked for 7Q3K: 7×1 + 23×2 + 3×3 + 19×4 = 138; 138 mod 32 = 10; digit 10 is A.

What that buys you: if a field worker (or an OCR scan of a smudged label) transposes two characters or reads a single character wrong, the check character computed from what they typed will usually not match the one that is printed. A single mis-keyed character in the body can only slip through if the weighted change is a multiple of 32.

Two design choices are worth calling out for anyone integrating:

  • It is not Crockford's own mod-37 check symbol. That scheme adds five extra characters (* ~ $ = U) to the check position. Those would look ugly on a printed label and — more importantly — several of them must be percent-escaped inside the QR code's deep-link URL. By keeping the check character inside the clean 32-letter set, the whole code is URL-safe and label-safe with no escaping, ever.
  • All three functions — the base32 encoder, the check-character function, and the runtime.encode_asset_tag(bigint) that wraps them with the VE- prefix — are declared IMMUTABLE. That lets them be composed inside a single INSERT … SELECT, which is exactly how the backfill (§2.7) tags a whole pre-existing network in one statement.

Code-verified corrections to the folklore. (1) The detection rate is not a flat “1 in 32 slips through”: a one-character substitution at 1-based position i with digit change d is invisible only when d·i ≡ 0 (mod 32). Every odd position is therefore always caught, position 2 misses one substitution in 31 (d=16), position 4 misses three, position 8 misses seven. (2) Swapping two adjacent different characters always changes the sum by exactly their difference, so adjacent transpositions are always caught. (3) Nothing on the server verifies the check character today. Resolve and LookupByCode do an exact primary-key lookup (assettag/resolve.go:33, store.go:48); the web /t/:code page and the Flutter app do not validate it either. A mis-keyed code is simply “not found” — unless it happens to be another real code. What the check character gives you today is a design guarantee: two distinct minted codes of the same length never differ in exactly one character at an odd position, so a single slip cannot turn one valid code into another in those positions. A client-side validator (like the one below) can use it to give a friendlier message before calling the API.

Caution The check character validates shape, not authority. It proves a code was typed without a single-character slip; it does not prove the code exists or that you're allowed to see the feature behind it. Those are the resolver's job (Chapter 5), and they are enforced separately.

2.4 The store: one table, runtime.asset_tags

∑ Model

Every code — generated or registered, active, superseded, or void — is exactly one row in one table, runtime.asset_tags (migration 0114). There is no per-class tag table and no tag schema; §2.8 explains why. The columns you'll meet again throughout this guide:

columnwhat it holds

Two ordinary indexes back the two hot read paths — (feature_class_code, feature_id) and (feature_id) — for “list this feature's tags” and “resolve this code.” The third index is not ordinary, and it is the whole integrity story.

2.5 One primary, enforced by the database

∑ Model

Section 1.3 promised that a feature has at most one primary code. That is not a convention the application politely upholds — it is a partial unique index the database refuses to violate:

CREATE UNIQUE INDEX asset_tags_one_primary
  ON runtime.asset_tags (feature_id)
  WHERE is_primary;

Read it as: “feature_id must be unique among the rows where is_primary is true.” Because the WHERE is_primary clause makes it partial, the constraint only counts flagged rows. So a feature is allowed to have:

  • one primary and any number of non-primary codes — the normal case; and
  • a voided former primary sitting alongside a new primary — because the old one is no longer flagged is_primary, it simply isn't counted.

This is why SetPrimary (Chapter 3) must clear the old flag and set the new one inside a single transaction: for one instant both could be flagged, and the index would reject the write unless the clear and the set land together. The application does exactly that. The upshot for you: it is structurally impossible for a feature to end up with two primaries, no matter what sequence of clicks, API calls, or concurrent edits gets thrown at it. Note that the index guarantees at most one — nothing forces at least one, which is why the bulk printer falls back to the newest active tag (§4.3).

2.6 How every feature gets a tag — the registry trigger

∑ Model

Here is the mechanism behind the boldest claim in Chapter 1: every feature has a tag, by every path a feature can be created. It works because tags don't watch the features directly — they watch the feature registry.

runtime.feature_registry (migration 0108, see the feature-registry note) is a cross-class index that the metadata compiler wires to every gis.<class> table with an AFTER INSERT/UPDATE/DELETE trigger. So the registry sees a new feature the instant it is written — whether it came from the REST API, an MCP tool, a field-sync replay, or a raw SQL seed that INSERTs straight into gis.* and never touches the Go code at all. That total coverage is precisely what “mint a tag for every feature” needs.

So tags hang a single trigger, feature_registry_tag_sync, on the registry — not one per class — declared AFTER INSERT OR DELETE and running runtime.sync_asset_tag():

  • On INSERT (a feature just entered the registry): mint one tag — source = generated, is_primary = true, status = active. Two guards make it safe to fire on anything: an EXISTS check means a feature id that reappears never mints a second generated tag, and ON CONFLICT (tag_code) DO NOTHING absorbs any code collision harmlessly.
  • On DELETE (a feature was hard-deleted — a purge removes its registry row): delete the now-dangling tags, so a resolve of the old label cleanly finds nothing.

The subtle, important part is what the trigger is not attached to:

  • A soft delete is an UPDATE, not a DELETE — the registry row survives. The trigger is not attached to UPDATE, so a soft-deleted asset keeps its tags. That is correct: the physical label is still stuck on the plant in the field, and a scan should still identify what's there, even if the record is retired from the live network. (Code-verified: getFeature has no soft-delete filter, so a scan of such a label still resolves and the envelope carries deleted_at.)
  • A registry re-sync (a bulk recompute) is also an UPDATE, so it never re-mints. Recompiling a class or rebuilding the registry does not spray a network with duplicate tags.
Tip Put plainly: inserts mint, purges clean up, and nothing else touches your tags. Everyday edits, soft-deletes, and re-syncs leave them exactly as they were.
Code-verified hazard Register accepts any text as an external code — including something that looks like a future VE- code. If an external code equal to the next generated code already exists, the trigger's ON CONFLICT (tag_code) DO NOTHING swallows the collision and the new feature is born with no tag at all (the sequence value is already spent). The “features with no tag” probe (§8.2) is the way to find that. Don't register codes that begin VE- by hand. The widget below can reproduce it.

2.7 The backfill — the day the migration landed

∑ Model

A “trigger on new features” would only tag features created after it was installed. So migration 0114 ends with a backfill: a single INSERT … SELECT over the entire existing registry — WHERE NOT EXISTS a tag already — that mints a primary generated tag for every feature that was already in the network. (This is where the IMMUTABLE functions of §2.3 pay off: the whole encode pipeline runs inside that one SELECT.) The practical consequence: from the moment the module went live, there was never a window of untagged plant. TX-Feeder7-014, surveyed years earlier, got its VE- code in that sweep. The backfill is a one-off in the migration; it is not re-run, and no endpoint exposes it.

2.8 Why tags ride runtime, not a schema of their own

∑ Model

Faults, outages, and defects each earn a dedicated schema (faults, OMS, wam) because each is a new record about an asset — new information with its own lifecycle and audit trail. Chapter 1 argued a tag is the opposite: a thin index keyed by the asset, carrying no new information. Two facts make the runtime placement the natural one:

  • The table it depends on — feature_registry — already lives in runtime, and the mint trigger hangs off it. Putting the tags beside their trigger keeps the machinery in one schema.
  • A tag resolve is “turn this id back into a class, an id, and a scope” — which is exactly what the registry already does for the whole application. Roughly four-fifths of the resolution path was built before tags existed; the tag layer just adds “code → id” in front of it.

So tags are a small, dependent layer in a shared schema, not a subsystem with a schema of its own — a shape that matches what they are.

2.9 No foreign key, on purpose

∑ Model

feature_id points at a row that could be in any one of dozens of gis.<class> tables, and PostgreSQL has no way to declare a foreign key that spans many possible tables. So — exactly like feature_registry and the connectivity tables — the tag store keeps a polymorphic reference: a (class, id) pair with no database-level FK. Integrity is instead maintained by the trigger (it deletes tags when the registry row is purged) and by the resolver, which joins through the feature read — so a tag whose feature has vanished simply resolves to nothing rather than to a stale ghost. You never get a dangling code that opens an empty panel; you get a clean “not found.” The same holds for the admin console, which INNER JOINs the registry (Chapter 7).

2.10 What you can rely on

Pulling the ∑ threads together, here is the trust contract this chapter establishes — the things you can state as facts about your tag estate:

  1. Every feature has exactly one generated primary tag, created the moment the feature existed, by any creation path — and by backfill for everything that pre-dated the module. (Exception found in the code: the §2.6 collision hazard.)
  2. No code is ever ambiguous. Codes are globally unique across all features and statuses; a voided code is never reused.
  3. No feature can have two primaries — the partial unique index forbids it structurally.
  4. A single mis-read character in an odd body position, or any adjacent swap, cannot turn one minted code into another — the check character guarantees it by construction (the server does not additionally validate it on lookup).
  5. Retiring a record doesn't blind a field scan (soft delete keeps tags), but purging a record cleans up after itself (hard delete removes them).

With the machinery trusted, the rest of the guide is about using it. Next: Chapter 3 — Working with a feature's tags, where Dana opens the Tags tab and registers TX-Feeder7-014's legacy number, sets a primary, voids a mistake, and reissues a damaged label.

Chapter summary

  • VE- + Crockford base32 of a global counter + a position-weighted mod-32 check character; unpadded, so codes lengthen as the counter grows.
  • One table, one trigger on the registry (INSERT mints, DELETE cleans, UPDATE does nothing), one partial unique index.
  • The check character is a design property of minted codes; the resolver does an exact, case-sensitive lookup and does not verify it.

which runs Register. Walk the ∑ through it, because several safety rails fire here:

  1. Required fields. A blank class or id fails first: feature_class_code and feature_id are required.
  2.   4.     3.3 Setting the primary

    ▶ Operator

    A week later the new VE- label is fitted in the field and the old plate is painted over. Dana wants the system primary to match what's now physically on the tank, so she opens the tab, finds the VE-7Q3KA row, and clicks Set primary. That's POST /tags/VE-7Q3KA/primary → SetPrimary.

    Now VE-7Q3KA is primary and OLD-4471 is a plain active tag — still resolvable (a stray scan of the old plate still finds the transformer), just no longer the printed one.

    ∑ Model

    SetPrimary is careful in three ways:

    • It refuses a non-active tag. if t.Status != "active" → tag "…" is superseded; only an active tag can be the primary (the status word is the actual status). You print the primary; a voided or superseded code must never be the one printed, so it can't hold the flag. ⚠️ An unknown code is a 404: no tag "…".
    • It's idempotent. If the tag is already primary, it just re-reads and returns — clicking twice is harmless.
    • It flips atomically. clearPrimary on the feature, then is_primary = true on VE-7Q3KA, both inside db.RunInTx. Same one-transaction discipline as register.

    3.4 Voiding a wrong tag

    ▶ Operator

    Suppose Dana had fat-fingered the legacy code as OLD-4471X. It's wrong; she wants it gone. She clicks Void on that row → POST /tags/OLD-4471X/void → Void. (Void is idempotent: voiding an already-void tag just returns it.)

    ∑ Model

    Two rules define voiding:

    • You can't void the primary. if t.IsPrimary → tag "…" is the primary; set another tag as primary before voiding it. This is the guardrail that guarantees a feature is never left with no printable code. If the bad code were somehow the primary, Dana must promote a good one first. The app enforces it early with a clear message rather than letting the write reach the index. (The assistant tool's description says voiding the primary “leaves the feature with no primary” — that sentence is stale; the store refuses.)
    • A voided code is kept forever, never reused. The row stays; only status becomes void. So a stale scan of a label that was already voided resolves to a clean “retired”, not to some unrelated feature that might otherwise have inherited a recycled code. 💡 “Delete” is the wrong mental model for a tag — the physical label may still be stuck to plant somewhere, and the system's job is to keep telling the truth about it.

    3.5 Reissuing a damaged label

    ▶ Operator

    The most interesting verb. Months on, TX-Feeder7-014's VE-7Q3KA label has been scorched by a fault and the QR won't scan. The asset is fine; only the label is damaged. Dana clicks Reissue on the VE-7Q3KA row → POST /tags/VE-7Q3KA/reissue → Reissue (201 Created, the body is the new tag).

    ∑ Model

    Reissue is a supersede-and-mint in one transaction:

    1. It draws a fresh generated code straight from the same machinery the mint trigger uses: SELECT runtime.encode_asset_tag(nextval('runtime.asset_tag_seq')). The new code — here VE-9F2P5 — is therefore indistinguishable from a natively minted one; nothing downstream can tell it was made by reissue.
    2. It marks the old code superseded (not void) and clears its primary flag.
    3. It inserts the new code active, carrying the primary flag over if the old one held it. (Because step 2 already cleared the old primary, there's no moment where two rows are flagged — the unique index stays satisfied.)

    Why superseded rather than void? Because between the moment Dana reissues and the moment a crew actually fits the new label, the old scorched label is still on the tank. A scan of VE-7Q3KA in that window must still resolve to the transformer — superseded codes resolve; void codes don't (Chapter 5). So reissue keeps the old code alive-but-retired precisely long enough to bridge the re-labelling. Reissuing an already-superseded code is refused (tag "…" has already been reissued) so the chain doesn't fork.

    Reissue also works on a non-primary or external code: the replacement is always source = generated, and it is primary only if the old code was. (Reissuing a legacy number therefore gives you a new VE- code; the legacy plate's number becomes superseded and keeps resolving.)

    • It returns one row per feature (DISTINCT ON (feature_id)).

    • A feature with no active tag at all simply isn't in the result. So len(result) can be less than the number of features Tom selected.
    • Ids are trimmed and de-duplicated; a blank feature_class_code with ids is a 400 (feature_class_code is required with feature_ids). The client chunks large selections, 120 ids per request.

    4.4 Counting prints

    ∑ Model

    Two endpoints keep the print_count column honest:

    • POST /tags/{code}/printed (MarkPrinted) bumps one code — the single-label path from the Tags tab. An unknown code is a 404 no tag "…".
    • POST /tags/printed with { "codes": [...] } (MarkManyPrinted) bumps a whole sheet in one statement — the bulk path. It's tolerant: blanks and duplicates are dropped, unknown codes are skipped, and it reports how many rows it actually bumped ({"updated": n}).

    Both accept any status — a superseded code can legitimately be re-printed while a crew is mid-way through re-labelling (though the Tags tab itself only offers Print on active rows; the console offers it everywhere). And both are writes (tags:write), because they change a row.

    Here's the subtlety the chapter title promised: producing the label is a read, recording that you produced it is a write. The bulk primary lookup (GET /tags?...feature_ids=) is a GET — it sits on the read side of the mount's method-aware gate, needs only tags:read, and fits the id list in a query string (the client chunks very large selections). The count bump is the POST. So a user with read-only tag access can still print labels — they just don't move the print counter (the UI simply doesn't fire the POST for them). That's the right split: printing a sticker doesn't change the network, so gating it behind write permission would be needless friction; the book-keeping that does change a row is what's gated.

    Why is print a counter and not a boolean? Because a label is produced many times over an asset's life — reissued after damage, re-run after a smudged batch, re-fitted after a pole change. The count, paired with the console's “unprinted” KPI (Chapter 7, status = 'active' AND print_count = 0), lets a coordinator see at a glance which freshly-minted labels a crew still needs to physically produce.

    Scanning & resolving

    A phone camera turns a sticker back into the transformer — if you're allowed to see it.

    This is the moment the whole module exists for: someone standing at the asset points a camera at the sticker and the system says “this is TX-Feeder7-014, the 315 kVA transformer on Feeder 7, and here's everything about it.” Resolution is the read path — turning a code back into a feature — and it is where the tag layer meets the platform's access control. This chapter is a braid: ▶ the three ways a code gets scanned, ∑ the single Resolve function they all funnel through, and the access rules it enforces.

    5.1 Three ways in

    ▶ Operator

    A code reaches the resolver by three doors, all landing on the same logic:

    1. The QR deep-link. Priya, a field engineer at the pole, opens her phone camera — no app — and points it at the label's QR. It encodes <origin>/t/VE-9F2P5, so the phone offers to open that URL; the browser loads VoltEdge's /t/:code route, which resolves the code and jumps straight to the feature on the map. 🗺️ This is the everyday field path, and it needs nothing installed but a camera and a login. (The route is gated tags:read like the API; there is also a bare /t page with a manual-entry box, placeholder “e.g. VE-XXXXXXX”.)
    2. A scanner gun / manual entry. A warehouse reader or a person typing into the search box submits the raw code. Because a raw code can contain characters that are awkward in a URL path, there's a query form, GET /tags?code=<c>, beside the path form. (The web page itself always uses the query form.)
    3. The path resolve. GET /tags/{code} — the direct API call that integrations use.
    ∑ Model

    Doors 1–3 all call the same handler, and it calls one function: Resolve. Everything about which codes resolve and who may resolve them lives there, so there's exactly one place to reason about — no door has its own rules. Code-verified: the API does not parse URLs. Only the web route (/t/:code) and the Flutter extractTagCode (Chapter 6) peel the code out of a deep link; pasting the whole URL into ?code= is just an unknown code. Lookup is also case-sensitive and exact (after trimming surrounding whitespace): ve-7q3ka is not VE-7Q3KA.

    5.2 What a resolve returns

    ∑ Model

    A successful Resolve hands back a Resolution:

    type Resolution struct {
    Tag     *Tag             // the exact code that was scanned
    Feature map[string]any   // the full feature read-envelope
    Tags    []Tag            // every tag on that feature
}

    Three parts, each earning its place:

    • Tag is the scanned code specifically — so the field view can say “you scanned VE-7Q3KA” even if that's a superseded code.
    • Feature is the identical envelope a normal GET /features/{class}/{id} returns — same attributes, geometry, everything. A scan is just another way to open a feature; downstream code treats the result like any feature read.
    • Tags is the whole tag list for that feature (primary first, then newest; every status, including void), so the view can add “…the current primary is VE-9F2P5” — invaluable when Priya scanned a scorched old label and needs to know the live one.

    5.3 Which codes resolve, and which are refused

    ∑ Model

    Resolve runs a short, deliberate gauntlet. In order:

    1. Unknown code → not found. LookupByCode misses → no asset tag "…". (404.) A blank code can't match either.
    2. Voided code → refused, with a distinct message. A retired or wrong label answers asset tag "…" has been retired (still a 404-class refusal, but the wording tells an authenticated user why). ⚠️ This is the payoff of “never reuse a voided code” (Chapter 2/3): a stale label that was voided resolves to a clear “retired,” never to some unrelated asset.
    3. Superseded code → resolves. A superseded label (say VE-7Q3KA after reissue) does resolve to its feature — because that scorched label is still physically on the tank while the field is being re-labelled, and a scan of it must still find the transformer. The returned Tags list then shows the crew the live primary to fit.
    4. Class gone → not found. If the tag's feature class was uncompiled or removed, metadata.Load misses and it's treated as not-found, not a 500 — the asset it named is simply no longer resolvable.
    5. The feature read gate. The big one — §5.4. Includes the case where the feature row is gone (a purge) — also not-found.

    So the rule of thumb: active and superseded codes resolve; unknown and voided codes don't — and even a resolvable code is subject to the same access gate any feature read faces. A soft-deleted feature still resolves (the feature read has no soft-delete filter; the envelope carries deleted_at).

      6.1 The pack carries a tag index
      
  
      ▶ Operator

      ∑ Model

      ∑ Model

          8.2 What the filter compiles to
          
  
          ∑ Model
    
          The control posts a tag predicate on the normal query body (POST /{feature_class}/query, field "tag"), and buildTagFilter turns it into a correlated EXISTS subquery against runtime.asset_tags:
          

          EXISTS (
  SELECT 1 FROM runtime.asset_tags _at
  WHERE _at.feature_class_code = ?          -- this class
    AND _at.feature_id = <table>.id         -- correlated to the outer feature row
    AND _at.status <> 'void'                -- retired codes never match
    [ AND _at.source = ? ]                  -- optional
    [ AND _at.tag_code = ?  |  _at.tag_code ILIKE ? ]   -- optional: exact | prefix (code || '%')
)
          
    
          Several deliberate details:
          
    
            
      
          • Void tags never match. status <> 'void' mirrors the resolver exactly (Chapter 5): a code that wouldn't resolve can't satisfy a search either. Active and superseded both count.
            • 
      
          • Present = false flips it to NOT EXISTS. That's the “find features with no such tag” case. 💡 Ask for features with no tag at all and — because every feature is auto-tagged at birth (Chapter 2) — you should get essentially nothing. That query is a genuinely useful integrity probe: a non-empty result means something slipped past the mint trigger (the §2.6 collision is the known way). An empty result is the system telling you the invariant holds. Code-verified nuance: because void tags never match, a feature whose tags are all void also shows up in this probe (the same state that makes the bulk printer skip it) — so a hit means “no live tag”, with a mint failure as one of two causes.
            • 
      
          • Everything is a bind parameter. The only things spliced into the SQL text are the fixed EXISTS/NOT EXISTS and operator tokens and the compiler-stamped physical table name — nothing a client can steer. Prefix match uses ILIKE (case-insensitive), same convention as the engine's starts_with; code-verified: the code is not LIKE-escaped here (unlike the console search), so % and _ typed into a prefix act as wildcards. Exact match is a plain =, hence case-sensitive.
            • 
      
          • Validation. A bad source is tag source must be "generated" or "external", got "…"; a bad match mode is tag match must be "exact" or "prefix", got "…" (both 400). Blank code means "any tag"; present defaults to true when omitted.
            • 
      
          • It's a normal query. The tag filter shares queryFeatures, so it inherits the same read scoping, private-draft visibility, and soft-delete exclusion as every other query. A tag search can't surface a feature a plain query couldn't — the Chapter 5/7 scope story, one more time. (Unlike resolve and the console, soft-deleted features are excluded here.)
            • 
    
          
    
          After the rows come back, enrichPrimaryTags does one batched lookup to stamp each with its active primary code (rows with no active primary tag simply lack the key). It's written inline in crud rather than calling the assettag package, because assettag imports crud — calling back would be an import cycle. A small, honest concession to Go's package graph.

          9.1 The code at a glance
          

             VE-7Q3KA
   ─┬ ──┬─ ┬
    │   │  └── check character  — position-weighted sum of the body, mod 32, same alphabet
    │   └───── body             — a value from runtime.asset_tag_seq, Crockford base32 (unpadded)
    └───────── prefix           — "VoltEdge-minted"
          
  
            
    
          • Alphabet (Crockford base32): 0123456789ABCDEFGHJKMNPQRSTVWXYZ — no I, L, O, or U, so the common misreads can't occur and generated codes stay clean.
            • 
    
          • Check character: sum of (digit value × 1-based position) mod 32. Always catches a one-character slip at an odd position and any adjacent swap; at even positions a slip with d·i ≡ 0 (mod 32) escapes. Kept inside the 32-letter set so the whole code is URL- and label-safe with no escaping. Not verified by the server on lookup.
            • 
    
          • Functions (all IMMUTABLE): runtime.encode_base32_crockford(bigint), runtime.asset_tag_check_char(text), runtime.encode_asset_tag(bigint) (adds the VE- prefix). A registered legacy code (OLD-4471) follows none of this — it's stored verbatim, case preserved, up to 64 bytes.

          9.3 The lifecycle state machine
          
  
          The clickable diagram in Chapter 1 (Interactive 1) is the live version of this. In words:
          
  
          
    
          fromactiontoconditions
          
    
          (none)mint (registry trigger) / backfillactive, primary, generatedfeature enters the registry; never over the API
          
    
          (none)registeractive, externalprimary only if make_primary
          
    
          activeset primary / printactiveset primary demotes the previous primary, atomically
          
    
          activevoidvoidonly if not primary
          
    
          activereissuesuperseded (+ a fresh active code)primary flag moves to the new code
          
    
          voidreissue quirksuperseded (+ a fresh non-primary code)accepted by the server; the console offers it
          
    
          supersededanything but print—reissue refused; set primary refused; terminal, kept and still resolving
          
  
          
  
            
    
          • Mint happens only from the feature_registry trigger (on feature insert) or the backfill — never over the API.
            • 
    
          • Reissue supersedes the old code and mints a fresh active one, carrying primary over.
            • 
    
          • Void and superseded are terminal; codes are never deleted (except when the feature is hard-purged) and never reused. At most one tag per feature is primary (asset_tags_one_primary); you cannot void the primary — promote another first.

          symptomcause & fix
          
    
          “Asset tag has been retired” on scanthe code is void — the label was retired. Scan the current label, or find the feature another way and check its Tags tab for the live primary. (The web /t page folds this into its generic “Tag not found” text.)
          
    
          “No asset tag …” on a code you know existseither the code is genuinely unknown (typo, wrong case, a whole URL passed to the API), or the feature is outside your territory / a private draft you can't see / has your own staged delete — the two are deliberately indistinguishable (§5.4). If you should have access, check your territory grants.
          
    
          Can't void a tag — button missing or refusedit's the primary (…is the primary; set another tag as primary before voiding it). Set another active tag as primary first, then void it (§3.4).
          
    
          Can't set a tag as primaryit isn't active — …is superseded; only an active tag can be the primary. Reissue or register a live code instead.
          
    
          A feature shows two codes but only one printsworking as intended — a feature has many codes but exactly one primary, and only the primary prints. Promote the one you want on the Tags tab.
          
    
          Registered a legacy number and it was refusedthe code is already in use somewhere (tag_code "…" is already in use — case-sensitive, any status), the feature was hard-purged or the id/class is wrong (no feature … in class …), or the text is empty / over 64 bytes / has a control character. Check for an existing tag with that code.
          
    
          Bulk print skipped some featuresthose features had no active tag (e.g. all voided). The print sheet's note line (“N selected features had no tag and were skipped.”) reports the count; check those features individually.
          
    
          Offline scan finds nothing but online worksyour field pack predates v10 or was built without tags:read, so it has no tag index — or the feature isn't in the pack, or the code was created after the pack was cut. The app falls back online automatically. Rebuild the pack as a tags:read user to resolve offline.
          
    
          “Could not resolve … (are you online?)”offline and the pack has no row: a void, unknown or unpacked code can't be told apart without a signal. Get a bar of coverage for the definitive answer.
          
    
          A query for “features with no tag” returns rowsshouldn't happen — every feature is auto-tagged (Chapter 2). Treat a non-empty result as an integrity signal: the known cause is an external code registered equal to a not-yet-minted VE- code, which makes the trigger skip that feature (§2.6).

          The scanner closed on a random barcodeextractTagCode only ignores empty values; any other string is treated as a tag code (§6.2).
          
    
          Print count didn't moveyou hold only tags:read (the count bump is a write), or the print dialog was cancelled — the count means “sent to print” (§4.2/4.4).
          
    
          A lower-case code doesn't scanlookup is case-sensitive and generated codes are upper-case. Check for auto-correct; the field app's manual box capitalises for you.

          Recipes — the one-page cheat sheet
          
  
          
    
          Add a legacy number
          1. Open the feature → Tags tab (🔒 write).
          2. Legacy code, type the number exactly as painted (case counts).
          3. Tick primary only if you will print this number.
          4. Register. Refused? Read the red toast (§3.2).
          
    
          Replace a damaged label
          1. Tags tab → Reissue on the damaged code.
          2. The new code is primary; the old stays superseded and keeps resolving.
          3. Print the new row, fit it.
          4. Scans of the old sticker still work until it is gone.
          
    
          Retire a wrong code
          1. If it is the primary, Set primary on a good code first (or reissue it).
          2. Void the wrong one.
          3. It now answers “retired” forever and is never reused.
          
    
          Print a whole class
          1. Features browser → pick the class.
          2. Select all → Print tags (N).
          3. Check the note line for skipped features.
          4. Printer on actual size; (writers) counters bump on Print.
          
    
          Find plant missing a legacy number
          1. Feature query → class → arm Asset tag.
          2. Has no matching tag, source external.
          3. Run; read the Tag column to see what a scan hits.
          
    
          Check estate integrity
          1. Query: has no matching tag, no code, no source.
          2. Expect zero rows.
          3. Any row: look for an external code equal to a VE- code (§2.6).
          
    
          Scan with no signal
          1. Build the pack as a tags:read user (v10+).
          2. Pack map → scan (QR, barcode or manual).
          3. Offline hit: instant. Miss: needs signal for the verdict.
          
    
          Work the unprinted queue
          1. Console → watch Unprinted.
          2. Filter active + class, select the page.
          3. Print selected until the chip is zero.
