Feeders, Sections
& Subnetworks

How VoltEdge divides the network into named, meaningful pieces — feeders, protection zones and switching sections — with one small schematic you can operate: trip a recloser, open a switch, close the tie, change a class's role, and watch every section re-draw itself.

▶ How to use it ∑ Why / the model

The cast: Dana (editor) curates feeders · Tom (analyst) reads sections off traces and load flows · Priya (dispatcher) scopes isolations during outages · Ada (admin) classifies the boundary devices. 🔒 marks a step that needs a permission.

01

The one idea

A subnetwork is a named section of the network, defined by where it starts.

A section is the span between boundary devices — and the kind of device decides the kind of section.

There is no separate “subnetwork” object to create and keep in sync. A section falls out of two things VoltEdge already has: the network’s topology and one attribute on each device class (boundary_role). Everything in this guide is a consequence of that.

02

The three kinds of section

∑ The grounded model — nested, and LV mirrors MV.

A distribution feeder isn’t one undifferentiated blob. It’s carved up by its own devices, and the kind of section depends on the kind of device:

1 · feeder

Everything load-side of a station breaker

The top-level subnetwork — off the station bus. The feeder head is a placement fact (this breaker, on this bus), so it’s modelled as a circuit’s source, not a class property.

2 · protection zone

What de-energises when this device trips

Bounded by the next downstream protective device (breaker, recloser, fuse). Answers “what goes dark on a fault?”

3 · switching section

What I can isolate to work on it

Bounded by the next switch in any state (disconnector, load-break switch, tie). Answers “what can I take out for work?”

They nest

Feeder ⊃ protection zones ⊃ switching sections. Every protective device is also a switching boundary (it can be opened), so the finer carve strictly subdivides the coarser one. In Interactive 1 you saw this as → → pieces (the ‘feeder’ count is the number of source breakers; the finer carves add a section for every extra boundary device). The widget below makes the nesting explicit: pick a device and read off the section it heads under each view.

LV mirrors MV exactly

The elegant part of the model is that the same grammar repeats at low voltage. The distribution transformer is the LV network’s “station breaker”; the pillar fuses are its downstream protective devices; the link box is its switch.

03

The backbone: boundary_role

🔒 One class-level attribute classifies what each device does to the network.

The whole model rests on one attribute, boundary_role (migration 0129). It has four values, and “unset” is a meaningful fifth:

ValueWhat it meansCarves
sourceoriginates a (sub)network at its load side — a generator, a grid infeeda new network
protectiveinterrupts fault currenta protection zone
switchingisolates or transfers without being primarily protectivea switching section
transformera voltage boundary — originates the next-voltage network at its secondarythe next voltage’s network
(unset)not a boundary: conductors, busbars, meters, poles, service points…—
Tip
This is the one piece of structure worth adding, and it’s electrically honest: it’s finer than lumping every switch together, because a fault-interrupting recloser and a manual isolator create different kinds of section.
Caution — the feeder head is per-instance
Whether a given breaker is the station feeder breaker is a placement fact, not a property of the breaker class — a mid-feeder breaker is still a protective boundary. VoltEdge models the feeder head as a circuit’s source (Chapter 4), not via boundary_role.

Be Ada for a minute

🔒 Ada sets boundary_role per class on the admin feature-class screens (it’s metadata, like functional_role). Most deployments inherit the seeded defaults and never touch it. Below, you can re-classify the device classes yourself and see what it does to the carve — this is a sandbox; nothing is saved.

▶ Things to try
  • Set MV_RECLOSER to switching. The protection-zone count drops by one — the recloser no longer clears faults as far as the model knows, so its zone merges upstream. Setting a class wrong makes sections wrong; that is why this is an admin screen.
  • Set MV_ISOLATOR to (unset). The tap it guards stops being a separate switching section.
  • Set DIST_XFMR to (unset): the LV network is no longer its own section — it merges into the MV section above it.
∑ Two seeded edge cases

MV_EARTH_SWITCH is deliberately not a boundary — it grounds for safety, it doesn’t section the network. And MV_SECTIONALIZER is not in the seeded backfill (seed/boundary_role_backfill.sql) even though a sectionaliser is conceptually a switching device — if your network uses them as section boundaries, set the role on that class yourself.

04

Feeders are circuits

▶ 🔒 You don’t build a separate “feeder” thing — it’s the circuit VoltEdge already has (migration 0062).

▶ Create and populate one — 🔒 circuits:write + features:write
  1. Admin → Circuits → create a circuit: name, MV/LV network, optional voltage.
  2. Set its source feature — the station circuit breaker (or the transformer secondary for an LV feeder). That’s the feeder head / subnetwork controller.
  3. Assign by trace — VoltEdge traces downstream from the source and stamps the circuit onto every feature it reaches (the circuit_ref label). Every conductor, switch and device on the feeder now knows which feeder it belongs to — on the map and in every feature’s panel.

Freshness — the one bit of “is it stale?”

After you assign, the network keeps changing. VoltEdge flags when a circuit’s stamped membership may be out of date: the Circuits list shows a stale — re-assign badge when a member feature has been edited since the last assign (migration 0130, one timestamp: members_synced_at).

Run the whole lifecycle yourself below. Note carefully what the badge does and doesn’t catch — that’s the caution in the manual, made visible.

Interactive · 4

Caution — what the stale check can’t see
It catches member edits, moves and deletes. It does not catch a pure connect/disconnect that touches no existing member — for example closing a tie that pulls brand-new features onto the feeder. (Try it: assign Feeder 7, then Close the tie after opening SW-101. The badge stays green, yet the live trace now reaches Feeder 8’s features.) Re-assigning is always safe, so when in doubt, re-assign.
∑ Why feeders are stamped but sections aren’t

A feeder’s membership is stored (circuit_ref on each feature) because it’s a human-meaningful, named, durable label — you want it in exports, on the map, in reports. A section is a read-time concept (next chapter), so it has no stored id and nothing to go stale.

05

A feature’s section, in results

▶ You never label sections by hand — VoltEdge derives them from the result you’re already looking at.

Run any trace, or a load flow, and each row knows its section:

  • In a trace result, each feature carries a small § section tag — its nearest upstream boundary device (the section head). You read “MV-4 · § past F-301” at a glance.
  • In a load flow, the results table gains a Section column showing the same section head per node.
∑ How it’s derived (and why it’s free)

Every trace and load-flow result already carries a parent tree — each feature’s one-hop-upstream neighbour. To find a feature’s section, VoltEdge climbs that tree to the nearest device whose class has a boundary_role. No extra queries, nothing stored on the feature, and always correct for the current switching state. A boundary device heads its own section.

Operate it: click a start point on the schematic to trace downstream from there, then click a row in the results table to watch the climb. Open a switch and re-trace — the parent tree (and so the sections) changes with the switching state.

Tip — why no “re-assign” for sections
Because a section is derived, there’s no membership to go stale — unlike feeders, which are stamped. Sections are a read-time concept; feeders are a stored one. Operate a switch in the widget above and the section heads change instantly; that’s exactly what happens against live data.
06

Highlighting a section on the map

▶ Select a feature → actions menu (⌄) → one of two choices.

To see a section, select a feature and open its actions menu (the ⌄ in the panel header). There are two choices because the two kinds answer different questions:

Switching section

Bounded by any isolating device (protective + switching) and the transformer. “What would I isolate to work on this?”

Protection zone

Bounded only by fault-interrupting protective devices (and the transformer). “What de-energises if a fault here trips the upstream device?” It stops at fewer devices — a plain switch doesn’t bound a protection zone.

Either one highlights the section on the map, with its upstream and downstream bounding devices marked. Priya uses Switching section to scope a planned outage (“who’s between these two switches”); Tom uses Protection zone when reasoning about coordination.

How this compares to a full utility-network model
VoltEdge intentionally does not clone the heavyweight apparatus.


  
Tiers, terminal-precise controllers, per-tier subnetwork-name fields, a derived subnetwork-line, a clean/dirty/invalid state machine, network-wide name-uniqueness — none of that is here. What’s deliberately out of scope

  

    
No section-coloured map tiles
Sections appear on demand (a highlight) and in results — not as a persistent per-feature colour. Addable later if a section-coloured overview is ever needed. (The colour-by-section views in this guide are teaching aids, not a map feature.)

    
No multi-tier labels on one feature
A feature carries one feeder (circuit_ref), not simultaneously a feeder and an LV-network name.

    
No tiers table, subnetwork-line, terminal controllers or validity state machine
One class attribute, one timestamp, and the trace/circuit machinery that already existed.

  


  
The payoff: feeders, protection zones and switching sections are all usable today — with one new attribute, one timestamp, and machinery that already existed.
