VoltEdge guide · users, roles, permissions & access control · for administrators and auditors

Who may do what,
and where.

Three independent decisions guard every request: who you are, which verbs you hold, and which places they apply to. This edition runs the real rules in your browser — the nine seeded roles, all 34 permissions and the route gates were rebuilt from the migrations and main.go, so what you see here is what the server decides.

Use As in the top bar to act as a real role. Ada (admin) can run the user console; Owen is the break-glass account; Dana edits data; Priya only reads; Sam is a supervisor (and shows a drift worth knowing). Widgets that need a permission you lack are marked 🔒 and tell you whom to switch to. Every action that the real server would audit is written to one shared log — open chapter 13 to query it.

Who this is for

Administrators who create accounts, assign roles, scope crews and run the emergency procedures; auditors who must answer “who could do this, how do we know, and where is the evidence?”; and developers adding a permission or a route. The full manual (access-control-guide.md) holds every table, SQL query and appendix; this edition keeps all seventeen chapters and makes the rules something you can poke.

Honest limits up front: roles are data, not code — there is no role editor in the product (roles change through SQL migrations); the API server does not accept bearer tokens (only the MCP, field-sync and webhook services do); and several things you might assume are audited, are not (chapter 13). Findings that contradict older documents are collected in the manual’s Corrections appendix.

01

The access model on one page

Authentication, RBAC, spatial scope — evaluated by different code, in a fixed order.

Every request is judged three times. Who are you? is answered by a session cookie (or, outside the API server, a bearer token). What verbs may you perform? is a set of resource:action permission strings — the union of the permissions of the roles you hold, recomputed on every request. Where may you perform them? is a set of territory ids resolved from your grants and your management chain. An action succeeds only when all three say yes. A fourth gate, private drafts, hides never-published features from everyone but their author chain.

QuestionMechanismStored inEnforced by

Where?territory grants + territory tree + manager treeuser_territories, users.manager_id, gis.territoriespredicates in crud, tiles, export, trace, analysis, import, packs
A user has no permissions of their own. There is no per-user grant, no deny, and no exception list. Roles are additive, authorization never learns how you signed in, and the only API for roles is a read-only list.

02

Users

Accounts hold state, not power. Creation, change, ending — and the guards.

A user row carries state: email (login name and SSO match key, immutable through the API), display name, status, the break_glass flag, lockout counters and the manager_id edge. Power comes only from the roles they hold. There are three creation paths: the admin API (admin:users + CSRF, audited), the authadmin CLI (bootstrap, defaults to break-glass + admin role, not audited in auth_events), and SSO — which never creates an account.

3.5 Choosing a role

  
Ask “what is the most limited role that still lets this person do their job?” Priya dispatches: viewer. Tom plans: analyst. Dana maintains data: editor. A surveyor on a tablet: field-surveyor; an enumerator creating assets: field-enumerator; a technician closing work orders: field-technician. Reserve admin for people who author metadata and manage accounts — it is the one role with no ceiling, and it ignores territory scoping. Roles are additive: to remove a capability you must remove every role that grants it (the diagnoser in chapter 14 finds the contributing role).

06
Authentication: sessions, cookies & CSRF
Opaque, server-side, revocable — two clocks and a partial CSRF net.

  
A login mints 256 random bits as the cookie value and stores only its SHA-256, plus a per-session CSRF token and two clocks: a sliding idle window (SESSION_IDLE_TIMEOUT, default 12 h) and a hard absolute cap (SESSION_ABSOLUTE_MAX, default 720 h). Validity: the row exists, is not revoked, is inside both windows, and the user is active. Any failure is an anonymous request, never an error.

6.2 Where CSRF is — and is not — enforced

  
Try it in the request tester above (choose a route with CSRF, then “token missing” or “cross-site”). RequireCSRF checks, on non-safe methods for an authenticated request: Sec-Fetch-Site (when present) is same-origin or none, and X-CSRF-Token equals the session’s token (constant time). The Origin header is not inspected. It is applied to a specific set of surfaces; the core data mounts rely on SameSite=Strict alone.

  
SecurityHeaders sets nosniff, X-Frame-Options DENY, Referrer-Policy no-referrer and COOP same-origin on every response, and HSTS only over TLS. The API sets no Content-Security-Policy; set one at the reverse proxy if you need it.







  
07
Passwords, lockout & rate limits
Argon2id, a fixed 5-strike lock, and a per-process token bucket.

  
Passwords are Argon2id (m = 19456 KiB, t = 2, p = 1, 16-byte salt, 32-byte key, PHC-encoded) with a 12-character minimum and no complexity or rotation rule. Unknown email, disabled account, no local identity, locked account and “local login off” all spend an Argon2 verification against a dummy hash before failing, so timing does not reveal which applied.

  
    
    
  1. Require email and password (400). Look up an active user — missing or disabled gives a generic 401.
    2. 
    
  2. locked_until in the future → the same generic 401 (a locked account does not say it is locked).
    3. 
    
  3. Find the local identity; none or no hash → generic 401.
    4. 
    
  4. The switch: allowed = break_glass || local_auth_enabled. Not allowed → 403 “local password sign-in is currently disabled” — checked before the password, so it is never a password oracle.
    5. 
    
  5. Verify. Wrong → count the failure; the 5th locks the account for 15 minutes and resets the counter. Right → clear counter and lock, mint the session.

08
Single sign-on & provisioning
SSO authenticates; it never authorises and never creates.

  
Two providers can be configured by environment — Azure AD (azuread, single tenant) and Google — each optional and independent. A provider that is unconfigured, or whose discovery fails at API start, does not exist (no button). SSO authenticates the person. There is no claim-to-role mapping, no group sync and no SCIM: roles, territories and manager are always assigned inside VoltEdge. And SSO never creates an account.

  
    
    
  1. GET /auth/oidc/{provider}/login makes state, nonce and a PKCE verifier, stores them in the 10-minute ve_oidc_flow cookie (base64 JSON, httpOnly, SameSite=Lax) and redirects.
    2. 
    
  2. The callback clears that cookie; refuses a provider error; compares state (constant time); exchanges the code with the verifier; requires an id_token; verifies signature, issuer and audience; compares the nonce.
    3. 
    
  3. Provider trust rules. Google needs email_verified and — if OIDC_GOOGLE_ALLOWED_DOMAIN is set — the hd claim or the email’s domain must match. Azure adds nothing: the tenant-scoped issuer already bounds who can mint a token (no separate tid check).
    4. 
    
  4. Match or reject: a linked (provider, subject) signs in (unless disabled); else the lower-cased email claim (Azure: preferred_username if it has @) must match an active pre-provisioned user, and the identity is linked on this first login.

09
API tokens, field logins & service identities
Every non-browser caller still becomes a real user with that user’s scope.

  
A bearer token is ve_mcp_ + 43 URL-safe characters (256 bits), stored as SHA-256 with a 12-character display prefix; shown once at mint. It may carry an expires_at (default: never) and is revoked by setting revoked_at (immediate). Validity: hash found, not revoked, not expired, user active. It resolves through the same permission and scope loaders as a cookie session, so it can never do more than its owner.

  
The main API server does not read Authorization: Bearer. Its SessionLoader looks only at the cookie. Tokens are accepted by the MCP server, the field-sync service and the webhook receiver. An agent holding Tom’s token cannot call POST /analysis/load-flow on the API directly — it asks the MCP server, whose tool is gated on analysis:run.

9.1 Webhook ingestion credentials

  
Each inbound endpoint has an auth_mode. hmac: X-VoltEdge-Signature = hex(HMAC-SHA256(secret, timestamp + "." + body)) with X-VoltEdge-Timestamp inside a 5-minute replay window (all failures one vague 401). bearer: a token whose owner is exactly the endpoint’s service user. both: a signature header selects HMAC, otherwise bearer. Every applied write runs as the service user, inheriting that user’s permissions and territory scope; the WAM and faults adapters check wam:write/faults:write explicitly. Give a service user the narrowest role its feed needs.

  
Background jobs build the same snapshot from a user id (LoadSessionUser); import and export jobs capture the requester’s scope at enqueue and the worker applies exactly that — a job queued before a revocation still runs with the permissions the requester had when they pressed the button.

11
Spatial access control (territories)
Two trees meet at the user; empty means nothing, never everything.

  
RBAC answers which verbs; spatial access answers which places. A grant names one territory node and includes its whole subtree at resolve time (the tree cascades down); a manager inherits the union of every grant held by all their transitive reports (the org tree cascades up). The seeded levels are utility (0), region (1), district (2, the minimum feature level), area (3), plot (4); the seeded boundaries are illustrative rectangles in central London.

  
11.1 Resolve a user’s effective set

  
The same three recursive steps as access.EffectiveIDs: reports → granted → scope. Edit the grants and the manager chain in chapter 2’s console (or here) and watch the set change.

Resolution runs per request (a 60-second per-process cache, flushed by every grant, revoke or manager change via InvalidateAll()); holders of territories:unscoped skip it. With several API replicas, another replica can serve a stale set for up to 60 seconds.

  
11.2 How a feature acquires a territory

  
territory.Assign runs on every geometric create and every geometry-changing update. Automatic: the deepest territory whose boundary contains the feature’s centroid (a line straddling a boundary resolves to exactly one). A match at or above the minimum level is stored even with enforcement off. Override: a supplied territory_id must exist and be at least the minimum level — always — but need not contain the feature. Failure: no covering territory (or only a too-shallow one) is a 400 with enforcement on, and a saved feature with territory_id = NULL with it off.

11.4 Rolling it out

  
  1. Author the tree and boundaries (territories:write).
  2. Backfill existing features (POST /territories/backfill); re-runnable.
  3. Review coverage (GET /territories/coverage): unassigned features become invisible once scoping is on.
  4. Grant crews (admin:users) and set managers.
  5. Flip PUT /territories/enforcement (territories:write) — it does not check coverage and is not audited in auth_events.
  6. Verify as a scoped user: out-of-territory GET → 404, write outside → 403, tile outside → empty.

Related but distinct · per-territory feature-class availability
  
Everything above scopes who may work where. A separate, class-level axis decides which feature classes exist where. An admin can take a feature class out of use without deleting its data:

  
    
    
  • Global off — feature_classes.status → deprecated (the Deactivate action, POST /admin/feature-classes/{code}/deactivate). The class drops out of the map, the New-Feature menu, the Features browser and every form; its table and rows are kept; Reactivate restores it. Enforced at write time (it accepts no new features), not just hidden.
    • 
    
  • Per-territory off — a metadata.feature_class_territory_disabled row turns a still-active class off for one territory and, by cascade, every territory beneath it. On create, the feature’s territory (resolved by the same point-in-polygon as above) is checked and a feature in a disabled territory is refused. Existing features are grandfathered; global off always wins.
    • 
  

  
This is authored on the class (Admin → Feature classes → Territory availability), and composes with — but is independent of — the user-level territory scope this chapter describes.







  
12
Private drafts & the pending-edit overlay
Never-published means private to the author chain; edits of published features can be staged.

  
A feature is a draft until published; published_at is a sticky marker. When private_drafts_enabled is on (no migration seeds it; missing means off), a feature is visible if it is public (status='published' OR published_at IS NOT NULL) or its created_by is the viewer or one of the viewer’s subordinates. The predicate is ANDed with the territory predicate and skipped for territories:unscoped, break_glass and session-less callers. Your manager can publish your orphaned draft — that is the recovery path (publishing still needs the required fields complete). Unpublishing does not make a feature private again.

  
Phase B. A user who is not unscoped and not break-glass has an edit of a published feature staged in runtime.feature_pending_edits: the public row is untouched; only the author’s own reads (get/list/query/tiles) are overlaid; the overlay is display-only; apply (apply-pending) is conflict-checked against base_version; discard with DELETE …/pending.

13
The audit trail
One append-only table, best-effort writes, no reader in the product.

  
iam.auth_events is append-only: the application only ever inserts. user_id is nullable with ON DELETE SET NULL so an event outlives its account. Columns: id, user_id, event_type, detail, ip, user_agent, created_at. Writing is best-effort: an audit insert failure never changes the outcome of the audited action. There is no API or UI to read it — review is an out-of-band SQL query. The ip column stores the first X-Forwarded-For value when present, so treat it as advisory unless your proxy overwrites client-supplied values.

    16.1 Known limits and findings
    
  
      
    
    • supervisor’s description does not match its grants (chapter 3).
    • is_system is not enforced; any role can be edited or deleted by SQL.
    • Read-only POSTs on method-aware mounts need the write permission (chapter 5).
    • CSRF middleware covers a subset of mutating routes (chapter 6).
    • Lockout is fixed and per account; the limiter is per process and keyed by peer address.
    • The audit IP trusts the first X-Forwarded-For value; admin password changes and both rollout flips are not audited; role_changed is overloaded.
    • Territory caches are per process (≤ 60 s stale on other replicas); GET /territories is not scoped.
    • The API server accepts no bearer tokens; the seeded boundaries are placeholders; private_drafts_enabled has no seeded row.
    
  
    Not verified at runtime: the 403 for a pure viewer on POST /features/{code}/query, quoted status codes for each branch, limiter timing, SSO against live tenants (code read only), and PostGIS-dependent territory queries (read from source; the scratch database stubbed PostGIS).
