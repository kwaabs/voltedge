VoltEdge guide · integrations · join a feature to SCADA, AMI, CIS & more

One asset.
Every system.

The same transformer is a tag in SCADA; the same service point is a meter in AMI and an account in CIS. This edition is a working one: register a system, tag a feature, build a live-fetch URL from a template, transform a foreign payload with a mapping spec, sign a webhook with real HMAC, and watch an inbound push adopt the right feature instead of duplicating it.

Use As in the top bar. Ada holds metadata:write — she registers systems & webhooks. Tom holds features:write — he links and tags features. Dana holds only features:read — she can look, not change. Actions lock to what the persona may do.

The one idea

Integration is about keeping identities joined up without copying everything into one database. VoltEdge stays the system of record for the network; each feature just carries a small note of what it's called elsewhere — the external reference — and that one note drives both looking out (fetch live data) and taking things in (a webhook push finds the right feature).

The four building blocks

Set them up in this order; two directions run through all of them.

In plain terms

First register a system (once). Then, per feature, add links (pointers out), record references (its id elsewhere), and configure webhooks (so another system can push changes in). References are the hinge: set a feature's id once and it works both ways.

Ada's job

The template turns an id into a request path — then the proxy fetches it.

In plain terms

The system's path template has {placeholders}. {id}/{ref} come from a scalar reference; named fields come from an object reference. VoltEdge fills them, checks the result is still a relative path (so a bad id can't point at another host), and fetches through the proxy.

{ "op": "upsert", // or "delete" "external_id": "8842", // correlation key (required) "feature_class": "SERVICE_POINT", "attributes": { "tariff": "D1" } }

tip The endpoint's Deliveries log (newest 100) shows every attempt's status; Test pastes-and-applies a payload inline to validate auth + mapping before go-live; Replay re-enqueues a stored delivery. The receiver never stores the Authorization header or the raw signature — only non-secret metadata.
6¾

Feed the protection register

Push a device's as-built relay / overcurrent settings in from a relay DB or SCADA — correlated, provenance-stamped.

In plain terms

VoltEdge keeps an as-built protection-settings register — one row per protective device holding its relay / overcurrent settings (pickups, time dials, CT ratio, curves, reclose scheme). Those settings usually live in a relay-setting database or SCADA; the protection target lets that system push them in instead of an engineer re-typing them. It's the protection sibling of operation: both resolve a device and write under features:write as the endpoint's service user — but a setting is an upsertable entity keyed on the device, so a repeat replaces it and op:"delete" removes it.

Naming the device

A change names the device directly (device_class + device_id, VoltEdge's own ids) or by its external id (device_external_id) — resolved through the external_ref reverse index using the endpoint's System code, exactly the correlation operation uses. external_id is only a label here (the device is the key); there's no event-dedup.

caution The resolved device must be a protective / switching class — MV_BREAKER, MV_RECLOSER, MV_FUSE, MV_SWITCH, MV_ISOLATOR, MV_SECTIONALIZER, LV_SWITCH or PROTECTIVE_RELAY. A device_external_id that resolves to a transformer or a line is rejected, so a mis-stamped reference can't quietly write settings onto a cable.

The change shape

{ "op": "upsert", // or "delete" "device_external_id": "FDR7-CB7-RELAY", "relay_model": "SEL-751", "ct_ratio": "400/5", "phase_pickup_a": 400, "phase_time_dial": 0.5, "phase_curve": "IEC_SI", "phase_instantaneous_a": 15000, "ground_pickup_a": 40, "reclose_operations": 4, "reclose_intervals": "0, 2, 5 s" }

Batch under {"changes":[ … ]}. Any omitted setting is written null (an upsert is a full replace). Fields: relay_model, ct_ratio, phase_* / ground_* (pickup_a, time_dial, curve, instantaneous_a), reclose_operations, reclose_intervals, notes.

Provenance

Every register row records the source of its last write. An ingested write stamps source = the endpoint's System code (falling back to the endpoint id); a register-UI edit stamps source = "manual". Because an upsert is last-writer-wins, source reflects who touched it last — correct an ingested setting by hand and it flips back to manual. The register screen badges any non-manual source, so a feed-driven row is visible at a glance.

tip On Admin → Webhooks → New, pick Target: Protection settings, a service user with features:write, and — if changes name devices by device_external_id — the External system code (the optional input now shown for the device-resolving targets operation, outage and protection). A system that already holds VoltEdge's own ids can skip the webhook and write the register directly: PUT /protection/settings/{class}/{id} (features:write). See the Switching & Protection guide for the register itself.
6⅘

Operations, outages & alarms from the field

Three targets turn a SCADA / AMI / CIS signal into an operational record — so the control room sees reality from telemetry, not a phone call.

In plain terms

These three share the device/service-point correlation of chapter 8: a thing is named by VoltEdge's own ids or by an external id resolved through external_ref + the endpoint's System code. All take op:"upsert" only (a field signal is never webhook-deleted) — except alarm, which adds op:"clear" for return-to-normal.

operation — the device-operation log (and an alarm)

A device operated: a trip, lockout, reclose, open, close, earth. Recorded as one row in the append-only operation log (the history behind MAIFI and the operations board) through the same path a crew log takes. external_id is the event's dedup key — a re-delivered SCADA batch records nothing the second time.

Also raises an alarm

An alarm-worthy op feeds the annunciator for every source, in the op's own transaction: lockout (high), earth (safety), alarm (medium) or trip (low) raises an operator alarm that stays until acknowledged. Routine reclose/open/close raise nothing.

{ "op": "upsert", "external_id": "SIG-88123", // event dedup key "op_type": "lockout", "source": "scada", "device_external_id": "FDR7-REC-03", "occurred_at": "2026-11-06T14:03:00Z", "cause": "overcurrent" }

outage — a customer outage from the field

The OMS counterpart to call-driven prediction. One target, three kinds:

kindDoesResult
device_tripRaises (or returns the open) incident blamed on the device, created confirmed with its downstream cone frozen as interruptions (the SAIDI clock starts). Idempotent per open-incident-per-device.an incident
last_gaspA meter's dying power-down frame → a machine trouble call (caller_ref = AMI:last-gasp) for the dark service point. Deduped on an open AMI call per SP.a trouble call
customer_reportAn IVR/CIS outage report → a trouble call carrying the premise id + callback number (so the restoration callback queue can reach them). Idempotent on caller_ref.a trouble call
tip The distinction that matters: device_trip raises an incident directly; last_gasp/customer_report log calls that POST /incidents/predict later clusters. An incident enters the reliability indices only when confirmed — which device_trip is, immediately.

alarm — an alarm point straight to the annunciator

Not every SCADA alarm is a device operation: a measurement limit violation, a comms failure, a station status alarm. The alarm target raises these directly onto the operator annunciator. Each point is keyed by external_id per system, so a re-raise updates one row and the sender clears it with op:"clear" (idempotent). severity is critical/high/medium/low (default medium); the device is optional — a comms/system alarm need name none.

{ "op": "raise", // or "clear" "external_id": "LIMIT-FDR7-V-01", "severity": "high", "category": "voltage", "message": "Feeder 7 undervoltage 0.91 pu", "device_external_id": "FDR7-CB7" }
Operation vs alarm

Post a trip/lockout to operation (it logs the op and raises an alarm); post a non-operation condition to alarm. The annunciator's own off-normal-configuration alarms are raised internally and need no feed.

tip A vendor that posts its own shape is bridged with the mapping spec (chapter 7). Mapping a SCADA state through an exhaustive table (LOCKOUT → device_trip) also filters: an unlisted state resolves kind to nothing, the field is omitted, and the adapter rejects a change with no kind — routine state chatter never raises an outage. The same payload can target operation or alarm on another endpoint by re-authoring the fields.

Senders that don't speak VoltEdge

A mapping spec transforms a foreign payload into native changes — before the adapter.

In plain terms

Most systems emit their own JSON shape. A field mapping on the endpoint rewrites it into VoltEdge's change shape: point items_path at the array of records, then map each field with a const (literal), a path (dot-path into the sender's JSON), or nested fields — with an optional map (value translation) and default.

Adopt, don't duplicate

Where webhooks meet references — the join that stops double records.

In plain terms

Set the endpoint's system code and a first-sight push checks the reverse index: if a feature of that class already claims the id, VoltEdge updates it instead of creating a twin. A genuinely new id creates a feature and stamps its reference so next time is a direct hit.

The other two directions on the same endpoint model.

Ada's job

🔒 Both need metadata:write. A pull endpoint inverts a push — VoltEdge fetches a feed instead of waiting to be called. An outbound endpoint emits a signed event when a matching feature changes, keeping the other system in step.

tip Outbound signs each delivery with X-VoltEdge-Signature (and tags it X-VoltEdge-Delivery), mirroring the inbound HMAC scheme so the receiver verifies it the same way. The endpoint view adds Ping (a synthetic event), an outbound delivery log, and per-delivery replay — the same operability as the inbound side.
Inbound keeps VoltEdge in step with the world; outbound keeps the world in step with VoltEdge. A full round-trip integration runs both, joined by each feature's external_ref.

Security & operations

What holds the whole surface together.

🛡️ SSRF-hardened proxy

Every outbound call (link, ref fetch, pull) is relative to the registered base URL and refuses private/loopback/link-local targets. A filled template is re-checked to be relative.

🔑 Sealed credentials

System credentials & webhook signing secrets are AES-256-GCM sealed, write-only, surfaced only as a boolean. No key ⇒ refuse to store, never plaintext.

⏱️ Replay & idempotency

Inbound HMAC carries a 5-minute timestamp window; Idempotency-Key de-duplicates retried deliveries.

🗺️ Territory & drafts

Reading/writing a feature's links & refs is gated exactly like the feature; inbound writes run as the service user and inherit that scope.

🗑️ Deleted leaves the index

A soft-deleted feature drops out of the reverse index, so it can never be adopted by an inbound push; restoring re-indexes it.
