VoltEdge guide · data validation & audit · keep a 200,000-change network trustworthy

Don't audit it all.
Let it prune itself.

Two hundred users, ten edits a day — a whole-database audit hands back a pile nobody can read. VoltEdge instead validates each change as it lands, keeps a small queue of issues that resolves itself when you fix things, and keeps a separate on-demand ledger of who changed what. This edition is a working one: run reconcile, fix a defect and watch it leave, drain the worker's backlog, and query the activity log.

Use As in the top bar. Sam is a data steward (connectivity:commit) — reconciles and triages. Remi (connectivity:read) reads the queue but can't act. Ada is an admin (admin:users) — hers is the activity audit. Dana has neither. Controls lock to what the persona may do.

Two capabilities, one idea

This guide covers two things that sit side by side. The issue queue answers "what is wrong with the data right now?" (correctness). The activity audit answers "who changed what, when?" (accountability). They are deliberately separate — don't conflate them.

The one idea to carry: flow beats batch. You never re-read the whole database. The worker validates each change as it happens and the queue shrinks itself, so what a human looks at is always small and always current.

1

What it is

Continuous validation plus an on-demand change ledger — correctness and accountability, kept apart.

In plain terms

Instead of auditing the whole network on a schedule and drowning in findings, a background worker re-checks each feature as it changes and keeps a short list of the problems that are currently open. Fix a problem and it drops off the list by itself. Separately, when you need to know who did something, you ask the change log directly.

The queue is bounded by the number of unfixed problems, not by the number of changes. That's what makes it something a person can actually work.

What's checked — and the scope trick

Two families of finding — connectivity and attribute — and the one change that makes per-edit validation cheap.

The worker runs the same audit as the whole-DB sweep — just scoped to the features that changed. Findings come in two families: connectivity (topology — orphaned links, coincident pairs) and attribute (data-quality — each existing row re-checked against the current metadata, plus admin-declared completeness rules). Why scope to the neighbourhood, not just the one feature

These problems are relational — a coincident pair or an orphaned link always involves two features. So a scoped run limits itself to connections, relationships and coincident pairs where either endpoint is a changed feature (feature_ids=…). That sees the whole of each problem it owns, while staying tiny. Empty feature_ids = the old whole-database behaviour; the summary reports scoped_to_features.

The self-pruning queue

The heart of it: find a problem, fix the feature, and watch the issue leave on its own.

Each finding gets a stable fingerprint (a coincident pair sorts its two ids, so A|B and B|A are the same issue). Reconcile upserts on it — found again? the same row updates, never a duplicate. Gone? it auto-resolves. Drive it:

6

The worker — making it automatic

No write-path change: the worker tails the change log the app already keeps.

In plain terms

Every feature write already appends one row to gis.feature_history (an auto-numbered ledger). The worker just remembers how far it's read (a cursor), grabs the new rows in batches, validates those features, and moves the cursor on. Nothing new had to be bolted onto the write path.

Make a few edits, then sweep. Each sweep takes rows past the cursor (up to the batch), validates their features, and advances the cursor.

—
The truncation guard. Auto-resolve trusts "I checked the whole scope." If a whole-DB run hits the findings cap and truncates, a missing fingerprint could mean fixed — or never reached. So on a Truncated run, reconcile skips auto-resolve (it still records what it found). Scoped per-edit runs are tiny and never truncate, so the automatic path always prunes correctly.
The one honest gap

feature_history ids can commit slightly out of order under load, so a burst edit can rarely be tail-skipped by the cursor. Two backstops make it a non-issue: the feature's next edit re-validates it, and a nightly whole-DB reconcile (POST /connectivity/audit/reconcile, no body) catches anything missed. The sweep is idempotent, so run exactly one worker — no lease needed, and two instances would just race the cursor.

Two deliberate choices

The snapshot is omitted. An activity log is who/what/when; to see the state a change produced, drill into that feature's own history. Keeping the before/after out keeps this a fast, scannable ledger.

Private drafts are respected. The same visibility gate the per-feature timeline uses applies here — a peer's staging rows stay inside their own draft chain and never surface in your cross-feature slice. (Try filtering to Kemi below: her stage row is hidden from everyone but her.)
