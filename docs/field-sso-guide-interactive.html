Administrators enrolling crews and operators deploying the field SSO config — plus anyone debugging a sign-in that won't complete. 01

Why field auth is different

Same accounts, same Azure — but a browser keeps a cookie and a tablet keeps a token.

Web and field SSO share everything that matters for identity: the same Azure provider, the same user accounts, the same match-or-reject logic. What differs is the credential the surface can hold, and that one difference shapes the whole flow.

WebField app
CredentialCookie session (browser auto-sends it)Bearer token in the device keystore
SSO ends bysetting the session cookie, redirect to /handing the device a one-time code via voltedge://, which it swaps for tokens

Two server processes matter, and they share one database — which is what makes the hand-off possible. cmd/server hosts the OIDC endpoints (/auth/oidc/…, /auth/providers) and holds the Azure-registered redirect. cmd/fieldsync is the field engine the device talks to for packs, sync, and redeeming the SSO code. SSO runs on the first, drops a one-time code in the shared Postgres, and the device redeems it on the second.

03

Enrolment & the two gates

Microsoft authenticates; VoltEdge authorises. Both must pass.

SSO never auto-creates accounts. A Microsoft sign-in only gets a crew member into the field app if an administrator has already provisioned them. Two steps:

  1. Create the user (Admin → Users) with email = their Microsoft account email. The emails must match — that's how VoltEdge links the Microsoft identity to the account on first login. No VoltEdge password is needed.
  2. Grant a role with field:login (any field role, or admin). Without it, Microsoft accepts them but the field app refuses.

So a field SSO login passes two gates, in order — Microsoft authenticates, then VoltEdge authorises. The password only ever reaches Microsoft, so a “password incorrect” message is a Microsoft/account matter, never a VoltEdge one.

04

The token model

A short access token the device uses, a long refresh token it swaps — so crews don't re-authenticate daily.

A password or SSO login (migration 0191) mints a pair:

Access token ~24h

An iam.api_tokens row — the bearer presented on every call. Short-lived so a leaked token self-heals quickly.

Refresh token 21d default

An iam.field_refresh_tokens row in the device keystore. The device swaps it for a fresh access token without re-authenticating. TTL = FIELD_REFRESH_TTL_DAYS (default 21).

Align with SSO password rotation The refresh token is independent of Azure — field-refresh re-checks the VoltEdge account (active + field:login), not Microsoft. So disabling the VoltEdge user cuts access within ~24h (next access refresh), but an Azure-side change (password rotated, account disabled in Entra) isn’t reflected until the refresh token expires. If your org rotates passwords every N days, set FIELD_REFRESH_TTL_DAYS ≤ N so a device must re-SSO within one cycle — re-SSO re-delegates to Azure’s current policy. A shorter TTL caps staleness; it is not instant revocation.
# .env — applies to all field logins (password and SSO) FIELD_REFRESH_TTL_DAYS=21 # default; set ≤ your IdP rotation period
Why non-rotating? Rotating the refresh token on every use is more secure in theory, but a field device's connectivity is flaky — a dropped rotation reply would strand it and force a needless re-login. v1 keeps the refresh token stable until expiry or revocation. Admin revocation of the user or their tokens still cuts off both web and field immediately.
05

Server & Azure setup

One extra redirect URI, one env var, one migration. Web SSO is untouched.

Field SSO reuses your existing Azure app and web OIDC config. Three one-time changes:

  1. Azure: add a redirect URI for the API origin the device reaches, i.e. <api-origin>/auth/oidc/azuread/callback, alongside your web redirect (keep both). The field flow derives this from the request — it just needs to be registered.
  2. Env: set FIELD_SSO_WEB_ORIGIN (on the API + fieldsync services) to that API origin, so GET /auth/sso-config tells the device where to start.
  3. Migrate: apply migration 0191 (the hand-off + refresh-token tables).

Local dev & device testing

The hard-won part: ports, tunnels, and two traps that look like app bugs.

In production there's one origin and none of this applies. But testing on a physical tablet against Docker containers has sharp edges — here they are so nobody re-walks them.

6.1 The port map (docker-compose defaults)

ServiceHost portServes
cmd/server (api)3704 (API_PORT; internal 8080)OIDC, /auth/providers, the field callback
cmd/fieldsync3706 (FIELDSYNC_PORT)packs, sync, /auth/sso-config, /auth/field-sso/exchange
web (Vite dev)5173the web app; proxies /api → :3704

6.2 Reaching the host from the tablet

Use adb reverse so the tablet's localhost maps to your host — then the same localhost URLs work on the device and in Azure:

# one task does all ports task adb-reverse # reverses 3702/3704/3706/5173, then --list adb reverse --list # confirm after every replug / adb restart
adb reverse drops silently A container recreate, a device replug, or an adb/flutter run restart clears the reverses. The symptom is Connection refused … localhost:3706 in the app while your PC curl to the same port works. Re-run task adb-reverse. This bit us repeatedly — check it first.

6.3 Trap 1 — don't route field SSO through Vite

The web dev server (:5173) proxies /api to the API. It's tempting to point FIELD_SSO_WEB_ORIGIN at localhost:5173/api so you reuse the web redirect — don't. The Dart HTTP client gets Connection reset by peer from Vite's proxy (a Dart-vs-Node-proxy quirk), even though the device's Chrome reaches the same URL fine. Point the field app straight at the API container (:3704) — a Go server, which the Dart client reaches cleanly (just like :3706). This is also the production shape: no Vite in prod.

6.4 Trap 2 — localhost vs 127.0.0.1

If the app's own HTTP calls intermittently Connection refused while the browser works, suspect IPv6: Android can resolve localhost to ::1, but adb reverse only listens on IPv4 127.0.0.1. In our setup both resolved fine — but if you hit it, the fix is not to change Azure (its Web platform rejects 127.0.0.1). Keep the browser/Azure on localhost; only the device's own socket needs IPv4.

Ordering Just to make the button appear, cmd/fieldsync needs to be rebuilt (it serves sso-config). To complete a sign-in you also need cmd/server rebuilt (the field callback) and migration 0191 applied.

08

Security model

What VoltEdge sees, what it never sees, and how access is cut.

  • VoltEdge never sees the password. It goes to Microsoft; VoltEdge only receives a verified id_token. A “password incorrect” is always Microsoft-side.
  • The hand-off code is single-use and short-lived. iam.field_sso_handoff rows are consumed atomically (only the first redeem of an unused code wins) and expire in 2 minutes. They store a user reference, never a token.
  • Request-origin redirect is safe against Host spoofing. The field flow derives redirect_uri from the request, but Azure only ever redirects to a pre-registered URI — an unregistered (spoofed) origin is rejected by Azure regardless.
  • PKCE + state + nonce protect the auth-code flow exactly as the web flow does; the field variant reuses the same verification.
  • Linking by email on first login is a trust decision. Whoever controls a Microsoft account asserting a verified email can claim the pre-provisioned VoltEdge account with that email. Bound by your Azure tenant restriction.
  • Revocation cuts both surfaces. Disabling the user, or revoking their tokens, stops web and field. Device sign-out revokes the refresh token; the short access token lapses on its own.
  • Trade-off noted: the refresh token is non-rotating in v1 (chapter 4) — a deliberate choice for field connectivity, revisitable with rotation + a grace window if policy requires.
