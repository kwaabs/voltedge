The task-oriented guide to the electrical-network GIS, rebuilt as something you can operate: sign in as a viewer, an analyst or an editor and watch the buttons appear and vanish; get territory-scoped; query a few hundred assets; wire a transformer; trace a feeder; run an outage from trouble call to restoration; print a label.

About this handbook

This handbook is for the people who use VoltEdge day to day: viewers, analysts, editors, field crews and supervisors. It’s deliberately how-to first. Where something is gated by a permission you may or may not hold, it says so plainly (“this needs the editor role”). If you administer VoltEdge — permissions, compiling feature classes, resets — the companion Admin & Break-Glass Guide is your reference.

It documents everything that has been built, including capabilities still being rolled out. If a screen described here isn’t visible, the usual reasons are: (1) you don’t hold the permission, (2) it’s outside your territory, or (3) your installation predates it.

01

Introduction & core concepts

The mental model you need before touching any button.

1.1 What VoltEdge is

VoltEdge is a geographic information system purpose-built for electrical distribution and transmission networks: a living map of every pole, transformer, switch, cable, busbar and service connection — combined with the electrical intelligence that ties them together. A general map tool stores dumb points and lines; VoltEdge understands that a transformer has terminals, that those terminals connect to conductors, and that power flows from a source through that chain to a customer. That’s what lets it:

  • Trace — “what is upstream of this fault?”, “what will I de-energise if I open this switch?”
  • Analyse — load flow, fault current, protection coordination, hosting capacity, arc-flash.
  • Operate — outages (OMS), defects and work (WAM) and fault events, all pinned to the same map.
  • Go to the field — build an offline pack, edit on a phone with no signal, sync back.

VoltEdge is metadata-driven: there’s no hard-coded list of “the twenty kinds of asset we support.” An administrator defines a feature class — its fields, symbol and rules — and the system compiles it into a working part of the product. That’s why two installations can look quite different.

Everything is built from a small set of concepts. The schematic below is the suburban feeder from §1.4. Pick a lens to see the same network through each concept; click any asset to see all of its data-model facets at once.

CircuitA named electrical grouping — the run of network fed as a unit. Membership is explicit (circuit_id); a denormalised circuit_ref label is derived by tracing and read-only. Managing circuits needs circuits:write.

1.3 The draft → published lifecycle

A draft is being worked on and isn’t part of the official network; a published feature is live. New features start as drafts; you publish to promote and unpublish to pull back. Two refinements (covered fully in Chapters 3 and 6) are private drafts — never-published work visible only to you and your management chain — and private edits over published features. Try them in Interactive 4.

Permissions & what you can see

Why your VoltEdge looks the way it does — two independent systems that stack.

Two systems decide what you can see and do: permissions (via your role) — which capabilities you have — and territory access — which slice of the network those capabilities apply to. You need the right permission and the feature must be in your territory.

3.1 How permissions work

  • A permission is a single named capability (“read features”, “commit connectivity”).
  • You’re assigned one or more roles; each carries a bundle of permissions. Your effective abilities are the union across every role you hold.
  • Hold no role and you can do nothing — not even view. An empty-looking app often just means no role has been assigned yet.

3.4 Territory access — which slice is yours

  • Grants cascade down the hierarchy: a grant covers that node and everything beneath it.
  • Management cascades up the org chart: if you manage people you inherit the union of their grants, transitively. (Never upward from your own manager.)
  • When enforcement is on, the constraint applies to the map, lists, opening a feature (out-of-scope → “not found”, never “forbidden”), editing, tiles, exports, queries, aggregates and history.
  • Fail-closed: “scoped to nothing” means you see nothing; a feature with no territory stamp is invisible to a scoped user.
  • territories:unscoped bypasses it entirely. Revocation is immediate. Enforcement is a rollout switch that ships off.

Operate the example from §3.4.9: pick a person, toggle enforcement, revoke a grant, add an unstamped feature.

5.5 Spatial scope — asking “…here”

  • No scope — everywhere you can see. Territory — that territory and everything beneath it (the same subtree logic as access grants). Radius — true ground metres: pick a point, set 100/250/500/1000/2000 m (default 250) or type an exact distance.
  • All feature classes pairs with a radius: drop a circle on a fault location and see “23 features here — 8 service points, 6 poles…”. A class you can’t read contributes nothing rather than breaking the sweep.

5.7 Drill-down — every number is a doorway

Click a total, a group row or an all-classes row and VoltEdge re-runs the query for exactly that slice — your conditions and scope preserved — listing the rows and highlighting them on the map. Back to counts returns; closing clears the highlight. Dana’s PILC loop: aggregate LV cables by material in Riverside (“PILC: 137”) → click the PILC row → click a row to fly to the cable → export to CSV for the programme.

Practical tips
• Results respect your access — two users running the same query can legitimately get different numbers. • Aggregate first, drill second. • Use scope to keep lists manageable (filters return a page of rows at a time). • The (unset) bucket and is empty are your data-quality friends. • Radius is true metres. • Computed fields are queryable but not editable.

6.4–6.6 Draft → published, private drafts and staged edits

Publish promotes a draft to the network of record (visible to everyone in territory; part of traces, analyses, exports, tiles). Unpublish pulls it back — use sparingly, other work may reference it. A feature you create and never publish is automatically a private draft (if enabled) — the privacy is the draft. A staged edit over a published feature shows a banner with Apply and Discard and a badge in lists; only you see it. Interactive 7 (Chapter 3) walks all of this.

6.7 Splitting a line feature

Split cuts one line into two at a point — a joint, or a new pole dividing a span. It applies only to simple line features (not points, polygons or multi-part lines), and you can’t split a deleted line (restore it first). The cut must be in the interior — on or right next to an endpoint is refused. The original is shortened to the near half and keeps everything else (attributes, connections, relationships, territory); the far half becomes a brand-new feature whose geometry is computed — you fill its subtype, name and attributes like any create. It starts unconnected; connection suggestions re-run so re-stitching is quick. Click along the span where the pole sits:

6.8 Deleting and restoring · 6.9 Concurrent-edit protection

Delete is soft: the feature drops out of the map, lists and queries but isn’t obliterated, so an accidental delete can be restored. References aren’t automatically fixed — prefer editing or splitting over delete-and-recreate. 6.10–6.12 Assemblies, a worked day, tips

Composites (a pole with its transformer kit, a packaged substation, an RMU) belong to guided assemblies — Chapter 7. 7.6.3 The feeder tie — meant to be open

A feeder tie is a one-click normally-open link between two different feeders, via a switch. VoltEdge creates the switch and both connections and forces it normally-open — it’s closed only during switching, never to parallel feeders in normal operation. It’s the cross-feeder counterpart of the bus coupler (which ties two busbars on one site). Contingency studies (Chapter 8) reason about it.

Tips and gotchas
“Touching” is not “connected.” Connect the right terminals — HV upstream, LV downstream. If the kind picker blocks you, those classes genuinely aren’t meant to relate that way. Use assemblies for anything multi-part — they can’t forget an internal connection. Don’t “fix” an open tie. Re-trace after revoking.

8.3 Traces in words

  • Barriers — a trace stops at an open device (open switch, breaker, tie); a feature’s operational state also shapes what it crosses. A trace that “stops early” is almost always correct — check the device states before suspecting the trace.
  • Supply path — walks upstream, barrier-free: LV switching devices → serving distribution transformer → MV devices → any power transformer → source. It ignores open devices because the question is “what supplies this?”, not “what’s energised now?”
  • Isolate from here — composed from two ordinary traces: a downstream walk (what goes dead) and an upstream walk (the protective boundary you must open). Only offered on a switching device.
  • Section — the run between the nearest bounding devices upstream and downstream. Feeder — the whole feeder from any starting point: find the root(s) upstream, then walk down.
  • Results open in a floating table and highlight on the map; only features in your territory are returned.

Operations modules (OMS, WAM, Faults)

What happens to the network over time — three views of one real-world event.

9.1 Shared ideas

  • Operational records are not map features. An outage, a defect, a work order, a fault event are transactions about features. They won’t appear in the Features browser or the query engine; each has its own page, its own permission pair, and attaches to assets by reference (asset class + id).
  • Three pages, three permission pairs: Outages (oms:read/oms:write), Faults (faults:read/faults:write), Works (wam:read/wam:write). No …:read → no sidebar entry; read without write → disabled buttons.
  • Every record has a lifecycle — a status that only moves forward. Explore each below.

9.2 Outage Management — the prediction rollup

Trouble calls (no supply · partial · flicker) may reference a service point or only an address. The prediction rollup takes open calls, walks upstream from each affected service point and finds the common protective device that would explain them all — writing a single predicted incident blaming it, with a confidence score. It touches nothing in the live network; a human confirms. Affected area is the downstream blast radius. Planned outages start at scheduled. A switching order is the ordered open/close program (isolate → restore; actions open/close/earth/verify/note) — generated, then executed step by step.

9.3 Faults

A fault event captures a type (SLG, LL, LLG, LLL/LLLG, earth, unknown), fault current (A), clearing time (ms), the protective device that operated and the optional affected asset. Lifecycle: detected → investigating → cleared → closed. Log it from scratch (asset-ID picker) or from an outage (Raise fault); Book defect mints a WAM defect linked back (de-duplicated). Every fault has an append-only history; the map has a status-coloured Faults overlay with impact halos (toggle it in Interactive 4), and each feature has a Faults tab.

9.4 Work & Asset Management

Defects carry severity (low/medium/high/critical), source (inspection/outage/condition monitoring/ad hoc) and status (open → work_ordered → resolved, or dismissed). One work-order engine serves four work types — inspection, corrective, preventive, construction — with one lifecycle and one priority scale (low/medium/high/urgent), assignable to an internal worker or a free-text external crew, with scheduled-for and due-by. Inspection templates are reusable checklists scoped to an asset class; each item answers as pass/fail, rating, numeric or free text and may carry a fail severity — marking it failing auto-raises a defect at that severity:

The field app (offline)

Download your work area while you have signal, work with none, sync when you’re back. The Field Tool guide is the full crew manual.

The companion Flutter app serves the field roles. A day always has three beats: Pack → Work offline → Sync. Your permissions travel with you — there’s no “field mode” that grants extra rights. You sign in with the same account (server address, email, password); the app exchanges it for a bearer token behind the scenes.

11.3 Field packs — frozen from your rights

A pack is an offline basemap (MBTiles) plus a data pack (SQLite — the edit-truth), always bounded by a bounding box, with a snapshot time. Its contents are frozen from your rights at the moment you request it: the build runs detached on the server with no ability to re-check you, so it packs exactly what your roles authorised. Ask for a module you can’t read and you don’t get an error and a leak — you get a pack without that module. WAM and Faults are independent inclusions.

Asset tags & scannable labels

Every feature carries a scannable code; print it, stick it on the plant, scan it back to the record.

Two permissions turn this chapter: tags:read (scan, resolve, view a feature’s tags, print) and tags:write (register, set primary, void, reissue, record a print). Codes are minted automatically for every asset, one asset can carry several, and a scan is scope-aware. (The Markdown handbook numbers this chapter’s subsections 14.x; they’re 13.x here.)

13.1 What a tag is — build one

A code looks like VE-7Q3KM: a VE- prefix, a body — a global sequence value in Crockford base32 whose alphabet omits I, L, O and U so nobody misreads 1 for I in the rain — and one trailing check character: a position-weighted sum of the body’s digits mod 32, mapped back through the same alphabet. Codes are globally unique and never reused. This is the real algorithm:

∑ What the check character really catches

Position weights mean most single-character slips change the sum. The widget above counts them honestly for the code you minted: for a typical 4–6-character body, a handful of substitutions (where position × difference is a multiple of 32) slip through. So “mistype one character and it’s invalid” is true of the great majority of slips — not every one. Read the printed text again before assuming the tag is broken.

13.1.2 One asset, many codes — and one primary · 13.4 Managing tags 🔒

Besides the system-minted code (source: generated) a feature can carry legacy/external codes (source: external). Exactly one is primary — the one printed. All active codes resolve. Register a legacy code (so scans of the old label still work), Set primary, Reissue (old → superseded — still resolves — plus a fresh code) or Void (stops resolving; you can’t void the primary). Soft-deleted assets keep their tags; only a purge removes them.

13.5–13.7 Resolving a scan — scope-aware, offline-first

On the web, …/t/<code> or Resolve tag looks the code up and, on a hit, selects the feature and opens the map on it. In the field app the scan resolves against the pack’s tag index first (instant, no network); if absent and online it falls back to an online resolve; an asset outside the pack is named but can’t be placed. A scan is a read, so it obeys the same two fences — territory and draft visibility — and an out-of-scope or non-existent code returns the same “not found”. A voided code is not found; a superseded one still resolves.

14.1–14.3 How authorization works

“Authorization as data”: a fixed catalogue of permissions (resource:action), roles as named bundles, a user holding one or more roles — effective permissions are the union. Every protected route checks one permission (read-style requests need the read-side, mutating ones the write-side). On top sit territory scoping (a spatial fence ANDed onto what permissions allow) and the break-glass override. Adding a distinction is a data row, not a code change. There are 34 permissions (the Markdown lists 33; features:wipe is the extra) and nine roles.

Permission says what you may do; territory says where.
