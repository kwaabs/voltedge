01

How the pieces fit together

Two server processes, two storage systems, two kinds of person.

Two server processes matter, and keeping them straight answers most “where do I look?” questions. cmd/fieldsync is the field engine: one process that receives a device’s edits, builds packs (tippecanoe + SQLite) and applies synced edits to the live database. It is the process you scale (Chapter 4). cmd/server is the main web API; it hosts the admin pack-management and sync-review surfaces you use, behind your web session and RBAC. Everything a crew does flows through cmd/fieldsync; everything you do flows through cmd/server. Pick an action and follow it:

Notice how often Postgres is the meeting point. The two processes never call each other: a held edit is released by cmd/server flipping a status, and a worker in cmd/fieldsync picks it up. That is why a database that is slow or out of connections hurts everything in the field tool at once.
02

Giving crews access

A login, a handful of permissions, and a territory.

2.1 Signing crews in

Crews sign in with email + password on the app’s Connection screen, which exchanges them for a long-lived device token behind the scenes — they never handle a token. A crew member needs a user account (created the normal way in the web app) and the permissions below. There is also a lower-level path — minting an API token directly (task authadmin-mint-token EMAIL=… NAME=field-tablet) and pasting it — but the email/password login is the normal route.

2.2 The permissions that gate the field tool

A crew member’s RBAC decides both whether they can use the field tool and what their packs contain. Crucially, these are frozen into the pack when it is built, from the requester’s RBAC at that moment. So if a pack is missing a work board or won’t let a crew connect features, check their permissions — then they must rebuild to pick up the change. Try it: build a pack, then change the permissions.

If you use spatial access control (territories), a scoped crew member’s packs and their synced edits are confined to their territories, exactly as in the web app. Their offline edits re-enforce that scope on the server when applied — an edit outside their territory is refused on sync, however the tablet allowed it offline.

Managing packs — the Field Packs page

Everyone’s packs, newest first, three actions.

Open Field Packs in the web app (/field-packs, gated on admin:field-packs). Unlike the crew view — which only shows a crew their own packs — this lists every user’s packs, newest first, with the owner, the area (bbox + classes), status, feature count and artifact sizes. Three actions:

ActionWhat it doesReversible?
DisableHides the pack from its owner’s device list (sets a flag). The files stay in storage. Stops a stale pack crowding a tablet.Yes — Enable brings it back
EnableUn-hides a disabled pack—
DeletePermanently removes both pack files from storage and the recordNo — permanent

Disable vs. Delete. Disable is the everyday tool — it declutters a crew’s device without destroying anything. Delete is for reclaiming storage from packs you’re certain are finished with; it reaps the (potentially tens-of-MB) files. Deleting a pack that is still building just removes the record; if the build later finishes, its upload is left for the storage retention sweep. 04

Tuning and scaling

Two surges, two workloads, one process to scale.

This is the operational heart of running the field tool for more than a handful of crews. There are two workloads — building packs (a download surge, usually shift-start) and applying synced edits (an upload surge, usually shift-end) — and both run in cmd/fieldsync.

4.1 The knobs

All are environment variables on the cmd/fieldsync process.

VariableDefaultWhat it controls
Pack build (download side)
FIELDSYNC_MAX_FEATURES200000Hard cap on features per pack. A bigger request fails loudly (“narrow the bbox or class set”) rather than building a giant pack that is slow to build, huge to download and risky to open.
FIELDPACK_MIN_ZOOM8Lowest map zoom in the pack. Keep it low — below it, the crew’s map goes blank when zoomed out to navigate.
FIELDPACK_MAX_ZOOM16Highest tile zoom. 16 (~2.4 m/pixel) separates typical utility features; crews can zoom past it (tiles scale up) and taps still hit full-precision data. 4.2 Scaling for a fleet

The shipped defaults (one cmd/fieldsync, concurrency 2 each) are fine for a small team but not for a large fleet syncing at once. For hundreds of crews, many concurrent at shift change:

  1. Put PgBouncer in front of Postgres. At high concurrency the single biggest limit is database connections; transaction pooling is effectively mandatory. (See the Production Deployment & Scaling guide.)
  2. Raise the concurrencies and run replicas. Both workers claim work with FOR UPDATE SKIP LOCKED, so you can run several cmd/fieldsync replicas safely; they share the build and sync queues. Size build concurrency to CPU cores (tippecanoe) and sync concurrency to your PgBouncer pool.
  3. If download and upload surges overlap (staggered or round-the-clock shifts), consider a read replica for pack builds — the build is read-only and the heaviest DB consumer, so moving it off the primary protects the sync/edit path.
  4. For a geographically clustered fleet, the biggest lever is not building the same area many times. If 60 crews cover one depot, that is 60 identical builds. Shared packs (Chapter 6) pre-build a depot once as a cell, overnight, and every crew covering it picks up the same build.

4.2a Worked sizing example

Build capacity is simple division, so you can predict the shift-start queue before it happens. Let N = packs requested in the surge, t = seconds one build takes (read it from the elapsed_ms the worker logs), c = FIELDSYNC_WORKER_CONCURRENCY, r = replicas.

   queue drains in  ≈  N × t / (c × r)
   120 crews × 40 s / (2 × 1)  =  2 400 s  ≈ 40 min   ← the last crew waits 40 minutes
   120 crews × 40 s / (4 × 3)  =    400 s  ≈  7 min   ← 3 replicas, concurrency 4

Two things cap how far you can push it. CPU: tippecanoe is CPU-bound, so c × r beyond your total cores only makes each build slower. Database connections: every in-flight build and apply holds one, so c × r must fit inside the PgBouncer pool. And the cheapest lever is to reduce N: a shared cell turns 60 builds into 1.

4.3 Reading the signals

  • Every successful build logs its duration (elapsed_ms) and counts. Watch these to size build concurrency and spot packs that are too large.
  • A build queue draining slowly at shift start → raise build concurrency / add a replica / trim FIELDPACK_MAX_ZOOM or the class set.
  • Synced edits taking minutes to show up in the office → raise sync concurrency / add a replica — but first check the review queue: a held edit can block a device’s later edits (Chapter 5) and look exactly like a slow worker.
The one rule: don’t raise the concurrencies without PgBouncer in front of the database. More workers hammering an unpooled Postgres makes things worse, not better.

  • Two workloads, both in cmd/fieldsync: build (shift-start) and apply (shift-end). Defaults suit a small team.
  • Drain time ≈ N × t / (c × r), bounded by cores and the pool. PgBouncer first; replicas are safe (SKIP LOCKED).

05

Reviewing field work — QA mode

Auto-apply, or hold for a human. And what holding does to a tablet.

By default every synced edit applies automatically moments after it is captured. For classes where you want a human to check field edits before they reach the live network, switch that class (or everything) to review mode. Those edits are held, and a supervisor posts or rejects each one. This is the Sync Review surface (/sync-review): sync:review to view, sync:post to act.

5.1 Setting the apply policy

The apply policy decides, per feature class, whether synced edits auto-apply or wait for review. Set a global default and per-class overrides — for example, global auto but MV_CONDUCTOR on review so conductor edits get a second pair of eyes. Clearing an override reverts that class to the global default. A companion setting, conflict detection, is also per class (with a global default): with it on, an edit whose feature was changed in the office after the crew’s pack was built is held as a conflict rather than silently overwriting (§5.5).

ModeBehaviour
autoEdits apply automatically (the default)
reviewEdits are held until a supervisor posts them

mode and detect conflicts are independent dimensions: a class can auto-apply and still be conflict-checked. An empty policy table means everything auto-applies and nothing is conflict-checked — QA mode is switched on by writing a row, with no redeploy.

5.2 The review queue — post or reject

Open Sync Review. The default view is the pending review queue, oldest first — which is also the order edits will apply in. For each held edit you see who submitted it, the feature and class, and the proposed change.

   held edit ──► review it ──► ┌─ POST   → released to apply (enters the normal queue)
                               └─ REJECT → quarantined; the crew sees it in
                                           "needs attention" with your reason

Post releases the edit — the worker applies it in order like any auto edit. Reject quarantines it with a reason you provide; the crew sees it on their device’s needs attention list and can re-do it. You can also filter to applied, rejected or conflict to audit what has been decided.

5.3 Resolving conflicts

A conflict means: the crew edited a feature offline, but the office changed the same feature after the crew’s pack was built. Applying the crew’s edit would overwrite the office change, so it is held. Open the conflict to see the crew’s proposed change against the current live value, then:

Resolve asResult
Apply anywayThe crew’s edit is applied, overwriting the current value
KeepThe crew’s edit is discarded; the live value stays. The crew sees it rejected in “needs attention” with your reason.

Conflicts only happen for classes with conflict detection turned on. Leave it off and the system is last-write-wins — fine for capture-oriented fields, risky for contended ones.

5.4 How held edits queue — one device, one lane code-verified

Edits from one device always apply in the order the device captured them. The worker enforces this with a per-device single-flight rule: it will not hand out an edit while an earlier edit from the same device is still active — received, applying with a live lease, pending_review, or conflict.

The consequence catches administrators out. A held edit blocks every later edit from that device — even edits to classes set to auto. If a crew’s first edit is on a review class and nobody posts it, their next ten edits (on any class) sit received behind it, and nothing from that tablet reaches the office. An unresolved conflict does the same. Run scenario ① in Interactive 9: the transformer and RMU edits never apply until the conductor edit is posted.
Edit statusMeaningBlocks the device’s later edits?
receivedCaptured, waiting for a workerYes (earlier and not yet applied)
applyingA worker holds it; lease is liveYes — until the lease lapses (then it is reclaimable)
pending_reviewHeld by a review policy; awaits Post/RejectYes
conflictHeld because the office changed the feature; awaits Apply anyway/KeepYes
appliedDoneNo
rejectedA reviewer (or an apply failure) refused it; the crew sees it in needs attentionNo — one rejected edit never stalls the device
supersededA newer edit to the same feature stepped in front of itNo

So the practical rule for a supervisor: clear a crew’s oldest held edit first — the queue shows oldest first for exactly this reason — and read “a crew says none of their edits arrived” as “find their oldest held edit”.

5.5 What a conflict check actually compares code-verified

When detection is on for a class, the worker checks each update or delete just before applying it. It compares the feature’s current live version with the snapshot of the pack the crew made the edit against (base_version, stamped on every edit by the device). If the live row changed after that snapshot, the edit is held as a conflict.

  • Creates are never checked — a create mints a new row, so there is nothing to conflict with.
  • An edit with no base_version is not checked (older edits made before the stamp existed) — tick “older edit” in Interactive 9 to see it slip through.
  • If the crew edited the same feature several times offline, only the newest edit surfaces as the conflict; older ones become superseded and step aside silently — one conflict per feature, not per keystroke (scenario ③).
  • Apply anyway re-queues the edit with the check waived; Keep discards it and tells the crew why.
  • If the check itself errors, the worker logs it and applies the edit anyway — detection fails open, so don’t treat it as a hard lock on a contended class.

Chapter summary

  • Policy is per class plus a global default: auto or review, and independently detect conflicts.
  • Post releases a held edit; Reject quarantines it with a reason the crew sees; conflicts resolve as Apply anyway or Keep.
  • One device, one lane: a held edit or unresolved conflict blocks all of that device’s later edits.
  • A conflict compares the live row’s last change with the pack snapshot the edit was made against — updates and deletes only, and only if the edit carries a stamp.
06

Pre-building shared packs

Build an area once; let every crew that covers it pick up the same build.

For a clustered fleet, the biggest waste is many crews each building the same area. Shared packs fix that: you pre-build an area once as a reusable cell, and every crew whose access covers it picks up that single build — instantly, no build wait — and reuses it for as long as the job runs. It is optional: where coverage is unpredictable (roaming crews into new ground), define no cells and crews keep self-serving their own packs. The two coexist.

How it’s managed today. Cells and their usage are driven through the Field Packs admin API (/field-packs/cells… under cmd/server, gated on admin:field-packs + CSRF). A web UI for cells is planned; until then these are operator/API actions, so each widget below shows the request it stands for.

Creating a pack as an admin — which route?

Unlike a crew (who builds their own pack on the device), an admin has no ad-hoc “build a personal pack” button. There are three routes, depending on who the pack is for:

You want to…UseHow
Give many crews one reusable areaA shared cell (§6.2)Define a cell → build a version → crews pick it up
Cover a big territory in sub-areasThe grid helper (§6.3)One call makes a whole grid of cells
Stage a personal pack for one crew memberBuild-on-behalf (§6.7)Build a pack owned by them, scoped from their RBAC

The common case — build a shared pack (3 steps): (1) define the cell — POST /field-packs/cells; (2) build a version — POST /field-packs/cells/{id}/build (or let a schedule do it overnight); it runs through the normal pack queue, queued → running → succeeded; (3) crews pick it up — anyone whose access covers the cell sees it under Shared packs and downloads it instantly. 💡 Just want a pack for yourself? You’re a user too — build one from the mobile app exactly as a crew does, or use build-on-behalf with your own user id.

6.1 How shared packs work — base + overlay

   SHARED BASE (one build, many crews)        PER-USER OVERLAY (each crew, live)
  ┌────────────────────────────────┐         ┌────────────────────────────────┐
  │  Published features + map tiles │    +    │  This crew's work board         │
  │  Connectivity / relationships   │         │  This crew's OWN draft features │
  │  Open faults, asset tags        │         │                                 │
  │  NOTHING personal/unpublished   │         │  (fetched at pickup + each sync) │
  └────────────────────────────────┘         └────────────────────────────────┘
                     └──────────────┬──────────────────┘
                        the device composes BASE + OVERLAY + the crew's own edits

The base is published-only and crew-neutral — no one’s unpublished drafts and no personal work board. That is the safety guarantee that lets one build be handed to many crews. The overlay is each crew’s thin personal layer, delivered when they pick up and refreshed each sync.

Pickup gating. A crew may pick up a cell only if their entitlements cover it: their territory access must include the cell’s territory, and they must hold the *:read permission for every extra the base carries. A crew that doesn’t fully cover a cell never sees it and can’t pull it — there is no reduced fallback. If crews have mixed permissions, define a leaner cell rather than weakening the rule. 6.4 Scheduling overnight rebuilds

  
A cell’s schedule is a cadence token — hourly, daily or weekly (anything else, or empty, means no schedule). A scheduled cell is rebuilt when its newest version is older than the cadence. To keep heavy builds off peak hours, confine them to a build window:

  
Variable (cmd/fieldsync)DefaultWhat it controls

    
FIELDSYNC_BUILD_WINDOW(unset)UTC hour window start-end (e.g. 0-5) scheduled builds are allowed in. Wraps midnight (22-5 works). Unset = any hour.

    
FIELDSYNC_MAINTENANCE_INTERVAL15mHow often the maintenance loop checks for due rebuilds and runs retention.

Exactly when does it fire? code-verified On a tick, each active, scheduled cell is enqueued only if both hold: no build is already queued or running, and its newest succeeded version is older than the cadence (or it never built). The window is hours [start, end) UTC — 0-5 allows 00:xx–04:xx, not 05:xx; a malformed value is ignored (any hour). The age counts from when the last successful build was enqueued, so a cell whose builds keep failing is due on every tick — fix the cause (usually the feature cap) rather than waiting. A scheduled build is attributed to the cell’s creator. And retention runs on every tick, in or out of the window — only scheduling is window-bound.


  
6.5 Retention — keeping storage in check

  
Rebuilding piles up versions. Retention reaps old ones — but never one a crew still holds. The per-cell policy:

  
PolicyBehaviour

    
manualNever auto-reaped — you delete versions by hand (the per-pack Delete, §3).

    
pinnedNever auto-reaped — explicitly protected.

    
keep_nKeep the newest N succeeded versions; reap older ones that no crew holds. FIELDSYNC_KEEP_VERSIONS (default 3) sets N.

  
The maintenance loop runs retention each tick; you can also apply a cell’s policy on demand with POST /field-packs/cells/{id}/reap (it reports how many were reaped). “Held” is precise: a version is held while it is some crew member’s latest pickup of the cell. Reaping deletes both stored files and the row; the ledger rows cascade with it. The next widget carries retention and the usage dashboard, because they read the same ledger.


  
6.6 Who’s holding what — the usage dashboard

Each synced edit carries the snapshot time of the pack it was made against. The report matches a crew member’s edits to the exact version they currently hold. So a crew member who just re-pulled a newer version shows quiet until they sync something made against that version, even if they synced plenty against the previous one. Read “quiet” as nothing synced against the version they hold yet, then look at the pickup date. Try it: press “re-pull latest” on a holder with synced work.


  
6.7 Staging a pack for a crew — build-on-behalf

  
Separately from cells, you can pre-stage a personal pack as a named crew member (POST /field-packs/on-behalf), so a tech finds a ready pack on first connection. Crucially it is scoped from their RBAC, not yours: the include flags come from the target’s permissions, their drafts from their own visibility, the territory filter bounded by their scope. The body carries only the crew member, bbox and classes — the include flags are deliberately not in the body, so an admin cannot widen them. The pack is owned by the target and shows up in their device list only.

6.8 Permissions

  
All cell administration is gated on admin:field-packs (plus CSRF), the same as the pack-management page. Pickup uses the crew’s own RBAC — territory access and *:read permissions decide which cells they may pull. Defining cells is an admin act; pulling them is self-service within each crew’s existing entitlements.

  
Chapter summary

  
    
    
  • A shared cell is built once and picked up by every covered crew; the base is published-only and crew-neutral, the overlay is personal.
    • 
    
  • Pickup is all-or-nothing: every *:read for the base’s extras, plus territory (when enforcement is on and the crew is scoped). No reduced fallback.
    • 
    
  • Grid helper: ≤ 500 cells, atomic, row 1 at the bottom; size cells under the feature cap.
    • 
    
  • Scheduling: window [start,end) UTC, due = not in flight and last successful enqueue older than cadence; failing builds re-fire every tick. Retention reaps only unheld versions beyond the newest N.
    • 
    
  • Usage reconciles the ledger with the sync inbox per exact version; build-on-behalf can never exceed the target’s own entitlements.
