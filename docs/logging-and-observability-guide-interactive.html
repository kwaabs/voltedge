Stream it.

Every VoltEdge binary writes structured lines to stdout and stops caring. This guide is a working log desk: a pipeline you can trace, a request line you can build, a small log estate you can query with LogQL, a retention calculator driven by the real Loki settings, and an incident drill where a user's failed export has to be found from a symptom.

Operators and administrators running the stack (Docker/Kubernetes/systemd) and anyone diagnosing a production incident. 01

The model: one seam, structured output

Format, level and destination are decided once.

Every VoltEdge binary logs through a single seam, the logx package (api/internal/logx). A binary calls logx.Init() as the first thing in main(); that builds the one logger, installs it as the process default, and every line from then on, whether written through logx or a stray standard-library slog call, lands in the same stream in the same shape. Binaries that call it: the API server (cmd/server), webhookworker, importworker, exportworker, fieldsync and mcpserver.

  1. Structured, not prose. Lines are key-value records (JSON in production). "http request" method=GET status=200 duration_ms=14 is a set of fields you can filter and aggregate, not a string you grep and hope. "Find every request slower than 500 ms" becomes a query instead of a prayer.
  2. The app streams; it does not store. VoltEdge writes to stdout and stops caring. It never opens a log file, rotates one, or offers an endpoint to read logs back. Where logs reside is the platform's job (twelve-factor). Chapter 5 is the whole of "so where do they go?".
  3. OpenTelemetry-compatible names. Fields follow OTel semantic conventions where one exists (http.request.method, url.path, http.response.status_code, user.id). Today it is plain JSON with no OTel SDK; because the names already match, a future OTLP exporter is a one-file change in logx.Init().

1.2 Honest limits of the model

  • Not every container speaks JSON. Only the VoltEdge Go binaries do. Postgres, Martin, RustFS and (in the production-shaped stack) nginx write plain text, and the Go panic stack printed by chi's Recoverer goes to stderr as text. Vector ships all of them, so a | json query shows them with a parse error (Chapter 5, Interactive 8).
  • A summary line says that a request failed, not why: handlers answer errors with writeErr and the message travels in the response body, which is deliberately never logged (Chapter 4).
02

Configuring it 🔒

Two environment variables, and one live control.

🔒 These are process environment variables, set wherever you define each service's environment (compose file, k8s manifest, systemd unit) — the same place DATABASE_URL lives. There are exactly two knobs, read once by logx.Init() at startup:

VariableValuesDefaultEffect
LOG_FORMATjson, textjsonjson = one JSON object per line (for a shipper). text = human-readable (for a developer at a terminal). Anything that is not text (case-insensitive, trimmed) selects JSON.
LOG_LEVELdebug, info, warn, errorinfoMinimum severity emitted; lower is dropped. warning is accepted as warn. An unknown or blank value silently falls back to info — no warning is logged.
Corrected The shipped docker-compose.yml lists no LOG_* variables under any service and uses no env_file, so putting LOG_LEVEL in .env alone does not reach the containers. Add it under the service's environment: (example in Chapter 8). .env.example documents the two variables but leaves them commented out.
Interactive · 3

What does Init() make of my environment?

  • Production: leave LOG_FORMAT at json and keep LOG_LEVEL=info. info carries the request summaries and worker lifecycle; warn/error carry the problems.
  • Local development: LOG_FORMAT=text for readable output.
  • ⚠️ Corrected: debug adds nothing today. A search of api/ finds no Debug log call anywhere (only the level plumbing in logx), so LOG_LEVEL=debug currently emits the same lines as info. The older manual promised "everything"; that becomes true only when someone adds debug statements. If you raise it anyway, do it briefly and put it back, because debug output added later may be sensitive.
  • 💡 There is no per-package level; the threshold is process-wide. "Just this subsystem" is a filter in the backend (Chapter 5).
  • 💡 There is no "off". The quietest level is error.

2.1 What a level keeps

The request summary line's severity follows its status (5xx error, 4xx warn, else info) so the level setting is also a traffic setting: at warn every successful request line disappears. Slide the threshold over a sample minute.

Dropped lines are struck through. Notice that at warn you can no longer see that worker started, or that a 2xx request happened at all, so you cannot compute an error rate from logs alone.

2.2 Changing the level live, from the UI 🔒

LOG_FORMAT and LOG_LEVEL are read once at boot, so changing the format means editing the environment and restarting. The level can also change at runtime, with no restart, at Admin → Logging (/admin/logging; the API is GET/PUT /log-settings).

🔒 Gated on admin:users for both read and write (unlike map-settings): a platform-operations control. Pick a level, press Apply, and it takes effect immediately for the running API server. The choice is validated, persisted first (iam.system_settings, key log_level) and then applied, and it is re-applied at boot over the env default. The handler reads an atomic level variable (logx.SetLevel).

Scope This governs the API server process only. The workers (exportworker, importworker, fieldsync, webhookworker) and mcpserver honour their own LOG_LEVEL and are not changed by this screen.

03
The request log line
One summary line per HTTP request, written when it finishes.

  
The heart of the API's observability is one summary line per request, written by the middleware in api/internal/httpx/logger.go (it replaces chi's plain-text logger). It is the outermost middleware (r.Use(httpx.Logger(rootLogger)) is first in cmd/server/main.go), so even requests rejected later with 401 or 413 get a line and an id. It is emitted at the end, because only then can it see the user the session middleware attached downstream.

  

    
FieldMeaning

    
request_idCorrelation id: 16 hex characters from 8 random bytes (fallback: a timestamp-based id prefixed t). Also the X-Request-Id response header.

    
http.request.methodGET, POST, …

    
url.pathThe path only, never the query string (Chapter 4). Behind the production-shaped nginx the /api prefix has already been stripped (rewrite ^/api/(.*)$ /$1), so you see /export/, not /api/export/.

    
http.response.status_codeThe status actually written (200 if the handler never called WriteHeader).

    
http.response.body.sizeResponse bytes

    
duration_msWall-clock milliseconds to serve (int64)

    
client.addressThe transport peer IP, port stripped (§3.2)

    
user.idOpaque id of the authenticated user, when there was one (§3.3)

  

  
Severity tracks the status: 5xx → error, 4xx → warn, else info. Your backend can alert on error lines without comparing the status field. The message is always http request; slog prefixes time, level and msg, and request_id comes right after because it is attached to the request-scoped logger.

3.1 The correlation id — the single most useful field

  
Every request is minted a random id that travels two ways: into the logs as request_id (on the summary line and every handler or engine line written while serving that request, because the request-scoped logger carries it down the call stack), and back to the client in the X-Request-Id response header. When Owen is handed a screenshot of an error, that header is the thread that pulls the whole server-side story out of the logs. 💡 Surface X-Request-Id in client error messages or frontend error reports so the link is always available.

  
Limits The id is generated per request in the API; it is not read from an incoming X-Request-Id, so an id minted by a proxy will not match. Worker and background lines do not carry a request_id: they use their own job id (Chapter 6). The job id of an export is returned to the client in the 202 response body ({"job_id": …}), which is not logged.

  
3.2 client.address behind a proxy

  
client.address is the transport peer (r.RemoteAddr) with the port stripped, deliberately not X-Forwarded-For, which any client can forge. ⚠️ Behind a reverse proxy it is the proxy's IP. The production-shaped stack puts nginx in front, sets X-Real-IP and X-Forwarded-For on every upstream request, and the API does not mount middleware.RealIP today, so every line shows nginx's container address. Mounting chi's RealIP ahead of the logger fixes that, but read the rules before you do.

3.3 user.id and nothing more

  
When a request is authenticated, a small middleware placed right after auth.SessionLoader adds only the user's opaque id to a pointer-carried attribute bag that the outer logger reads at the end. Email and display name are kept out. The id answers "who did this?" against iam.users without spilling personal data. An anonymous request simply has no user.id.







  
04
What is deliberately not logged
Audit-grade, but privacy-aware.

  
The following never appear in a log line, by design:

  
    
    
  • The query string. Only url.path is logged; query parameters can carry tokens, search terms or other sensitive values.
    • 
    
  • Request and response bodies. This includes error messages: writeErr puts the reason in the response body, so a 500 summary has no cause on it. Get the text from the user's screenshot, or from the job's stored error column for background work.
    • 
    
  • Authorization headers, cookies, CSRF tokens, API tokens.
    • 
    
  • User PII. Email and display name stay out; only the opaque user.id identifies the actor.
    • 
  

  
⚠️ This is a contract to preserve when you add logging: log the user id, the path, never a body "just to debug". The value of "audit-grade" collapses the first time a credential lands in an aggregator a wider audience can read. Paste a candidate line or log statement below.

05
Where the logs go, and how to read them 🔒
The app streams; the platform decides the rest.

  
5.1 Out of the box: Docker's json-file driver

  
No logging driver is configured in docker-compose.yml, so Docker uses json-file. Read with docker logs voltedge-api (add -f to follow) or docker compose logs -f api. corrected Container names carry the voltedge- prefix (container_name: voltedge-api), so the older manual's docker logs api fails; the Compose service name works with docker compose logs api. In the production-shaped file, scaled services (api, workers) have no fixed name, so use docker compose -f docker-compose.prod.yml logs api.

  
Ephemeral and local Tied to the container, lost when it is removed, not centralised, not searchable across services, and growing on the host disk until something rotates it (no max-size is set). Fine for development; not an observability solution.

  
Because the output is JSON you can pipe it through jq. corrected Keys contain dots, so each must be quoted; the old {url.path, …} object shorthand is a jq syntax error.


docker logs voltedge-api | jq 'select(.level=="ERROR")'
docker logs voltedge-api | jq 'select(.request_id=="a1b2c3d4e5f6a7b8")'
docker logs voltedge-api | jq -c 'select(.duration_ms > 500) | {path: ."url.path", duration_ms, status: ."http.response.status_code"}'

  
Non-JSON lines (Postgres, a panic stack) make plain jq stop with a parse error; use jq -R 'fromjson? | select(.level=="ERROR")' to skip them.


  
5.2 For real: ship to an aggregator

  
For anything beyond one box, run a shipper that tails each service's stdout into a store you can search, dashboard and alert on: Vector (collector) → Loki (store) → Grafana (UI). The lines are already JSON with stable names, so Vector forwards the body untouched with two labels, and everything else is parsed at query time with | json.

  
Opt in with one overlay (docker-compose.observability.yml; configs in infra/). Set a read token first, because the proxy refuses to start without one:


LOKI_READ_TOKEN=$(openssl rand -hex 32) \
  docker compose -f docker-compose.yml -f docker-compose.observability.yml up -d

  
Production-shaped stack: docker compose -f docker-compose.prod.yml -f docker-compose.observability.yml up -d. Grafana is at http://localhost:3708 (GRAFANA_PORT), the Loki data source pre-wired. Images are pinned: Loki 3.3.2, Grafana 11.4.0, Vector 0.44.0-alpine, Caddy 2.8-alpine.

  
Which containers does Vector take, and what are they called?

  
The rule is two lines of vector.yaml: include containers whose label com.docker.compose.project=voltedge, exclude voltedge-loki, voltedge-vector, voltedge-grafana; the service label is the container name. Everything follows from that.

5.3 The one rule: don't build a log endpoint 🔒

  
⚠️ External access to logs is the aggregator's job, governed by its access control, never an application API. A GET /admin/logs route would mean re-implementing a log store, retention and RBAC inside VoltEdge, badly, and widening the blast radius of any auth bug. The boundary is: the app streams, the platform ships, and Loki/Grafana (or equivalent) enforces who may read, with its own authentication. (The one log-related app route, /log-settings, changes verbosity; it returns no log lines.)

  
5.4 Retention, volume and cost 🔒

  
The shipped Loki is a single binary on the filesystem: retention_period: 168h (7 days, to match the export/attachment defaults), compactor retention_enabled: true, TSDB schema v13 with a 24 h index period, ingestion_rate_mb: 16, ingestion_burst_size_mb: 32, reject_old_samples: false. Estimate what your traffic costs.

06
Worker and background-job logs
Same structure, a job id instead of a request id.

  
The HTTP request line is the API's story; the workers (the out-of-band cmd/ processes) tell theirs the same structured way. Each long-running worker builds a logger tagged with its identity and threads it through the job, so a line can always be traced to which worker and which job:

  
    
    
  • worker — the family. corrected Seven values exist: webhook, webhook-outbound, import, export, fieldsync, sync, attachment-sweep (the older manual omitted webhook-outbound).
    • 
    
  • worker_id — the process: hostname-pid. In a container the hostname is the container id, so two replicas are distinguishable. (The attachment sweep carries worker but no worker_id, and so do the "ignoring invalid env var" warnings printed while reading configuration.)
    • 
    
  • A per-job id — delivery_id (webhook and webhook-outbound; the latter also adds event_type), job_id (import, export), pack_id (fieldsync build), op_id (sync apply). Every line a job emits carries it, so one job's trail filters out exactly like a request_id.
    • 
  

  
Which binary hosts which family: webhookworker runs webhook and webhook-outbound; exportworker runs export plus the attachment-sweep; fieldsync runs fieldsync (pack builds) and sync (applying device edits) plus its maintenance loop; importworker runs import. The dev docker-compose.yml has services for exportworker, fieldsync and mcpserver only; webhookworker and importworker appear in docker-compose.prod.yml (and task webhookworker-dev for the former).

6.1 What a worker does and does not log

  
A worker logs worker started at boot (with its concurrency and lease), an error on a failed claim, heartbeat failed, a warn on a lost lease, a panic with its stack, and the exceptional "recording … failed" cases. corrected The ordinary outcome of a job is not a log line: an export or import that fails normally records its reason in the job row (ops.export_jobs.error, shown in the app) and is silent in the logs. The exceptions are fieldsync's pack built (info, with counts and elapsed_ms) and the maintenance/retention lines (scheduler: enqueued rebuild, maintenance: reaped versions, sweep reaped deleted attachments). So to learn why a job failed, read the job's error field first, then use the logs to see panics, lease loss and infrastructure errors.

  
The binaries that install the structured logger are the API server, webhookworker, importworker, exportworker, fieldsync and mcpserver. corrected Boot-time fatals such as a missing DATABASE_URL run after logx.Init(); Go's slog.SetDefault routes the standard log package through the handler at info level, so the final line is an info-level JSON object and — with LOG_LEVEL=warn or error — the process exits with no message at all. (Verified with a Go test program using the same pattern.)

  
Tip To watch one webhook delivery end to end, filter on its delivery_id; to audit a field-sync apply, filter on op_id. Pick the id, get the whole trail.







  
07
Diagnosing an incident, end to end
Two ids and a time window.

  
Owen gets: "the export failed for user X at about 14:05 with a strange error." The method:

  
    
    
  1. Client error with X-Request-Id? Filter the API logs on that request_id. Every line the request wrote appears, in order, with user.id, url.path and the final status. Remember the line shows that it failed; the reason text was in the response body, so ask for the screenshot text too.
    2. 
    
  2. Background job (export, webhook)? Move to that worker's logs and filter on the job id. The enqueue response returns it ({"job_id": …}) but the API does not log it, so lacking the id, use the user.id and the time window on the API side, then look for worker lines in the same minutes. Also read the job's stored error (the Exports list in the app).
    3. 
    
  3. Correlate across services. The API line that enqueued the job and the worker line that ran it are close in time; the aggregator lines them up. Workers do not carry user.id, so the bridge is time and the job id.
    4. 
    
  4. Trail too thin? corrected Raising LOG_LEVEL to debug adds nothing today (no debug statements exist). Widen the time window, search the other services, read the job row, and only then consider adding targeted logging in code.
    5. 
  

  
The whole method rests on request_id for the synchronous path and the per-job id for the asynchronous one, plus structured fields that make "this, within that window" a query rather than a scroll.

7.1 Alerting on the signal

  
Severity tracks status exactly so you can alert without parsing it: count error-level API lines, the share of 5xx, slow requests, worker errors, or silence. The repo provisions only the Grafana data source (infra/grafana/provisioning/datasources/loki.yaml); no dashboards or alert rules ship, so you author them in Grafana. Loki's ruler directory is configured but no Alertmanager URL is, so use Grafana-managed alerts (not verified end to end here). Design a rule and replay it over the estate's twenty minutes.

8.2 Quick reference

  
Configuration. LOG_FORMAT = json (default) | text. LOG_LEVEL = info (default) | debug | warn | error. Set them in each service's environment. The API server's level can also be changed live at Admin → Logging (admin:users), which persists and survives a restart; format and the workers' levels stay env-only.

  
Key fields. request_id (also the X-Request-Id response header) · http.request.method · url.path · http.response.status_code · http.response.body.size · duration_ms · client.address · user.id. Workers add worker · worker_id · job_id/delivery_id/op_id/pack_id.

  
Severity by HTTP status. 5xx → error · 4xx → warn · else info. Never logged. Query strings · request/response bodies · auth headers, cookies, tokens · user email/display name.

  
Reading logs. Dev/single box: docker logs voltedge-api (JSON; pipe through jq). Production: ship stdout through Vector → Loki → Grafana (the repo ships Vector; Promtail is mentioned in the older manual but is not provided). Never expose logs through an application endpoint.

  
Behind a proxy. client.address is the connection peer, not X-Forwarded-For. Mount chi middleware.RealIP ahead of the logger only behind a proxy that overwrites every forwarded header it reads (True-Client-IP, X-Real-IP, X-Forwarded-For).
