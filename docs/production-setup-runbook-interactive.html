Install.
Verify. Upgrade.

The order of a production install is not a matter of taste: every step leaves the next one something to stand on. This edition lets you reorder the steps and see what breaks, size the PgBouncer pool, check an .env against what docker-compose.prod.yml actually passes to the containers, replay the 135 real migrations, and probe the health check the way Docker does.

Use As in the top bar. Priya (Platform admin) can do everything. Omar (On-call) can scale, back up and read. Dev (Developer) can build and run migrations/seeds. Alma (Auditor) is read-only. These are operator roles, a modelling device: the product’s own roles (viewer, analyst, editor, supervisor, admin, break-glass-admin, field-*) appear in chapter 5.

Who this is for

The operator deploying VoltEdge with the multi-replica stack (docker-compose.prod.yml + infra/nginx/nginx.conf). It is the how-to-install; its companion Production Deployment & Scaling is the why. Assumed: Docker Engine + Compose v2, the repository checked out on the host, and Node.js to build the SPA. Throughout, PC is shorthand for docker compose -f docker-compose.prod.yml; set it once: PC="docker compose -f docker-compose.prod.yml".

Read this before trusting any older copy of the runbook. The code and compose file disagree with it in a few places that matter (the .env variables that never reach the containers, the nginx host port, the /s3/ proxy idea, the migrate-verify command). They are fixed in the Markdown and listed in the Corrections table in chapter 10. Statements this edition could not confirm from the repository are marked not verified.

01

What you are standing up

One image, many commands; one front door; one stateful database.

nginx (:80/:443 in the design; published as WEB_PORT=3710 -> :80 by default)
  serves the SPA + proxies /api and /tiles
  -> N api replicas (stateless)
       -> PgBouncer (transaction pool)
            -> Postgres (PostGIS)      [+ optional read replicas]
  workers: exportworker, webhookworker, importworker, fieldsync (scale by replicas),
           mcpserver
  rustfs (S3-compatible object storage for attachments/exports)
  bootstrap (one-shot sidecar: psql + migrations; does nothing until exec’d)
  martin (legacy tile server, still started by up -d)

The API image (api/Dockerfile) bakes every binary you need — server, exportworker, webhookworker, importworker, mcpserver, and the ad-hoc authadmin / resetdata admin tools — and the compose service picks which to run via its command. So $PC exec api authadmin … runs the admin CLI with the API’s exact environment. fieldsync is the exception: it has its own image (api/Dockerfile.fieldsync, which bundles tippecanoe). Click a service; flip the view to see which host ports are published and which services --scale can actually fan out.

02

Prerequisites, sizing & secrets

Hardware, DNS/TLS, and an .env that actually reaches the containers.

2.1 Prerequisites & host sizing

  • Docker Engine + Compose v2, a host (or VM) with headroom. A sane single-host start for a few hundred users: 8 vCPU / 16 GB RAM / SSD. Postgres and the api replicas are the CPU/RAM consumers; give Postgres the bulk. (For ~1,000 users Postgres and the replicas move off one host — see the scaling guide.)
  • The repository on the host (compose files, infra/, migrations/, seed/, web/).
  • Node.js on the host (or a CI step) to build the SPA in chapter 3.
  • A DNS name + TLS certificate for the public URL (chapter 7). Secure session cookies require HTTPS — not optional in production.

Postgres is started with max_connections=200, sized for PgBouncer’s server pool plus replication plus headroom — not raw clients. That number is fixed in the compose file; PgBouncer’s knobs are the ones in .env. The app’s own pool is unbounded (the server sets no SetMaxOpenConns), so PgBouncer is what stops N replicas from exhausting the database. Try the arithmetic:

PgBouncer pool budget & queueing

Assumptions are yours to set: connections per replica and transaction time are not in the repository. The pool limits (DEFAULT_POOL_SIZE 25, RESERVE_POOL_SIZE 5, MIN_POOL_SIZE 5, MAX_CLIENT_CONN 1000) and max_connections=200 are read from the compose file. 2.2 Secrets & environment (.env)

Compose reads .env from the repo root. Copy the template and harden every value — do not ship the dev defaults:

cp .env.example .env
Read this twice. .env only feeds ${...} substitutions inside the compose file. docker-compose.prod.yml has no env_file:, and the api service passes through only DATABASE_URL, PORT and RUSTFS_*. So AUTH_INSECURE_COOKIES, SESSION_*, OIDC_*, EXTERNAL_SYSTEMS_ENCRYPTION_KEY, LOG_FORMAT/LOG_LEVEL, RUSTFS_PUBLIC_USE_SSL and others written to .env never reach the container until you add them to the service’s environment: block. The builder below marks each variable and prints the lines to add.

SSO (optional): to enable Azure AD / Google, set the OIDC_* block (and pass it through to api). A provider is enabled only when its variables are set and discovery succeeds at startup; otherwise it is silently absent from the login screen. The redirect URL registered with the provider must be https://<your-host>/api/auth/oidc/<provider>/callback (note the /api prefix — nginx strips it to the backend’s /auth/oidc/...). Build the images and the SPA

Know which binary lives in which image before you reach for a command.

3.1 Build the images

$PC build

This builds the API image (all binaries), the fieldsync image (bundles tippecanoe) and the bootstrap sidecar image (infra/gitbash). The nginx, postgres, pgbouncer, rustfs and martin images are pulled. Note that pgbouncer and rustfs use :latest tags and postgres is pinned to supabase/postgres:15.8.1.049.

Admin tooling lives in only some images. Ask where a command can run:

3.2 Build the web SPA

The React app is a static bundle nginx serves; the backend does not serve it. Its API base is hard-wired to /api (web/src/lib/api.ts), so no build-time env is needed — nginx maps /api and /tiles to the backend.

cd web
npm ci
npm run build        # runs "tsc -b && vite build"; produces web/dist
cd ..

docker-compose.prod.yml mounts ./web/dist into the nginx container read-only. Rebuild the SPA whenever the frontend changes; $PC restart nginx is the safe habit (files are served from a bind mount, so a restart should not be strictly needed — not verified). If you prefer a CDN/separate static host, drop that mount and point the host’s /api + /tiles at the API instead.

Build the SPA before the first up. If ./web/dist does not exist when nginx starts, Docker creates an empty directory for the bind mount and nginx serves 404 for everything. Chapter 10: “SPA loads but every call 404s”.

Data tier & database

Bring up the data tier first, migrate before any API replica connects, then load schema and seed data.

The whole install is one ordering problem. Before the individual steps, reorder them yourself: drag nothing, just use the arrows and skip toggles, and read what the dependency rules say would break. Each rule is a fact about this repository (cited in the verdict).

Interactive · 6

Step order — “what breaks if you skip or reorder”

4.1 Start the data tier first

Bring up Postgres, the pooler, object storage and the bootstrap sidecar — but not yet the app — so you can migrate before any API replica connects:

$PC up -d postgres pgbouncer rustfs bootstrap

Wait for Postgres healthy: $PC ps should show voltedge-postgres healthy (pg_isready -U postgres every 5s, up to 10 retries). The voltedge-exports bucket (RUSTFS_BUCKET) is created on boot by api, exportworker, importworker and fieldsync if missing — no manual bucket step; if RustFS is not yet reachable at that moment the API only logs a warning and exports fail until it is.

rustfs has no healthcheck, and api only waits for it to be started, not ready. bootstrap waits for Postgres to be healthy and then just sleeps (restart: "no").

4.2 Apply migrations

The bootstrap sidecar has psql + the repo mounted at /workspace and connects directly to Postgres (not through PgBouncer — DDL wants a stable session):

$PC exec -T bootstrap bash /workspace/migrations/apply.sh

Verify (the DATABASE_URL must expand inside the container, hence the single quotes):

$PC exec -T bootstrap bash -c 'psql "$DATABASE_URL" -c "SELECT filename, status FROM ops.migration_log ORDER BY id;"'

apply.sh walks every *.sql in migrations/ in filename order, skips any already in ops.migration_log, runs the rest with psql -v ON_ERROR_STOP=1 -f, then records filename, the -- Purpose: header line and a SHA-256. There are 135 files (two share the 0060 prefix; both run, alphabetically). Only 14 of them contain a BEGIN; psql -f is not run with --single-transaction. Replay it:

4.3 Load the schema + seed data

  
Two honest paths — pick by whether this is your first environment or a promotion:

  
    
    
  • Greenfield (first environment ever): the full metadata + compiled schema is produced by the authoring flow task migrate + task seed-all. seed-all runs 114 ordered steps: 100 metadata/config seeds (class metadata, fields, symbology, templates, CIM mappings), then compile-all (materialises every class into its gis.<code> table), then 13 instance/network seeds. It is idempotent (ON CONFLICT-guarded) and is a one-time authoring activity. Run it against a staging stack, verify, then dump it — do not hand-run them against production. The Taskfile targets use the dev compose’s gitbash service and go run (the prod images do not contain compile).
    • 
    
  • Production (the normal path): restore a validated dump of the staging/reference database (schema + metadata, plus whatever reference data you want pre-loaded):
    • 
  

  
# on staging, after task seed-all + verification:
pg_dump "<staging-dsn>" -Fc -f voltedge-seeded.dump

# into production (through the bootstrap sidecar or any psql host):
pg_restore --no-owner -d "<prod-dsn>" voltedge-seeded.dump

  
Then re-run 4.2 so any migrations newer than the dump are applied forward. The bootstrap container mounts the repo at /workspace, so a dump written there lands in your checkout — keep it out of git. Whether pg_restore --no-owner works cleanly with the supabase role/extension layout was not verified; rehearse it on a scratch database.

  
This mirrors how utilities actually provision: build + validate the model once, restore it, then roll migrations forward on every upgrade (chapter 8).

05
Create the first break-glass admin
One command, one password that never touches disk, one policy switch that defaults to off.

  
authadmin is baked into the API image; run it with the password passed just-in-time (never stored):

  
$PC exec -e AUTHADMIN_PASSWORD='<a-strong-password>' api \
  authadmin create --email admin@utility.com --name "Break-glass Admin"

  
Defaults from the source: --break-glass is true and --role is admin (pass --role "" to assign none). The password comes from AUTHADMIN_PASSWORD only — there is no password flag. Grant roles / list accounts the same way: $PC exec api authadmin list, $PC exec api authadmin grant-role --email <e> --role <role> (authadmin roles lists them). SSO users are pre-provisioned by email before their first login. For an AI/MCP integration token: $PC exec api authadmin mint-token --email <e> --name <label> (printed once; optional --ttl 720h, default no expiry).

  
Why break-glass matters on day one: the migration seeds iam.system_settings.local_auth_enabled as false. With it off, only break-glass accounts may sign in with a password; everyone else is refused until an administrator turns local sign-in on (or SSO is configured). 06
Start the application tier
One command, then scale; and the part everyone forgets — the browser talks to RustFS directly.

  
$PC up -d                      # brings up api (×API_REPLICAS), workers, nginx, mcpserver, fieldsync (and martin)

  
Scale on demand:

  
$PC up -d --scale api=6 --scale exportworker=3

  
(fieldsync can scale by replicas too in principle — its build and sync workers both claim work with SKIP LOCKED and build in isolated temp dirs. Scale it on pack-build backlog, with CPU-heavy pods for tippecanoe. In this compose file it runs one instance by choice: it has a container_name and a fixed published port, so to scale it you drop both and front it with nginx like the api tier. One caveat: its shared-pack maintenance loop runs in every replica, so a scheduled cell rebuild can be harmlessly double-enqueued — retention reaps the extra, or leader-elect that loop to avoid it.)

  
A depends_on reminder: api waits for pgbouncer and rustfs to be started only. Nothing in the file waits for a service to be healthy except pgbouncer, martin and bootstrap (on Postgres).

  
RustFS public reachability (don’t skip)

  
Attachments and exports are uploaded and downloaded by the browser directly to RustFS via presigned URLs. The browser must be able to resolve and reach RUSTFS_PUBLIC_ENDPOINT. The API process talks to rustfs:9000 internally but signs URLs for the public endpoint, offline, with no network round trip. Either publish RustFS on a public host with TLS (and set RUSTFS_PUBLIC_ENDPOINT + RUSTFS_PUBLIC_USE_SSL=1 — the latter needs the compose pass-through from chapter 2), or terminate TLS in front of RustFS on a dedicated host name and point the public endpoint at that host. If presigned downloads 404 in the browser, this is almost always why.

  
Correction to the old advice. An nginx location /s3/ with a path-prefixed public endpoint cannot work as written: the endpoint setting is host[:port] only (it is handed to the S3 client as an endpoint, which has no path component), and a SigV4 presigned URL is signed for a specific Host. Proxy RustFS from its own server block / host name, forwarding the original Host. Not run end to end here (not verified).

TLS, the nginx edge & the login brakes
Secure cookies need HTTPS; nginx decides where a path goes and who gets throttled.

  
7.1 TLS

  
Secure cookies (and therefore login) require HTTPS to the browser. Two options:

  
    
    
  • Terminate at an external LB / proxy (cloud L7 LB, Caddy, Cloudflare) in front of nginx:80. Simplest; the LB holds the cert.
    • 
    
  • Terminate at this nginx: uncomment the "443:443" port line in the compose file, mount your cert/key, and add a TLS server block (and redirect :80 → :443). Keep the /api, /tiles, and SPA locations identical. The shipped nginx.conf has only a plain listen 80 server.
    • 
  

  
Either way, confirm AUTH_INSECURE_COOKIES is unset/0 (chapter 2) and that the browser reaches the app over https://.

7.3 The login brakes

  
Three independent limits sit in front of a password guess. 1) nginx limit_req zone=login on exactly /api/auth/login: rate=5r/s, burst=10 nodelay, keyed on $binary_remote_addr, excess answered 503. 2) the app’s per-IP limiter: 10 requests burst then 10/minute, per replica, answering 429 with Retry-After: 60, keyed on the TCP peer (it deliberately ignores X-Forwarded-For). 3) the account lockout: 5 consecutive failures lock the account 15 minutes. Because the app sees only nginx as its peer, every user shares each replica’s bucket; and if an external LB sits in front of nginx, nginx’s own key is the LB’s address, so the edge bucket is shared by everyone too (no real_ip module is configured — the config shows none). 8.1 Observability (optional but recommended)

  
Layer the opt-in Loki + Grafana + Vector overlay on top (see the Logging & Observability guide):

  
LOKI_READ_TOKEN=$(openssl rand -hex 32) \
  $PC -f docker-compose.observability.yml up -d

  
Grafana comes up on GRAFANA_PORT (default 3708); external log consumers go through the bearer-token proxy (Caddy) on LOKI_PROXY_PORT (default 3709). Loki itself is not published. Vector reads container logs through the Docker socket and labels each stream with the container name (service) and project=voltedge. Set the alerts from §11 of the scaling guide (DB connection saturation, replication lag, tile p95, worker queue depth).

8.2 Upgrades (zero-downtime)

  
Because the API tier is stateless and the schema changes are additive-first, you can roll forward without downtime:

  
    
    
  1. Build the new image + SPA (chapter 3).
    2. 
    
  2. Apply migrations first, once, via the bootstrap sidecar (4.2). They are backward-compatible with the currently-running image (the compiler’s additive-nullable pattern guarantees old replicas keep working).
    3. 
    
  3. Roll the API tier: $PC up -d --no-deps api recreates replicas on the new image. With API_REPLICAS ≥ 3, drop one at a time (or use a rolling strategy) so there is always a healthy replica. nginx.conf defines no health checks of its own: it re-resolves api every 10 s through Docker DNS (valid=10s), so a removed replica can be tried for up to that long. How Compose orders the recreation was not verified.
    4. 
    
  4. Roll the workers: $PC up -d --no-deps exportworker webhookworker importworker mcpserver fieldsync.
    5. 
    
  5. For a breaking schema change, use expand → migrate → deploy → contract across two releases (never expand and contract while old replicas overlap) — see §10 of the scaling guide.
    6.

Backups, DR & verifying the deployment
A backup you have never restored is a hope, not a backup.

  
9.1 Backups & DR

  
    
    
  • Postgres: scheduled pg_dump -Fc at minimum; for real RPO use continuous archiving / PITR (a Postgres operator — CloudNativePG/Zalando — gives you this plus replica failover; strongly recommended once you add read replicas). The compose Postgres already runs wal_level=replica, 10 WAL senders and 10 replication slots, so it is replication-ready; nothing here configures archiving.
    • 
    
  • RustFS/object storage: back up or replicate the bucket — attachments and exports live only there, not in Postgres. The data sits in the rustfs_data volume (and Postgres in postgres_data); $PC down keeps both, down -v deletes them.
    • 
    
  • Test a restore. A backup you have never restored is a hope, not a backup.
    • 
    
  • The break-glass factory reset (resetdata) is a destructive maintenance tool, not a backup; keep RESETDATA_PASSWORD out of .env.
    •
