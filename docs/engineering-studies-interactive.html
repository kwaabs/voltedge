Network Analysis:
how features become maths

Every study — load flow, fault, hosting, EV headroom — runs over one shared model: your connected features, read as a graph. Understand that model and you understand all seventeen studies. Drive the voltage profile yourself below.

▶ Planner — what it means & when to run it ∑ Engineer — the model & equations
01

Your features become a graph

A study doesn't look at a map. It looks at the connectivity graph.

▶ When you run a study, VoltEdge ignores the map. It reads the connectivity graph: every feature is a node, every committed electrical connection is an edge. You nominate one start feature — the source — and the engine walks outward along power flow, away from the source, following connections until it runs out of network or hits something that stops it.

02

The radial tree & its barriers

One path to every point — and open devices stop the walk.

▶ The fast load-flow and fault engines assume the network downstream of your start is radial — a tree, where power reaches every point by a single path. Real distribution is almost always run radially (rings exist but are run open at a tie), so this is usually exactly right. Two things shape the tree:

A loop → it stopsa point reachable two ways isn't radial. The engine names the feature and refuses rather than guess a path. (Use the meshed/nodal engine for loops.)
An open device → a barrieran open switch/cutout/link box de-energises everything beyond it, so the walk stops there and records a barrier hit. An open ring becomes two radial feeders.
∑ Barriers are data, not code

"Radial" is enforced in buildTree: reach an already-visited node by a second path and the radial callers abort with an invalid error. Barriers load the DOWNSTREAM_TRACE config's own trace_barrier_rules — the same rows the downstream trace uses (DIST_SWITCH, SERVICE_CUTOUT, LV_LINK_BOX on device_state = OPEN) — checked live against each feature's current attributes on every run, never baked into a stored graph. The one override: a node the contingency study hypothetically closed (a normally-open tie) isn't treated as a barrier for that run — in memory only, never touching committed connectivity.

💡 If a study fails with "not radial (loop/mesh detected)", run the LOOP_CHECK_TRACE to find and open the loop — or switch to the meshed/nodal engine (the markdown guide, Chapter 3).

03

What a node contributes

Load, generation, or both — resolved to one net injection.

Loada demand: demand_kw + power_factor. A SERVICE_POINT at 100 kW, 0.95 pf is the common case.
−
GenerationPV, a diesel set, a battery: modelled as negative load — it injects power, lifting local voltage, reducing upstream flow.
=
Net injectiondemand − generation. A rooftop-PV-behind-a-meter nets the two; a pure generator ends up negative.
∑ How each resolves

Load → (P, Q) from demand_kw and power_factor: Q = P · tan(acos(pf)), with pf defaulting to unity (Q = 0) when unset/invalid — the load is kept, not discarded. Generation → an injection from dispatch_kw (authoritative even at 0 — a curtailed unit injects nothing), falling back to the rated_kw nameplate, at the unit's power_factor. The backward pass carries a negative own-kW up the tree as reduced upstream flow; the forward pass reads it as a local voltage rise — the same negative-demand model the hosting-capacity study uses for a candidate DER.

⚠️ A generator's fault contribution is separate (fault_contribution_ka, subtransient_reactance_pct) — a generator is a load-flow injection and a second fault source, modelled independently (Chapter 4 of the markdown guide).

▶ Smart EV charging is a special load

A charging site's coincident demand is its installed charger load, diversified, then clamped to a managed cap: effective_kw = min(managed_demand_cap_kw, connected_load_kw × diversity_factor). That's a whole topic — see the dedicated EV Charging interactive guide for the calculator and the feeder-headroom study.

04

Transformers — where voltage changes base

Report a drop against 415 V, not against 11 kV.

▶ A transformer does two things to a study: it changes the voltage base (an 11 kV/415 V unit means everything below it is analysed at 415 V), and it drops some voltage through its own impedance under load. VoltEdge reads both from the nameplate — the primary/secondary voltages give the ratio, the impedance-percent plus the rating give the through-impedance.

∑ The two-winding model

From primary_voltage (a coded VOLTAGE_CLASS, parsed — "11KV" → 11000), secondary_voltage, impedance_pct, and x_r_ratio (default 2.0). Ratio = secondary/primary × tap factor (1 + tap_position·tap_step_pct/100). The series impedance referred to the secondary:

Z_base  = secondary² / S_rated   (per-phase ohm)
Z_series = (impedance_pct / 100) × Z_base
R = Z_series / √(1 + XR²),  X = R · XR

Rating from rated_kva (distribution) or rated_mva (power, ×1000). Three-winding units (a tertiary_voltage turns the model on) resolve to a star equivalent (three arms meeting at a point); the vector_group (default Dyn) is read only by the ground-fault calc — the balanced load flow ignores it.

The transformer — not the cables — is usually where most of a feeder's drop happens. The widget in Chapter 5 shows it.

05

The voltage profile

The study you run most — drive it yourself.

The everyday study answers two questions: "is the voltage acceptable at the far end?" and "is anything overloaded?" — both from one radial forward-backward sweep. The widget below is that sweep on the guide's micro-feeder: source → MV cable → a 315 kVA 11 kV/415 V transformer → LV cable → a service. Each node is plotted in per-unit against its own base, so the 11 kV and 415 V halves share one chart; the green band is the ANSI C84.1 0.95–1.05 range.

∑ The sweep, exactly

Backward pass walks the tree in reverse (every child before its parent), setting each node's cumulative power to its own net plus its children's. Forward pass runs a fixed 3 iterations (not a convergence loop — at distribution drops, three passes over-converge), each re-measuring a branch's ΔV against the previous pass's sending voltage:

ΔV (volts) ≈ (P·R + Q·X) / V

The start node absorbs the source impedance against total demand; a conductor drops across its resolved impedance; a transformer rebases to parent_voltage × ratio then drops on the secondary base; a junction is a pass-through. Branch current I = S/V, and a conductor over its ampacity (or a transformer over its kVA) is flagged overloaded in the same pass. The load flow and the voltage profile run this identical sweep — the profile just adds the band check and loss summary, at no extra solve cost.

06

Graceful degradation

Missing data degrades the answer — it doesn't fail the run.

▶ Real networks are never fully surveyed. Every study follows one rule: a missing value becomes a documented assumption, not an error. And the result tells you when a value was assumed rather than resolved — so you know which numbers to trust and which to go survey.

Missing……is treated as
a conductor's material / resistancedrops nothing (resolved = false)
a transformer's impedance percentan ideal ratio (no series drop)
a transformer's X/R2.0
a load's power factorunity (Q = 0)
a generator's dispatchits nameplate rated_kw
the source impedanceideal / infinitely stiff
a zero-sequence impedance3× positive (conductor) or Z0 = Z1 (transformer/source), flagged estimated

💡 Your first run on a new feeder is often "optimistic" — no drops, no losses. That's not a bug; it's the signal to send Dana out to survey the transformer and conductor nameplates. Results carry a material_resolved flag per node, so a client can tell "0 % drop because stiff" from "0 % drop because unsurveyed."

07

Anatomy of a run

Five steps, nothing written to the database.

1 · Resolve startthe start feature exists and isn't deleted
→
2 · Build treewalk downstream, honour barriers, reject loops
→
3 · Resolve statesload each feature once; read its electrical inputs
→
4 · Solvebackward pass (accumulate), forward pass (drop voltage)
→
5 · Formatshape the answer the study asked for

∑ The shared core is runSweep; nothing in the sequence writes to the database. The query-heavy work (walk the tree, load every node) happens once — which is why a capacity search can run dozens of trial sweeps in memory, and why two studies can share one solve (the load flow and the voltage profile are the same sweep, formatted differently). Every result panel also carries a collapsible "How this was calculated" strip that restates, from the run's own figures, the worst node and the binding constraint — so the explanation travels with the number.

Resolve once, sweep many, write nothing. That one discipline is why every study over your live data is fast and side-effect-free.
