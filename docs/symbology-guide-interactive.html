01

How symbology works

Two tables, a client-side matcher — and nothing baked.

This chapter builds the vocabulary the rest of the guide assumes, and answers the single most common confusion up front — the one that sends people restarting services that have nothing to do with the problem. If you only ever remember one thing: a symbol is chosen in your browser, per feature, from rules the server hands down — nothing is “baked” and no picture is stored.

1.1 ▶ The problem symbology solves

Priya opens the map. She can see conductors and transformers, but the ring main units her team just surveyed are invisible — or worse, they are all identical grey dots she can’t tell apart from anything else. She pings Ada: “Can you make the RMUs actually look like RMUs?” That request — “make this kind of feature look like that” — is the whole of symbology. Every feature in VoltEdge is stored as plain geometry plus attributes. None of that says anything about appearance. Symbology is the configuration that sits on top and says: when you draw an RMU, draw it as this little square icon in copper; when you draw an MV_CONDUCTOR that is underground, draw it as a dashed line.

Ada owns that configuration. She never edits Priya’s features to change how they look — she edits the rules that decide how a whole class is drawn. Do it once, and every ring main unit — the thousand already on the map and the next one Dana places tomorrow — wears the symbol automatically.

1.2 ∑ Two tables, two different jobs

Here is the fact that trips up almost everyone the first time: symbology is two separate things, in two separate tables, and doing only the first one renders nothing.

TableWhat it holdsThe analogy
metadata.symbology_iconsNamed pieces of SVG artwork: icon_ref → markupA library of stamps. A stamp on the shelf marks nothing.
metadata.symbology_rulesWhich style (which icon, colour, size…) applies to which featureThe instruction “stamp this stamp on every RMU”
The number-one mistake
Uploading an SVG to the icon library and expecting it to appear on the map. It won’t — you have created a stamp but never told anything to stamp it. You need both an icon and a rule that references it. Chapters 2 and 3 are exactly those two steps, in order.

Why split them at all? Because the two jobs change independently. You can redraw what a symbol looks like (edit the icon markup) without touching a single rule about where it is used — and vice versa. A stroke-width tweak to the RMU glyph instantly re-flows to every rule that uses it. That separation is why the icon’s identity (its icon_ref) is fixed and only its artwork is editable in place.

1.3 ∑ The picture is never stored — it is resolved, in your browser

The second surprise: the map’s tile server never sees a symbol at all. VoltEdge serves feature geometry as vector tiles through Martin. Those tiles carry the shapes and every attribute column — a point, its subtype, its voltage, its status — but not one byte of styling. Instead, when the map layer for a class loads, the browser fetches that class’s schema — GET /feature-classes/{code}/schema — and inside it a symbology array: the class’s rules, pre-resolved into a shape the browser can match directly. Then, for each feature the tiles deliver, the browser runs a tiny matcher (resolveSymbology) that reads that feature’s own attributes, picks the best-fitting rule, and paints the glyph.

  metadata.symbology_icons ─┐                     Martin tiles
  (icon_ref → SVG markup)   │                (geometry + attributes,
                            │                    NO styling)
                            ▼                          │
                   GET /symbology/icons                │
                            │                          ▼
   metadata.symbology_rules │                   ┌─────────────┐
   (which style, which      ├──► browser ──────►│ resolve per │──► glyph
    feature)                │                   │   feature   │    on map
                            │                   └─────────────┘
                   GET /feature-classes/RMU/schema
                     (rules, pre-resolved)

This is why the two “obvious” fixes are the wrong ones. Restarting Martin does nothing for symbology — it serves geometry and has no idea symbols exist. Recompiling a class does not drive its map symbols either — recompiling rebuilds the class’s table and tile function; the schema endpoint reads symbology_rules live at request time. What does make a change appear: a fresh fetch of the class schema. The map caches each class’s schema for a few minutes and only rebuilds a layer when that fetch changes, so the reliable trigger is a hard browser refresh (Ctrl/Cmd-Shift-R). 1.4 ∑ How one feature’s style gets picked: most-specific-wins

A class can carry many rules at once — a plain default, a different look for one subtype, a special colour when a status field has a certain value. When the browser draws a single feature, several might match. VoltEdge scores each matching rule by how narrowly it targets, and the narrowest match wins. A rule can be pinned on two independent axes: Subtype — worth 2 points; a field value — worth 1 point. For each feature, every matching rule is scored and the highest score paints it.

  Specificity of a rule = (subtype pinned ? 2 : 0) + (field value pinned ? 1 : 0)

   subtype 3  AND  status = open   →  3   (most specific — wins over all below)
   subtype 3                       →  2
   status = open                   →  1
   (neither — the default)         →  0   (the safety net — always matches)

That score-0 “neither” rule is special: it matches every feature of the class, so it is the guaranteed fallback. Every class must have exactly one of these — the mandatory default rule. Ties are not expected: authoring is meant never to produce two equally-specific rules for the same combination. 💡 Think of it as a cascade of increasingly specific overrides on a base coat. 1.5 ∑ Two worlds: the map and the diagram

Every rule also declares a render context: map — the geographic map (the vector-tile layers Priya is looking at) — or diagram — the schematic single-line diagram (the stencils on a substation one-line). The same class can, and usually does, carry rules for both: a real-world copper icon on the map, a standardised schematic symbol on the diagram. They are authored side by side and never interfere — each consumer reads only its own context’s rules.

A diagram rule never shows on the geographic map
However perfect its icon. If a symbol is missing from the map, the first thing to check — after “does a rule exist at all” — is that the rule’s context is map, not diagram. A real and easy mix-up. (Flip the context switch in Interactive 1.)

1.6 ▶ The shape of the work ahead

With the model in hand, the operator path for Priya’s request is three moves, and the rest of this guide is those moves in depth:

  1. Draw and register the icon (Chapter 2) — create the voltedge-rmu artwork in the icon library. 🔒 metadata:write
  2. Attach it to the class (Chapter 3) — add a map symbology rule to the RMU class whose icon is voltedge-rmu. This is the step that actually puts it on the map. 🔒 metadata:write
  3. Refine it (Chapters 4–6) — make it change with the feature’s fields, tune its size and colour, control when it labels and at what zoom it shows.

Then hard-refresh, and Priya’s RMUs appear — wearing a symbol that finally looks like an RMU.

1.7 Chapter summary

  • Symbology turns stored geometry + attributes into a styled picture; it is configuration on a feature class, not an edit to any feature.
  • It lives in two tables: symbology_icons (artwork, keyed by icon_ref) and symbology_rules. An icon alone renders nothing — a rule must reference it.
  • Symbols are resolved in the browser, per feature, from rules the schema endpoint hands down live. Martin never sees a symbol; recompiling does not drive map symbology. The reliable “make it appear” action is a hard refresh.
  • When several rules match, the most specific wins (subtype = 2, field value = 1); a mandatory default rule is the always-matching safety net.
  • Every rule has a render context — map or diagram. A diagram rule never shows on the map.
02

Authoring SVG icons

The artwork half: a stamp on the shelf.

This is the first of Ada’s three moves: drawing the artwork. By the end of the chapter she has a valid, named icon — voltedge-rmu — sitting in the library, previewed and ready. It still won’t be on the map (that is Chapter 3’s job — the rule), but it will exist as a reusable stamp. Everything here is the icon library: metadata.symbology_icons. Nothing in this chapter mentions a feature class, because an icon knows nothing about where it will be used.

2.1 ∑ The library, and the five shapes you already have

The library is never empty. Five shapes are built into the frontend as a fallback (FALLBACK_ICONS in symbology-icons.ts) and always resolve, even on a database with zero authored icons:

icon_refShape
circleFilled disc (the default when a rule names no icon)
squareRounded filled square
triangleFilled triangle
triangle-outlineHollow triangle — stroke only, transparent centre
diamondFilled diamond

Two reasons they matter. A brand-new install can style its whole network from these alone. And — the safety net Chapter 1 promised — if a rule names an icon_ref that isn’t in the database (a typo, or a fetch still in flight), the resolver falls back to circle rather than drawing nothing. A missing icon degrades to a shape; it never makes a feature invisible.

∑ shape vs. modifier

triangle-outline is the same triangle as triangle but with fill="none" and a stroke — a genuinely hollow silhouette. It exists so an open switch can differ from a closed one by shape, not merely by colour. Chapter 4 uses exactly this pair.

2.2 ▶ Where you author icons

Ada opens Admin → Symbology icons. 🔒 Seeing the page needs metadata:read. The New icon, edit (✏️) and delete (🗑️) controls only appear with metadata:write — the page gates its own write buttons to match what the server will allow, so Tom sees the gallery but no way to change it. The page lists every authored icon as a card: a live thumbnail, the icon_ref in monospace, and a badge reading Tintable or Full-color (§2.5).

2.3 ▶ Creating the icon — the two fields

  1. Name — becomes the icon_ref, the permanent identity a rule uses to reach this artwork. lower-kebab-case: a letter, then lowercase letters, digits or hyphens — ^[a-z][a-z0-9-]*$, enforced in the form and again on the server (iconRefPattern). The field lowercases as you type. voltedge-rmu is valid; Voltedge_RMU and 2-rmu are not.
  2. SVG markup — the drawing, pasted as raw <svg>…</svg>. Beside it: a live preview and a tint colour swatch, re-rendering as you type (once the text contains <svg).
The name is the identity and it does not change later — editing an icon changes only its markup, never its icon_ref. A house prefix like voltedge-… or a standards prefix like iec-… keeps the library legible.

Create writes the row (POST /admin/symbology-icons) and the icon is immediately live in the library — no deploy needed. (The map still needs a rule before it draws it — Chapter 3.)

2.4 ∑ What makes a valid, renderable SVG

Three rules separate an icon that renders from one that silently fails. Rule 1 — carry explicit width and height, not just a viewBox. The failure mode is nasty because nothing errors — the icon just never appears. The browser rasterises an SVG for a map glyph through a detached Image(), and Chromium sizes an image with no intrinsic width/height at 150×150 — far too big for the icon slot, so it drops out. The editor hint says so: “Must carry explicit width/height, not just a viewBox.”

<!-- ✅ renders -->
<svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24">…</svg>

<!-- ❌ viewBox but no width/height → 150×150 → silently vanishes -->
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100">…</svg>

This is exactly the trap behind “I attached the symbol, recompiled, restarted the tile server, and nothing showed up.” The recompile and restart were red herrings (Chapter 1); the icon simply had no width/height. Rule 2 — author on a 24×24 canvas. Every built-in is drawn at viewBox="0 0 24 24", and the render math assumes it (§2.7). Rule 3 — use {{COLOR}} where the rule’s colour should go (optional, next section).

2.5 ∑ Tintable vs. full-colour: the {{COLOR}} placeholder

Write fill="{{COLOR}}" or stroke="{{COLOR}}" and at render time that token is replaced by the colour the rule specifies — one icon, any colour. The library card badges these Tintable. Leave {{COLOR}} out and the artwork renders exactly as authored — a harmless no-op, how a multi-colour logo or a standards symbol with fixed colours opts out of tinting. Badge: Full-color. You never choose a “mode”; the markup decides.

∑ line weight & canvas size

Raise stroke-width for a bolder glyph; fill="none" keeps the box hollow, fill="{{COLOR}}" on the <rect> makes it solid; stroke-linecap="round" softens the leads. These are ordinary SVG attributes — the editor imposes nothing beyond the three rules. If you draw on a larger canvas (say viewBox="0 0 100 100" with heavier strokes) the icon still renders once it carries width/height — but it looks smaller, because the map scales the whole box down and your art fills only part of it. That is “it’s authored but looks tiny.” Fixes, in order of preference: redraw at 24×24; tighten the viewBox to the artwork’s bounds; or drive its size up with the rule’s scale (Chapter 3).

2.7 ∑ How big the icon actually lands

  on-screen scale = ICON_BASE_SCALE (0.65)  ×  (rule.scale ?? 1)

ICON_BASE_SCALE is a fixed 0.65 (in map-layers.ts) — it scales a 24-unit icon down to roughly the size of the plain dot it replaces. The rule’s own scale (default 1) multiplies that. Experiment: how big is the art itself, given the canvas it was drawn on?

2.8 ▶ Editing and deleting icons

Editing (✏️) reopens the editor on the existing markup. Rewrite the drawing freely and Save (PATCH /admin/symbology-icons/{icon_ref}). The change is instant and global: every rule that references this icon_ref now draws the new artwork, because the identity never moved. The one thing you cannot change is the icon_ref itself. Deleting (🗑️) is guarded: an icon can only be deleted while no symbology rule references it; otherwise the server refuses rather than leave rules pointing at a hole. Safe order: repoint or remove the rules first, then delete the icon. (Try it in Interactive 3: press “↪ use” on a card, then delete it.)

Prefer SQL? The library is a plain table — metadata.symbology_icons (migration 0023), icon_ref → svg. INSERT INTO metadata.symbology_icons (icon_ref, svg) VALUES (…) works and takes effect on the next schema/registry fetch. The same three rules apply — width/height especially, since SQL won’t warn you.

2.9 Chapter summary

  • Icons live in metadata.symbology_icons, authored at Admin → Symbology icons (🔒 metadata:read to view, metadata:write to change). Five built-in shapes always resolve; a bad icon_ref degrades to a shape.
  • A new icon needs a lower-kebab name (its permanent icon_ref) and SVG markup, checked against a live tinted preview.
  • A renderable SVG carries explicit width/height (missing → silent 150×150 failure), is best authored at 24×24, and uses {{COLOR}} where the rule’s colour applies.
  • On-screen size = 0.65 × (rule.scale ?? 1). Editing changes only the artwork and is global and instant; deletion is blocked while any rule references the icon.
03

Attaching a symbol to a feature class

The rule that actually puts it on the map.

The icon exists; now make it appear. This is the step that puts a symbol on the map — the rule that says “draw every RMU as voltedge-rmu.” By the end, Priya’s ring main units finally look like ring main units.

3.1 ▶ Where rules live

Rules are edited per feature class, not in one global list: Admin → Feature classes → open the class (e.g. RMU) → the Symbology section. That section lists every rule the class already has, each with a live swatch of exactly how it renders, and gives you four actions: Add rule, Edit, Duplicate, Delete (🔒 all metadata:write; metadata:read sees the list read-only). Separate Labelling and Display zoom sections sit nearby — those are Chapter 6.

3.2 ▶ The Add-rule form, field by field

Add rule opens one dialog. The top row is targeting (who the rule applies to); the bottom is style (what it draws). For a first default rule you touch only two things — render context and the icon — and leave the rest at “any”.

The style controls change with the class’s geometry: a point shows Scale + Icon; a line shows Width + Dash; a polygon shows Fill color + Stroke color (Chapter 5). RMU is a point, so you get the icon picker.

3.3 ∑ The default rule — the one every class must have

A rule with Subtype = any and Field = any targets nothing in particular, so it matches every feature of the class. That is the default rule, and every class must have exactly one (per render context). It is what guarantees a feature is never unstyled.

  • Nothing enforces “exactly one default” after a class is created — not the rule editor, and not the compiler (cmd/compile and internal/compiler contain no symbology check; older comments saying otherwise are out of date). You can freely add, edit and delete rules; leave a class with no default and nothing fails — unmatched features just fall back to the map’s plain geometry styling. Two defaults are accepted too.
  • Deleting rules has no guard — deletion can only ever remove specificity, and nothing re-checks the set afterwards, so keep your own default rule in place.
Rule of thumb: always keep one any/any rule per class. Build specificity on top of it (Chapter 4), never by removing it.

3.4 ▶ Worked example — put voltedge-rmu on the map

  1. Admin → Feature classes → RMU → Symbology → Add rule.
  2. Render context: map. Subtype: any. Field: any. (This is the default rule.)
  3. Color: pick the copper tone. Icon: choose voltedge-rmu (its thumbnail is tinted with the colour you picked). Scale: 1 — or 2 if it reads small.
  4. Add rule → the row appears with a live swatch (POST /admin/feature-classes/RMU/symbology-rules).
  5. Hard-refresh the map (Ctrl/Cmd-Shift-R). Every RMU now wears the glyph.

If the RMU class already had a plain default rule (many seeded classes do), Ada doesn’t add a second one — she Edits the existing default and swaps its icon. One default, edited, not duplicated.   • Rules are authored per class at Admin → Feature classes → {class} → Symbology (🔒 metadata:write), each shown with a live swatch.
  • The Add rule dialog is targeting (render context / subtype / field / value / zoom) over style (colour + geometry-specific knobs + icon).

04

Targeting: by subtype and by field value

Narrow rules over a base coat; the engine picks.

A single glyph for a whole class is rarely enough. You want open switches to look different from closed ones, transmission poles heavier than distribution poles, faulted assets to jump out. That is targeting: narrowing a rule so it paints only some features, and letting the most specific rule win.

4.1 ∑ The two axes, and who wins

Rule pins…SpecificityBeats
Subtype and field value3everything below
Subtype only2field-only and default
Field value only1default
Neither (the default)0nothing — the fallback

For each feature the browser scores every matching rule and paints with the highest. You never order rules by hand; you author the narrow ones and the engine picks. Authoring should never create two equally-specific rules for the same subtype+value combination — that is the one ambiguity to avoid (the list flags it with a ⚠ tie).

4.2 ▶ Targeting by subtype

Use this when a subtype should simply look different — an underground vs overhead conductor, a transmission vs distribution pole. Add rule → Subtype: pick it (the dropdown shows code: name) → Field: any → set the style → Add rule. That rule scores 2 and overrides the default for just that subtype; everything else falls through.

4.3 ▶ Targeting by field value — the coded-field requirement

The value axis only works on a coded field: one backed by a domain (a fixed list of allowed values). In the Add-rule form the Field dropdown lists only the class’s coded fields; a free-text or numeric field never appears. Once you pick a field a Value dropdown appears, populated from that field’s own domain, and it is required — a field without a value is rejected both in the form and on the server.

Field on SWITCHKindIn the Field dropdown?
namefree textno
rated_anumberno
statecoded (domain: open, closed)yes
∑ exact string equality

At render time the match is exact string equality: the feature’s stored value must equal the rule’s value code. So the codes you target are the domain’s value codes (open, oh, CU…), not their display labels.

4.4 ▶ Worked example — open vs closed switches

Tom wants open switches to read as a hollow triangle and closed ones as a solid triangle. His switch class has a coded state field whose domain includes open and closed. Three rules:

  1. Default (any/any) — triangle, normal device colour. (Score 0 — a switch with no state, or an unexpected state, still draws.)
  2. Field = state, Value = closed — triangle (solid). (Score 1.)
  3. Field = state, Value = open — triangle-outline (hollow). (Score 1.)

A closed switch matches rules 1 and 2 → rule 2 wins. An open switch matches 1 and 3 → rule 3 wins. This is exactly why triangle-outline exists. 💡 Want open switches red and hollow? Give rule 3 a red Color too — a rule sets targeting and style together.

4.5 ▶ Combining both axes

Pin Subtype and Field together for a score-3 rule — e.g. “load-break switches (subtype) that are open” drawn differently from other open switches (recipe ③). Reach for this only when a broad field rule genuinely needs a per-subtype exception; most maps never need score-3 rules.

4.6 Chapter summary

  • Targeting narrows a rule; specificity = subtype (2) + field value (1); the highest-scoring matching rule paints each feature, automatically.
  • The value axis needs a coded (domain-backed) field — only those appear in the Field dropdown, and a chosen field requires a value.
  • Layer narrow rules on top of the default; default triangle, closed→solid, open→hollow triangle-outline is the canonical example.
  • A rule sets style and targeting together, so one rule can change both shape and colour for its slice.

Styling lines and polygons

Points wear icons; lines and polygons wear strokes and fills.

When the class’s geometry is a line or a polygon, the Add-rule form swaps the icon picker for the knobs that geometry actually uses — and shows a live swatch. Targeting (Chapter 4), the default rule (Chapter 3), and zoom (Chapter 6) work identically; only the style controls differ.

5.3 ∑ What’s written, and why blobs stay clean

Behind the form a rule stores only the style keys its geometry uses: icon_ref/color/scale for a point, color/width/dash for a line, fill_color/stroke_color for a polygon (color is shared). Only keys you set are written — a point rule never carries empty line keys. You don’t manage this; it’s why the form shows only the relevant knobs.

5.4 Chapter summary

  • Style controls follow geometry: point → Scale + Icon, line → Width + Dash, polygon → Fill + Stroke (Color is shared).
  • Dash is one of solid / dashed / dotted / dashdot.
  • Targeting, default rule and zoom behave exactly as for points — style underground conductors dashed via a subtype rule over a solid default; thicken by voltage with a field rule on top.
06

Zoom, labels, and visibility

The decluttering toolkit — three controls, three jobs.

A correct symbol on a crowded map is still unreadable if everything draws at every zoom. This chapter hinges on telling apart three different zoom controls that beginners conflate. Get these straight and map tuning becomes easy.

6.1 ∑ Three controls, three jobs — do not confuse them

ControlWhereWhat it does
Rule zoom band (Apply rule from/to zoom)inside a rulePicks which style applies at a zoom — never hides anything
Display zoom (min/max)the Display zoom sectionHides the whole feature (glyph and label) outside a zoom range
Label min zoomthe Labelling sectionSuppresses just the text label below a zoom
The trap: a rule’s zoom band does not hide features. Outside it the feature still draws — some other rule (or the default) paints it. If you want a class to actually disappear when zoomed out, that is Display zoom, not a rule band. The rule form even says so inline.

6.2 ▶ Restyle by zoom (rule band)

Use a rule band to simplify a symbol when zoomed out — a small dot far out, the full icon up close. A default rule (no band): the full icon (applies where no banded rule does). A rule with Apply rule to zoom = 12, styled as a small plain circle (wins at low zoom; above 12 it drops out and the default takes over). Because a banded rule that falls out simply yields to a lower-specificity rule, keep an unbanded rule to cover the zooms the band doesn’t — otherwise a feature can be left with no matching rule at that zoom and fall back to plain styling.

6.3 ▶ Hide a class at some zooms (Display zoom)

Admin → Feature classes → {class} → Display zoom → Set range. Enter a Min and/or Max zoom (whole numbers 0–24; leave either blank for no bound). Outside the range the entire feature vanishes — glyph and label. This is how service points or LV detail stay hidden until you zoom in, and how a transmission backbone can drop out when you zoom way out. 💡 It’s the big hammer for clutter, and it’s map-only — the diagram one-line always shows everything.

6.4 ▶ Labels — the map label editor

Admin → Feature classes → {class} → Labelling → Add label. There is one label config per class (not per rule):

  • Template — the label text with {field} placeholders substituted from each feature’s attributes, e.g. {name} ({voltage_kv} kV). An Insert field… dropdown appends tokens. An empty template turns labels off. Missing values collapse out cleanly.
  • Size, Color, Bold, Italic — text appearance, with a live preview.
  • Halo (on by default) with its color and width — the legibility outline over busy backgrounds. Leave it on.
  • Min zoom — suppress the label below this zoom (declutter without hiding the glyph).
  • Offset X/Y and Rotation — nudge and spin point/polygon labels (a line label rides its line and ignores these).

Worked example — name your transformers. Dana labels DIST_XFMR with {name} at Size 11, halo on, Min zoom 14 — so names appear only when zoomed into a neighbourhood, not as a wall of text across the region. ∑ The label config rides label_def jsonb on the feature class and is published on the same class schema the map already reads — so, like rules, a label change is live on the next schema fetch (hard refresh), no recompile.

6.5 Chapter summary

  • Three zoom controls: a rule band picks a style (never hides); Display zoom hides the whole feature; Label min zoom hides only the text.
  • To make a class disappear when zoomed out, use Display zoom, not a rule band — and keep an unbanded rule so banded features never fall through to plain styling.

07

Diagram symbology

Same machinery, render context flipped.

Everything so far has styled the geographic map. VoltEdge also draws the schematic single-line diagram, and it has its own symbology — a standard stencil for each class, independent of how the class looks on the map. This chapter is short because you already know the machinery: it’s the same rule editor, with the render context flipped.

7.1 ∑ Why diagram symbology is separate

On the map a transformer is a real-world glyph at a real location; on a one-line it is a standardised schematic symbol wired into a bus. Different pictures of the same asset, so each class carries two independent sets of rules, told apart by render context: map rules paint the map, diagram rules paint the one-line. Each consumer reads only its own context. The resolution is otherwise identical: most-specific-wins, the same subtype/field targeting, the same default-rule requirement per context. Diagram resolution runs without a “current zoom”, so rule zoom bands don’t apply there — a diagram isn’t zoomed the way a map is.

7.2 ▶ Authoring a diagram symbol

  1. Admin → Feature classes → {class} → Symbology → Add rule.
  2. Render context: diagram.
  3. Target and style exactly as for a map rule — pick a schematic icon, set colour, layer subtype/field rules the same way.
  4. Save; the one-line canvas uses it (no zoom to gate on, so it reads diagram rules directly).
The most common mix-up, restated: a rule authored diagram will never show on the geographic map, and a map rule never shows on the one-line. If a class looks right on the map but wrong on the diagram (or vice versa), you’re almost always looking at the wrong context’s rules. Check the Render context column first.

7.3 ▶ Practical guidance

  • Give a class a diagram default rule too, if it appears on one-lines — the same “exactly one default per context” discipline keeps its schematic never unstyled.
  • Diagram icons are typically standards symbols (IEC-style), often authored as full-colour artwork (no {{COLOR}}) so they render as-drawn regardless of a rule’s colour. The icon library is shared — one iec-… icon can serve many classes’ diagram rules.
  • Use field-value diagram rules to reflect state schematically — e.g. an open disconnector drawn as a break in the line — exactly as §4.4 does for the map.

7.4 Chapter summary

  • Each class carries separate map and diagram rule sets, chosen by render context; each surface reads only its own.
  • Authoring a diagram symbol is the same editor with Render context = diagram; give it its own default rule, and note rule zoom bands don’t apply on the diagram.
  • A symbol on the wrong surface almost always means the wrong render context — check that column first.

Troubleshooting & recipes

The reference you jump to when a symbol misbehaves.

This chapter distils every gotcha in the guide into a checklist, a set of SQL peeks, and a one-page cheat sheet. The checklist is a live diagnoser: pick a fault, and each step below tells you — against the actual rules, icons and cache — whether it passes. The preview is what Priya’s browser is drawing.

8.1 ▶ “I attached a symbol and nothing appears” — the checklist

Walk these in order; the top three catch almost everything:

  1. Is there a rule, not just an icon? An icon in the library renders nothing on its own (Chapter 3). (The #1 cause.)
  2. Does the icon carry width and height? Not just a viewBox — a missing intrinsic size resolves to 150×150 and silently vanishes (Chapter 2). (The #2 cause, and the one this network actually hit.)
  3. Is the rule’s render context map? A diagram rule never shows on the map (Chapter 7).
  4. Did you hard-refresh? The map caches each class’s schema for a few minutes; a soft refresh may keep the old one. Restarting Martin and recompiling do not help — symbology is resolved client-side from the live schema (Chapter 1).
  5. Is the class hidden by Display zoom at your current zoom (Chapter 6)?
  6. Does the targeting actually match? If the rule pins a field value, the feature’s stored value must equal the rule’s value code exactly (Chapter 4). A default (any/any) rule is immune — add or check one.
  7. Does the class have its mandatory default? No default → nothing fails (the compiler does not check), but features with no more-specific match fall back to plain geometry styling.

8.2 ▶ “It shows, but it’s the wrong size”

  • Too small / too big: drive the rule’s scale (on-screen = 0.65 × scale), Chapter 2.7 — don’t resize the SVG unless the artwork is genuinely off.
  • Authored on a big viewBox and reads tiny: the art fills only part of a large canvas that gets scaled down. Redraw at 24×24, tighten the viewBox, or bump scale (Chapter 2.6). The sizing calculator in Interactive 4 does this arithmetic.

8.3 ▶ “Wrong colour”

  • Tint ignored: the icon has no {{COLOR}} placeholder, so it renders as authored (Full-color). Add {{COLOR}} to the fill/stroke you want the rule to control (Chapter 2.5).
  • Everything one colour: you’re seeing the default rule; add a subtype/field rule to differentiate (Chapter 4).

8.6 The one-paragraph mental model (keep this)

Two tables — icons (artwork) and rules (which style for which feature) — resolved in the browser, per feature, most-specific-wins, from rules the class schema hands down live. An icon alone draws nothing; a rule attaches it. Every class needs one default rule per render context. Symbols must carry width/height. Nothing is baked: a hard refresh — never a recompile or a Martin restart — is what makes a change appear.
