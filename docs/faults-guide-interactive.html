A fault is a record.
Not a feature.

The Faults module keeps one durable row for each electrical fault event on the network — the earth fault, the short, the protection operation — and hangs it between the outage it explains and the repair it triggers. This guide is a working copy of the real engine: a JavaScript port of api/internal/faults with the same validation order, the same error strings and the same HTTP status mapping. Log a fault, PATCH it, push it through the lifecycle, replay an offline capture, book a defect — and watch the record, its history and the webhook events change.

Use As in the top bar. Vic (viewer) and Tom (analyst) hold faults:read only. Priya (editor, the same role as Dana) and Ada (admin) add faults:write. Widgets that call the API are gated exactly as the server gates them, so switch persona to see a real 403.

Who this is for

Control-room operators logging and tracking faults, network engineers investigating them, and field crew who clear a fault and book the repair. The manual (faults-guide.md) holds every table and appendix; this edition keeps all nine sections and both appendices and makes each rule something you can poke. Where I checked the manual against the code and found it wrong, the fix is in the manual and listed in the Corrections box in chapter 10.

01

What a fault record is — and is not

Two things named “fault”, and a hinge between an outage and a repair.

A fault here is an operational record of an electrical fault event that happened — about the assets on the map, not drawn on it. It is the causal hinge between an outage (the OMS incident the fault explains) and a defect (the WAM repair the fault triggers):

   OMS incident  ──explains──►  FAULT EVENT  ──triggers──►  WAM defect ──► work order
   (the outage)                 (this guide)                (the repair)

VoltEdge has two completely separate things with “fault” in the name. Confusing them is the first trap. Pick a job and see which one does it:

They share only vocabulary: a fault record carries a fault_type and a fault_current_a from the same classification the engine speaks, so you can compare measured against predicted — but there is no code dependency; neither reads the other. And a fault is not a map feature: it is a row in faults.fault_events, not a compiled gis.<class> table. It points at the faulted asset by a loose reference and may carry a location pin, but you never draw or trace through it.

02

Who may do what

Two permissions, one method-aware gate — and no territory filter.

Two permissions gate the whole module (seeded by migration 0107, constants in auth/rbac.go), enforced on the /faults mount at main.go:279 with RequirePermission(faults:read, faults:write): GET/HEAD/OPTIONS need read; every other method needs write. The grants mirror OMS and WAM: everyone who can see the map reads; whoever can edit features writes.

Interactive · 2

The role matrix and the method gate

Faults are not territory-scoped. Unlike map features (Phase 58 spatial access control), faults.fault_events has no territory_id and no route narrows by territory. Every faults:read holder sees every fault on the system, whatever districts they are scoped to on the map. If you rely on territory scoping to partition what a user sees, the fault board is organisation-wide.

Note the personas are people, not roles — there is no “operator” role; Priya and Dana are both editors. In the web app the sidebar entry needs faults:read and the Log fault button and row actions appear only with faults:write.

04

The lifecycle

Four statuses, one write path — and an API more flexible than the UI.

A fault moves through four statuses: detected (just logged, still on the network) → investigating (patrol dispatched, cause being established) → cleared (off the network: isolated or repaired enough to restore) → closed (the outage and the booked defect are wrapped up). Reaching cleared or closed stamps cleared_at automatically (SetFaultStatus COALESCEs it to now); dropping back to a non-terminal status clears it again, so the DB invariant (status ∈ cleared,closed) = (cleared_at is set) always holds.

SetFaultStatus does not enforce a forward-only path — any valid value can be set (even the current one), which is how a reopen works. The UI offers only the sane transitions. Pick a fault, then try every target status and compare what the API permits with what the web board offers.

Interactive · 4

State machine — API vs UI

Every change is audited. faults.fault_event_history (migration 0109) is an append-only trail: one immutable row per change with an action, the actor_id from the session (null for a system write), the time and a full snapshot of the fault after the change.

The fault record has no created_by; “who” lives only in the history. Read it at GET /faults/{id}/history (newest first, with the actor’s display name or email joined in) or the expandable History panel on each board row. History rows survive the fault: fault_id and actor_id are deliberately not foreign keys.

05

How to log a fault

Board, map tab, Outages button, API — each door shows different fields.

  1. Sidebar → Faults (the ⚡-off icon). The board lists faults newest first; Open only is ticked by default, so cleared/closed faults are hidden until you untick it.
  2. Click Log fault (🔒 faults:write).
  3. Give it a title and anchor it: the faulted asset (class + feature; the picker resolves names through the feature registry) or a location (longitude + latitude). The API also accepts an incident_id anchor, but this dialog only enables Log fault for an asset or a location.
  4. Optionally add fault type (pre-selected unknown and always sent), cause, detected by, fault current, clearing time, description. Log fault → POST /faults, 201, status detected.

From the map: select the faulted feature → the attribute panel’s Faults tab (needs faults:write) shows that asset’s fault history and lets you log (title, type, cause — the asset anchor is filled in), investigate, clear, close, reopen and book a defect without leaving the map. From an outage: the Outages page has an icon-only ⚡ button per incident — chapter 6.

5.1 The log-a-fault simulator

Switch between the web dialog (which hides the protective device, reference, notes and incident, and only enables Save with a title plus an asset or location) and the raw API (everything the server accepts). Errors come back in the same order and wording as CreateFault; database-level problems (a negative current, a non-UUID id) are plain errors and so 500, not 400.

5.2 Findings vs. status — two different writes

PATCH /faults/{id} is a sparse patch of investigation findings (reference, fault type, cause, device pair, current, clearing time, detected-by, incident link, title, description, notes). It does not touch status. POST /faults/{id}/status is the only way to move the lifecycle. Keeping them apart makes “I learned the cause” and “I’m marking it cleared” distinct, separately-audited actions. Only non-null fields are written; a pair travels together; an empty fault_type clears it.

The web app defines a useUpdateFault hook, but no screen calls it. Today findings are patched through the API, the agent tool faults_update, or an inbound webhook — not from the board. A PATCH cannot change the asset, the location pin or detected_at.

5.3 Offline-safe logging

A field device mints the fault’s id itself and pushes a fault_create sync op (the id rides in the op’s feature_id) when it reconnects. The insert is ON CONFLICT (id) DO NOTHING, so replaying a queued capture never double-logs and writes no second history row or webhook event. The REST POST /faults body has no id field (createFaultRequest) — an id sent there is silently ignored, so it is not replay-safe.

The connections — asset, device, incident, defect

Three loose references and one real cross-module call.

A fault sits at the centre of four links. Three are loose references — a bare class/id pair or a bare uuid, deliberately not a foreign key, so a fault survives its asset being re-modelled. One (the defect) is a real call into WAM. Click a link:

Interactive · 8

The four links and how each is validated

None of the loose links is checked for existence. CreateFault validates that class and id come as a pair (and that ids are well-formed uuids at the database), but never looks the asset, device or incident up. A random uuid logs happily; the map simply cannot place it. Only raise-from-incident reads oms.incidents, and only book-defect calls wam.CreateDefect.

6.1 Raise a fault from an outage (③)

🔒 faults:write. On the Outages page, the ⚡ icon on an incident (hidden for cancelled incidents) calls POST /faults/from-incident/{id}. The direction is fault attaches to an existing incident: the fault inherits the incident’s predicted device (as the device that operated) and its cause, anchored by incident_id. The button sends an empty body, so the title is “Fault behind incident” until renamed; the API accepts title, fault_type, cause, detected_by and notes overrides. The incident is read by raw cross-schema SQL — faults does not import oms.

Interactive · 9

Raise from an incident

6.2 Book the repair from a fault (④)

🔒 faults:write. Book defect on the board row (or the map tab, or the mobile app) calls POST /faults/{id}/defect → wam.CreateDefect (source = outage, carrying the fault’s incident_id; title defaults to “Fault damage: <title>”; severity defaults to medium), then writes defect_id back onto the fault, in one transaction. It needs an asset or a location and no existing defect. The defect then becomes a work order inside WAM — the fault does not create the work order directly. The web board and map tab hide the button once a fault is closed; the API does not.

Interactive · 10

Book a defect — preconditions and result

One-directional dependency. faults imports wam (to book a defect) but not oms (the incident link is raw cross-schema SQL). The graph is faults → wam; faults ↔ oms is DB-only — no import cycle. The impact trace likewise reuses the shared trace engine rather than importing OMS.
07

Impact & the map

Where a fault’s marker goes, what “impact” counts, and how the board filters.

7.1 The map overlay

GET /faults/map returns every fault with a resolvable point, filterable like the board. An asset-anchored fault is drawn on its asset: a marker guaranteed to lie on the geometry (ST_ClosestPoint(geom, centroid)) plus the asset’s full GeoJSON for the highlight. Asset geometry is preferred over a pin when both exist. A location-only fault keeps its pin. Omitted: incident-only faults, and faults whose asset class is uncompiled, deleted or geometry-less with no pin. The layer is off by default; its legend shows only detected and investigating until you tick cleared/closed; live faults pulse (unless the OS asks for reduced motion). Clicking a marker draws its impact area.

7.2 The impact area

GET /faults/{id}/impact answers “what did this fault take out?”: it walks downstream of the fault’s protective device and returns the de-energised service points below it (FaultImpact, geometry.go). It counts only SERVICE_POINT features and is barrier-free / topological — the same conservative basis the OMS impact trace uses, per the code comment. 08

Automation & integration

Outbound events, inbound ingestion, agent tools, offline sync.

  • Outbound webhooks. CreateFault emits faults.event.raised; a status change emits faults.event.cleared (on cleared/closed) or faults.event.updated (webhookout/outbox.go). A findings PATCH and a defect booking emit no event. Wire these to a downstream CIS/WMS.
  • Inbound webhooks. An ingestion endpoint with target fault (webhook/adapter_ops.go) creates or updates faults from the sender’s own external_id: first sight creates (same validation and anchor rule as a hand edit); a repeat patches findings and/or sets status. op must be upsert — a fault is never webhook-deleted — and the acting identity needs faults:write.
  • Agent / MCP tools (agenttools/tools_faults.go) — each carries its route’s permission. Reads: faults_list, faults_get, faults_list_history, faults_list_map, faults_impact_area. Writes: faults_create, faults_set_status, faults_update, faults_raise_from_incident, faults_book_defect (annotated “confirm with a human”).
  • Offline sync. Sync ops fault_create, fault_status, fault_book_defect (fieldpack/sync.go); there is no offline findings-update op. The Flutter field app has a Faults screen (raise fault, update status, book defect). Book-defect replay is idempotent on the fault’s own defect_id. The submitting user is stamped as detected_by/reported_by. The sync endpoint’s own permission gate is outside this guide (not verified here).

10.5 Corrections made to the manual

  • Webhook names. Manual said fault.raised/cleared/updated; the code emits faults.event.raised/cleared/updated (webhookout/outbox.go:51-53), and only create and status change emit — not PATCH or book-defect.
  • Offline idempotency. Manual said a device can mint an id and POST /faults; the REST body has no id field (faults/http.go:92-110). The idempotent path is the sync fault_create op (fieldpack/sync.go applyFaultsOp).
  • Log-fault dialog. Manual listed the protective device and an incident anchor; the dialog (routes/faults.tsx LogFaultDialog) has no device, reference, notes or incident field, and Save needs an asset or location. The board also defaults to Open only, not “every fault”.
  • Findings edit. Manual implied operators patch findings from the board; useUpdateFault (hooks/use-faults.ts) is unused by any screen — API/agent/webhook only.
  • Raise-fault button. Icon-only, hidden for cancelled incidents, sends an empty body (routes/outages.tsx), so the title is “Fault behind incident”.
  • Added, not wrong: inbound-webhook fault target, offline ops, mobile Faults screen, map-overlay defaults, impact-area limits, unknown-id → 400.
