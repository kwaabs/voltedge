01

Orientation: the administration model

RBAC for the verb, spatial access for the place — and one boolean column that is not a permission.

Before any specific admin task, you need the shape of the system and the two ideas that govern who can do what: RBAC (role-based access control — which actions a person may take) and spatial access (which territories those actions may touch). Everything else in this guide — user provisioning, metadata authoring, setup, break-glass — hangs off this model.

1.1 Who administers VoltEdge, and this guide’s two personas

VoltEdge draws a deliberate line between operating the network data (what the user handbook covers) and administering the platform. Administration is itself two distinct jobs, and this guide personifies them so the difference stays visible:

Ada

The system administrator

Holds the admin role. Provisions users and assigns roles, authors the metadata catalog (feature classes, fields, domains, symbology), configures map settings and external service layers, runs ETL imports, manages territories and circuits. A normal account with a powerful role: every action is gated by the same permission checks as everyone else’s.

Owen

The break-glass administrator

Exists for the day the normal path fails: the SSO provider is down, local auth was switched off and no one can sign in, or a destructive out-of-band operation (a factory reset) is needed. His account is flagged in a way Ada’s is not, and the flag buys three specific emergency powers (§1.5). “The fire-axe behind glass” — rarely used, deliberately conspicuous, audited when it is.

The distinction is not “more permissions”
The admin and break-glass-admin roles both grant every permission. What separates Owen from Ada is a database column that changes how Owen can authenticate and what survives a reset — not a bigger permission set. Keeping that straight is the single most important idea in this guide.

1.2 The system in one page

VoltEdge is a metadata-driven electrical-network GIS. The parts an administrator touches:

The Go API api/

A chi router over the bun ORM against PostgreSQL/PostGIS. The API connects as a single Postgres superuser over one DATABASE_URL, and all access enforcement lives in Go — there is no Postgres row-level security. If a route isn’t wrapped in a permission check, the database won’t stop it: the middleware is the security boundary.

The React frontend web/

TanStack Router + React Query + OpenLayers; admin screens at web/src/routes/admin-*.tsx.

The Flutter field app

Offline-capable; authenticates with the same identity system via a bearer token.

The cmd/ binaries

The API server plus out-of-band tools: authadmin, compile, resetdata, mcpserver, exportworker, importworker, fieldsync, uncompile.

Migrations

Repo-root migrations/: sequentially numbered SQL (0001…), applied by migrations/apply.sh, tracked in ops.migration_log.

The compiler

Feature classes are authored as metadata and then compiled into physical gis.<code> tables — so an admin authoring a class is, in effect, defining a database table and its API surface.

The iam schema (not auth — that name is reserved by the base Postgres image) holds all identity and access data: iam.users, iam.sessions, iam.roles, iam.permissions, iam.role_permissions, iam.user_roles, iam.user_territories, iam.api_tokens, iam.system_settings, and the iam.auth_events audit log.

1.3 RBAC: how a permission check actually works ∑

Access control is the trust boundary, and it’s small enough to understand completely. The package is api/internal/auth. When a request arrives, middleware resolves the caller into a SessionUser — a snapshot attached to the request context:

type SessionUser struct {
    ID                 string
    Email              string
    DisplayName        string
    BreakGlass         bool                // the break-glass column, carried through
    Permissions        map[string]struct{} // every permission this user's roles grant
    AllowedTerritories []string            // resolved spatial scope (§1.4)
    Unscoped           bool                // holds territories:unscoped → skip spatial filter
    Subordinates       []string
    SessionID          string
    CSRFToken          string
}

The check is exactly one method — a map lookup, nothing more:

func (u *SessionUser) Has(perm string) bool {
    _, ok := u.Permissions[perm]
    return ok
}
There is no break-glass short-circuit in Has()
A break-glass user isn’t “allowed everything by fiat” — they pass permission checks because their role put every permission string into their Permissions map, exactly like the admin role does. If you somehow had a break_glass = true account with no roles, Has("features:write") would return false. Break-glass power over actions is entirely a function of the role you also assign; the column governs authentication, not authorization (§1.5).

Where the permissions come from. On session load, loadPermissions unions every permission across the user’s roles — iam.user_roles ⋈ iam.role_permissions — into the Permissions map. The same resolution runs on the API-token path (ResolveAPIToken), so a bearer token is scoped exactly like the user who owns it.

The gate. Routes are wrapped in RequirePermission(readPerm, writePerm):

  1. No session → 401 Unauthorized.
  2. Pick the required permission by method: readPerm for GET/HEAD/OPTIONS, otherwise writePerm.
  3. user.Has(required) is false → 403 Forbidden.

So a single mount like RequirePermission(PermMetadataRead, PermMetadataWrite) makes reads need metadata:read and writes need metadata:write in one line. Write routes additionally require CSRF (RequireCSRF, a double-submit token plus Sec-Fetch-Site/Origin check) on the browser path. The permission strings are Go constants mirroring the iam.permissions catalog — PermFeaturesRead = "features:read", PermUsersManage = "admin:users", PermAuthSettings = "admin:auth-settings", and so on.

1.4 Spatial access: the second axis ∑

RBAC answers “may this user perform this kind of action?” Spatial access answers “…on features in which territories?” The two are AND-ed: a user needs both the permission and the territory to touch a feature. The resolver is api/internal/access (Phase 58). It deliberately never imports auth — auth depends on it, keeping the dependency one-way:

  • EffectiveIDs(ctx, db, userID) resolves a user’s effective territory set with one recursive CTE: the territories granted to the user, plus those granted to anyone who reports up to them (down the iam.users.manager_id org tree), each expanded down the gis.territories subtree. A manager inherits their reports’ scope; a grant on a parent territory covers its children.
  • Fail-closed. An empty result means “match nothing” — never “no filter.”
  • The bypass. Holding territories:unscoped sets SessionUser.Unscoped = true and the spatial predicate is skipped entirely. Both admin and break-glass-admin roles hold it (migration 0094), which is why Ada and Owen see the whole network — not a special case in the code, just a permission.
  • Instant revocation. Results are cached (CachedEffectiveIDs), and every territory/manager mutation calls access.InvalidateAll() after commit.
Spatial enforcement ships OFF
It’s gated by the territory_enforcement_enabled flag (migration 0029, default off). Until an admin turns it on, RBAC is the only axis in force and every authorized user is effectively unscoped. Chapter 4 covers the rollout — and lets you try it.

1.5 The break-glass admin, precisely ▶∑

Now the central distinction. A break-glass admin is a User whose iam.users.break_glass column is true, a boolean carried through to SessionUser.BreakGlass. That column does not grant any permission. Its power is three specific authentication/lifecycle bypasses — and by convention such an account is also assigned the break-glass-admin role (every permission), so it can actually do things once it’s in.

  1. Login bypass (login.go). Normal local (password) login is gated by the local_auth_enabled system setting. The login handler computes allowed := user.BreakGlass and only consults that setting when the user is not break-glass. A break-glass account can always sign in with its local password, even when local auth is globally disabled — the SSO-outage escape hatch. Audited as break_glass_login.
  2. Auth-settings toggle bypass (setLocalAuthHandler). Flipping the switch requires user.BreakGlass || user.Has(PermAuthSettings). A freshly bootstrapped break-glass account — column set, no roles yet — can still turn local auth back on for everyone.
  3. Factory-reset survivor (cmd/resetdata, Chapter 6). The destructive reset authenticates via VerifyBreakGlassAdmin and makes that same account the sole surviving user. Only a break-glass account can authorize a reset, and only it lives through one.

VerifyBreakGlassAdmin(ctx, db, email, password) looks up the user, verifies the Argon2id password on their local identity, and requires break_glass == true and status == "active". It fails closed with a single opaque error ("break-glass authentication failed") no matter which check failed — no oracle for an attacker.

There is no BREAK_GLASS_* environment variable
The whole concept is the break_glass DB column plus the local_auth_enabled runtime switch in iam.system_settings. The only break-glass-adjacent env inputs are the passwords the out-of-band tools read — AUTHADMIN_PASSWORD and RESETDATA_PASSWORD — never flags. Break-glass state lives in the database, not the environment, deliberately: it’s runtime-toggleable and audited, not a deploy-time constant.

2.1 What a deployment is made of

  
Chapter 1 established the security model — Go is the boundary, one Postgres superuser, no RLS. Setup makes that concrete: a deployment is one database and a small fleet of Go processes that all open it from the same DATABASE_URL. The processes are the cmd/ binaries, in two groups:

  

    
Long-running
Services that stay up
server — the HTTP API (PORT, default 8080; compose publishes API_PORT=3704); it enforces every check in Chapter 1.
mcpserver — MCP for AI agents (MCP_PORT 8090), optional.
exportworker — drains the export queue; needed only if users export.
importworker — drains the ETL queue (Ch 8).
fieldsync — builds/serves offline region packs (FIELDSYNC_PORT 8091).

    
One-shot
Tools that run and exit

resetdata — the break-glass factory reset (Ch 6).

  

  
Every one of these opens its own connection pool from DATABASE_URL. There is no privileged “admin connection” and no unprivileged one — they are all the same superuser; the only thing that makes authadmin more powerful than server is that authadmin is a command you run from a shell with database credentials, while server is a daemon that answers strangers over HTTP and therefore runs everything behind the RBAC middleware.

The one variable that is never optional is DATABASE_URL (postgres://<user>:<pass>@<host>:<port>/<db>). Every cmd/ binary opens its pool from it. 2.4 Building the schema: migrations

  
VoltEdge’s schema is a sequence of plain SQL files in the repo-root migrations/ directory, numbered 0001… through the hundreds (0113 at the time of writing). They are applied in filename order, and each file is applied exactly once. Two pieces make that work: ops.migration_log — the ledger of what has been applied (bootstrapped by 0002_create_migration_log.sql) — and migrations/apply.sh, the runner. For every .sql file, in filename order, it checks whether that filename is already logged; if not, it applies the file with psql -v ON_ERROR_STOP=1 -f (migrations are transactional per file), then records the filename, the -- Purpose: header as description, and a sha256sum checksum.


task migrate                                   # = docker compose exec -T … gitbash bash /workspace/migrations/apply.sh
DATABASE_URL='postgres://…' ./migrations/apply.sh   # against a Postgres you reach directly
task migrate-status                            # SELECT filename, status, applied_at FROM ops.migration_log ORDER BY id

2.5 Materialising feature tables: compile

  
This step surprises people coming from an ordinary application, and it is the heart of VoltEdge’s metadata-driven design. Migrations build the fixed schema. But the feature tables themselves are not written by migrations. A feature class like MV_CONDUCTOR exists first as metadata — rows in metadata.feature_classes, metadata.feature_fields, and friends. The physical table gis.mv_conductor — with a real typed column per field — is generated from that metadata by the compile tool:


go run ./cmd/compile MV_CONDUCTOR      # compile one class by code
go run ./cmd/compile --all             # compile EVERY registered class   (task compile-all)

  
--all enumerates every row in metadata.feature_classes and compiles each into its gis.<code> table. It is idempotent and additive — re-running it brings tables into line with current metadata without dropping data — and it continues past a class that can’t compile, naming the offender loudly rather than aborting the batch.

  
    
    
  • Compile happens after the metadata that defines a class is loaded, and before any instance data for it. That is why bootstrap order is migrate → compile → seed, and why task seed-all runs compile-all between its metadata seeds and its instance seeds.
    • 
    
  • Adding a field to a class already holding data is a compile operation, not a migration. A non-destructive field is added in place by re-running compile; a change that can’t be done in place needs uncompile (drop) then compile (rebuild), which discards that class’s rows (Chapter 6).
    • 
  


  
2.6 Seeding: metadata catalog and example data

  
A freshly-migrated, freshly-compiled database is structurally complete but empty of content. In this repo the whole reseed is one task, task seed-all, which runs in three phases:

  

    
PhaseWhatNeeds

    
1 — metadata / configLoad every class definition, subtype, field, domain, symbology rule, diagram stencil, placement/network/relationship rule, and CIM mapping. Writes only to metadata (and config tables).no compiled gis table needed yet

    
2 — compileA single compile-all: now that all class metadata is loaded, materialise every gis.<code> table.Phase 1 done

    
3 — instance / network dataSeeds that INSERT/UPDATE actual gis.<code> rows — the example feeders, transformers, switches, LV ring network…Phase 2’s tables

  

  
seed-all is idempotent (every seed is ON CONFLICT-guarded; compile is additive). It deliberately excludes the destructive one-off migrations (collapse-rmu-*, migrate-dist-switch-to-mv-switch) and diagnostics: those migrate an existing install forward, not build a fresh one.

  
A boundary worth drawing for production
Phases 1 and 2 give you a working, empty application — the catalog of what a feature can be, with real tables to hold them, but no example assets. Phase 3 is demo network data. On a real deployment an administrator typically wants Phases 1–2 (or a curated subset of the metadata seeds matching the utility’s asset model) and then loads real asset data through the ETL import engine (Chapter 8). task seed-all is the dev path — know which parts you want before pointing it at anything that isn’t a scratch database.

  
Ada, on staging, wants a populated system to demo, so she runs the full task seed-all and gets Feeder 7, TX-Feeder7-014, the Oakwood zone, and the rest of the familiar cast.


  
2.7 Creating the first account

  
Here is the gap the whole chapter has been pointing at: migrations seed roles, but never users. iam.user_roles is empty after migrate. There is no default admin@voltedge with a known password — by design, because a shipped default credential is a shipped vulnerability. A freshly bootstrapped system has a working login screen that nobody can pass. Closing that gap is the job of the out-of-band authadmin tool:


AUTHADMIN_PASSWORD='<strong password>' \
  go run ./cmd/authadmin create \
    --email owen@oakwood.example \
    --name  "Owen — Break-glass Admin"

Identity, authentication & RBAC
Users, identities, roles, the three front doors — and one snapshot behind all of them.

  
Chapter 1 sketched the model; this chapter is the operating manual. It is where Ada spends most of her time: creating the accounts Priya, Tom, and Dana sign in with, giving each exactly the reach their job needs, and understanding — precisely enough to reason about a security question — how the system decides, on every single request, whether the person behind it may do the thing they asked. Two ideas run through everything here, and it pays to hold them apart:

  
    
    
  • Authentication — who are you? Proving identity: a password, a single-sign-on token, a bearer credential. VoltEdge has three front doors (local, SSO, field/bearer) and they all lead to the same room.
    • 
    
  • Authorization — what may you do? Deciding, given a proven identity, whether a specific action is permitted. This is RBAC (which actions) and — Chapter 4 — spatial access (which territories).
    • 
  

  
The elegant part, and the thing to internalise first: authorization never learns how you authenticated. A password login, an Azure AD token, and a field device’s bearer token all resolve to the same SessionUser snapshot carrying the same effective permission set, and every gate downstream reads only that snapshot. Change how someone signs in and nothing about what they can do changes.

3.4 How authorization actually happens, on every request

  
This is the heart of the security model: every gate in the whole API is just this mechanism applied at a mount point. The snapshot (SessionUser, Chapter 1) is built when the session middleware validates a request’s credential and “deliberately carries no password or token material”; handlers read it via UserFrom(ctx), and there is one unexported context key so nothing outside the auth package can forge it.

  
The check — Has is a map lookup, nothing more. Read the five lines literally: there is no if u.BreakGlass { return true }. Owen passes permission checks for the same reason Ada does: his role put every permission string into his Permissions map. (An earlier note calling this a “gap” read it as an oversight; it is the design. Omnipotence over actions comes from the role’s permissions, not a bypass in the check. The column’s powers are about authentication and lifecycle only.)

  
The gate:


func RequirePermission(readPerm, writePerm string) func(http.Handler) http.Handler {
    user, ok := UserFrom(r.Context())
    if !ok { → 401 "authentication required" }            // anonymous
    required := writePerm
    switch r.Method { case GET, HEAD, OPTIONS: required = readPerm }   // method picks read vs write
    if !user.Has(required) { → 403 "…required permission (X)" }
    next()
}

  
    
    
  • 401 vs 403 are distinct and meaningful. No session → 401 (authenticate first). A session that lacks the permission → 403 (you are known, and refused).
    • 
    
  • One gate covers a mixed read/write mount. The HTTP method selects which permission is required, so features mounts with RequirePermission(PermFeaturesRead, PermFeaturesWrite) and a single line correctly lets viewers read and requires editors to write.
    • 
    
  • The permission strings are Go constants, not literals — a gate in main.go references a symbol and can never drift from the seeded permission by a typo.
    • 
  

  
Where the snapshot comes from. On each request loadSession (cookie) or ResolveAPIToken (bearer) builds Permissions from one query:


SELECT DISTINCT rp.permission_key
FROM iam.user_roles ur
JOIN iam.role_permissions rp ON rp.role_id = ur.role_id
WHERE ur.user_id = ?

  
Two consequences: a role change takes effect on the next request (recomputed every time, never cached in the session row — revoke Dana’s editor and her next write is 403), and a permission-load failure fails the request closed. The identical query backs the bearer path (loadPermissionsFor), guaranteeing a token can never do more than its owner. (Interactive 1 in Chapter 1 lets you replay any caller × mount × method.)

  • Recognisable and hashed. Every token is prefixed ve_mcp_ and stored only as its SHA-256; the raw token is shown exactly once at mint and never persisted. A 12-character prefix is kept in the clear for identification in listings.

    • 
  


  
3.6 Sessions, CSRF, and the response-header baseline

  
    
    
  • Opaque, server-side sessions. A login mints 256 bits of random token, stores only its SHA-256, and hands the raw token to the browser in a cookie once. There is no JWT — validity is a database lookup, so revocation is instant.
    • 
    
  • Two expiry windows. A sliding idle window (SESSION_IDLE_TIMEOUT, default 12h) that every valid use pushes forward, and a hard absolute cap (SESSION_ABSOLUTE_MAX, default 720h/30d) that no activity can extend. A session dies at whichever comes first.
    • 
    
  • Cookie hardening. HttpOnly, SameSite=Strict, host-scoped, and Secure unless AUTH_INSECURE_COOKIES=1. A companion CSRF cookie is intentionally not HttpOnly — the SPA reads it to echo in a header — but it is useless without the session cookie.
    • 
    
  • Defense-in-depth CSRF. RequireCSRF guards state-changing methods with two independent checks on top of SameSite=Strict: Sec-Fetch-Site/Origin must be same-origin, and the X-CSRF-Token header must equal the session’s token, compared in constant time.
    • 
    
  • A baseline of security headers on every response (SecurityHeaders): X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer, Cross-Origin-Opener-Policy: same-origin, and — only over TLS — HSTS.

Spatial access control
Where may you do it? Two trees, one recursive query, and a switch that ships OFF.

  
Chapter 3 answered what may you do? — the action axis. This chapter answers the second, orthogonal question: where may you do it? A utility does not want every editor able to edit every asset across the whole service area. Dana maintains the Oakwood district; she should be able to edit Oakwood’s features and see Oakwood’s map, and neither edit nor even see a feeder three regions away that another crew owns. That is spatial access control — territory scoping — a completely separate mechanism from RBAC, ANDed on top of it.

  
    
    
  • RBAC (Chapter 3) decides the verb: may you write features at all?
    • 
    
  • Spatial access (this chapter) decides the place: of the features you may write, which are in territory you hold?
    • 
  

  
A write succeeds only when both pass. Take either away and the write is refused — a 403 from RBAC if she lacks features:write, a 403 (or an invisible feature) from spatial access if the feature sits outside her territories. One framing decision governs everything: spatial enforcement ships OFF. A fresh install applies no territory predicate anywhere. Scoping is a capability an administrator rolls out deliberately (§4.7) — the “off” default is itself a load-bearing design choice.


  
4.1 The two trees

  
Spatial access is computed from two independent hierarchies that meet at the user:


   TERRITORY TREE (gis.territories)          ORG TREE (iam.users.manager_id)
   cascades DOWN ▼                            cascades UP ▲

   Region  ──────────────┐                    Ada (region manager)
     └─ Zone             │  a grant here            ▲
         └─ District  ◄──┘  covers the         Tom (zone lead)
             └─ (features)   whole subtree           ▲
                                               Dana (district crew)

  
    
    
  • The territory tree (gis.territories) cascades down. Territories nest — a Region contains Zones, a Zone contains Districts, each row pointing at its parent_id, each at a level (from the ranked gis.territory_levels). A grant on a node covers that node and its entire subtree. You never grant a subtree explicitly — you grant the node and the subtree is expanded at resolve time.
    • 
    
  • The org tree (iam.users.manager_id) cascades up. A manager inherits the union of every territory grant held by everyone who reports up to them, transitively. Grant Dana the Oakwood District, make Tom her manager, and Tom sees Oakwood without a grant of his own.
    • 
  

  
The genius of composing these two trees: an administrator rarely has to grant territory to managers at all. Grant the people at the edge — the crews who actually own ground — and the management chain inherits the union by virtue of the org chart. Change a manager_id and everyone’s effective reach re-derives on the next request. A user can hold grants and no reports, reports and no grants (a pure manager), both, or neither (scoped to nothing — fail-closed, §4.6).


  
4.2 How a feature acquires a territory

  
Before scoping can filter by territory, every feature needs a territory_id — assigned at write time, automatically, by point-in-polygon. territory.Assign is the single entry point the CRUD engine calls on every create and every geometry-changing update:

  
    
    
  • Automatic (the normal path). With no override, Assign resolves the deepest territory whose boundary contains the feature’s centroid (ResolveContaining) and stores that node’s id. A qualifying match is stored even when enforcement is off — that is how coverage gets populated before the rollout flip.
    • 
    
  • Explicit override. A caller may name a territory directly. It is validated to exist and to be at least the minimum feature level, always — independent of the enforcement flag. An override is not required to spatially contain the feature: it exists for when the boundary is missing or imperfect and a human asserts membership.
    • 
    
  • The minimum-level rule. A feature must belong to at least a configured minimum level (e.g. “at least a District,” never merely a whole Region).
    • 
  

  
The enforcement flag governs only the failure case of the automatic path. With enforcement off, “no territory covers this location” or “only a too-shallow one does” leaves the feature unassigned (territory_id = NULL) — the write still saves. With enforcement on, the same situation rejects the write with a 400 (“this location isn’t within any "District" — no territory covers it”). Click the map:

Resolving Dana: reports = {Dana}, granted = {Oakwood District}. The empty result is fail-closed: a user with no grants and no (granted) reports yields an empty slice, and the enforcement layer treats empty as “match nothing,” never “no filter” — the single most important safety property.

  
Caching. Tiles arrive in bursts, and each resolves the session. CachedEffectiveIDs wraps EffectiveIDs in a process-local, 60-second TTL cache keyed by user (see the cache line in the widget). The TTL is only a backstop — grant and manager mutations call InvalidateAll for true instant revocation. A sibling primitive: access.Subordinates walks the same org tree down (transitive reports, excluding the user) to feed private-draft visibility (Chapter 8); it shares the cache and the flush.


  
4.5 The bypass: territories:unscoped

  
Some accounts must see and edit everything, regardless of grants — an administrator authoring across the whole network, a break-glass operator in an emergency. That is the territories:unscoped permission (access.PermUnscoped), seeded by migration 0094 to the admin and break-glass-admin roles. In loadScopeFields:


if _, ok := perms[access.PermUnscoped]; ok {
    return nil, true, nil, nil   // Unscoped=true; skip the resolver entirely
}
allowed, err = access.CachedEffectiveIDs(...)   // scoped user: resolve the set

  
An unscoped holder skips the resolver entirely — correct (confined to nothing) and fast. Note the layering that keeps packages decoupled: the unscoped check lives in auth, so package access never imports auth. Because admin/break-glass-admin are unscoped, Owen inherently sees every private draft and every out-of-territory feature — not special-casing, but because scoping is simply switched off for him at the resolver. (Switch Acting as to Ada and resolve Tom: her own scope would be skipped, but Tom’s is still computed.)


  
4.6 Enforcement at request time

  
Resolving the set is half the story; applying it is the other half. Enforcement lives at each read/write site (crud.readScope), and is a complete no-op unless every condition holds. It applies no predicate when any of these is true: enforcement is switched off · the class is geometry-less (no territory_id column) · the user is unscoped · there is no session on the context (an internal, non-HTTP caller; every real HTTP read arrives behind the session middleware). When it does apply:

  
    
    
  • List / query reads append territory_id::text IN (?, ?, …) for a non-empty set, or — critically — 1 = 0 for an empty set. An empty effective set matches no rows: fail-closed, in SQL.
    • 
    
  • GET-by-id (enforceReadScope): a feature outside the user’s set — including a feature with no territory_id at all — returns notFound, not forbidden. Hiding an out-of-scope feature as “not found” avoids leaking that the id even exists.
    • 
    
  • Writes (enforceWriteScope): the feature’s resolved territory must be in the user’s set, else forbidden (403) — a write names a specific feature the user is acting on deliberately.
    • 
  

  
And enforcement is not only CRUD — the same effective set drives the predicate in trace, export, and map tiles, so a scoped user cannot route around the filter by tracing a network, exporting a region, or reading vector tiles. (Replay it in Interactive 1: tick “territory enforcement on” and pick a feature in another district.)

05
The break-glass administrator
Three bypasses, an audit trail, and the discipline of holding them.

  
Every prior chapter described the system as it runs when things work. This chapter is about the day things don’t — the SSO provider is down and no one can sign in, a configuration change has locked the administrators out, the account catalog itself is corrupt. For those days there is Owen, and the account he holds: the break-glass administrator. The name is the metaphor: a fire-alarm behind glass you break only in an emergency, whose use is loud, logged, and never routine. Owen’s account is not “a more powerful admin.” It is a deliberately narrow set of bypasses that let a trusted human get back in and turn the lights back on when the normal doors are all shut — nothing more.

  
Break-glass is a property of an account (the break_glass column), not a set of permissions and not a role.


  
5.1 What the break_glass column is — and is not

  
Mechanically, break-glass is one boolean column on iam.users, surfaced as SessionUser.BreakGlass. It is worth stating the negatives as sharply as the positives, because almost every misconception is a confusion of the column with something else:

  
    
    
  • It is not permissions. The column puts nothing into the Permissions map. A break-glass account with no role Has() nothing and is refused by every RequirePermission gate.
    • 
    
  • It is not a role. break-glass-admin (the role) and break_glass (the column) are different things that share a word. The role is permission-identical to admin; the column is the three bypasses below. You can hold either without the other.
    • 
    
  • It is not spatial omniscience. Owen sees every territory and private draft because of the territories:unscoped permission his role carries, not the column. Strip his role and he is scoped like anyone else (and, having no permissions, can do nothing anyway).
    • 
    
  • It is not an environment variable. There is deliberately no BREAK_GLASS_* env var. Break-glass status is data — set through the provisioning tools, auditable in the database, revocable by clearing the column.
    • 
  

  
So the mental model is a two-part identity: a fully-functional break-glass admin like Owen is column + role — the role makes him omnipotent over actions and unscoped over territory (the same powers Ada has), and the column adds the three recovery bypasses (which Ada does not have).


  
5.2 Power 1 — the local-login bypass

  
The problem it solves. A security-conscious deployment often switches off local password login entirely and forces everyone onto SSO. That is good posture — until the SSO provider has an outage. Now no one can sign in, including every administrator. Someone has to be able to get in and turn local login back on. That someone is a break-glass account. Inside authenticateLocal, before the password is even checked:


allowed := user.BreakGlass
if !allowed {
    on, _ := s.localAuthEnabled(ctx)   // consult the org-wide switch
    allowed = on
}
if !allowed {
    _, _ = verifyPassword(password, dummyArgon2idHash)   // spend the time anyway
    → 403 "local password sign-in is currently disabled; use SSO or contact an administrator"
}

  
For an ordinary account, local login is permitted only if the local_auth_enabled switch is on. For a break-glass account, allowed is true from the first line — it never consults the switch at all.

  
    
    
  • The check is before the password, and timing-flat. The bypass decision happens before verifying the password, so a disabled-local policy never becomes a password oracle — and the code still spends the hash time on the reject path.
    • 
    
  • The switch is fail-closed. localAuthEnabled treats a missing or unparseable local_auth_enabled row as off. Only the break-glass bypass is immune to that default.
    • 
    
  • It is audited under its own event. A successful break-glass login writes break_glass_login to iam.auth_events, distinct from the ordinary login_success.
    • 
  


  
5.3 Power 2 — the auth-settings bypass

  
The problem it solves. Once Owen is in during an SSO outage, he needs to actually fix the situation — turn local login back on for everyone. Toggling that switch normally requires admin:auth-settings. But a break-glass account must work even when it holds no role. So the toggle has its own bypass. setLocalAuthHandler (POST /auth/settings/local-auth):


if !user.BreakGlass && !user.Has(PermAuthSettings) {
    → 403 "you do not have permission to change this setting"
}
// …then flip local_auth_enabled and record who did it

  
The authorization is BreakGlass OR Has("admin:auth-settings"). Ada flips it via her permission; Owen flips it via the column, needing no permission at all. Power 1 gets Owen through the door; Power 2 lets him change the setting even with no role. Every toggle is recorded: setLocalAuthEnabled stamps updated_by with Owen’s id and the handler writes a local_auth_toggled audit event with the direction.


  
5.4 Power 3 — the factory-reset survivor

  
The heaviest power belongs in full to Chapter 6; here is the shape. The out-of-band resetdata tool performs a factory reset — wiping operational data back to a clean slate while preserving configuration. The break-glass account plays two roles: it is the authorization gate (resetdata calls auth.VerifyBreakGlassAdmin(email, password) and refuses to run unless it succeeds — an ordinary admin, however privileged, cannot invoke it) and it is the sole survivor (the reset reduces the user table to that single break-glass admin). VerifyBreakGlassAdmin Argon2id-verifies the password and requires break_glass == true and status == active, and fails closed and opaque: a missing user, a non-break-glass account, a disabled account, a missing local identity, and a wrong password all return the identical "break-glass authentication failed".

5.6 Creating and provisioning a break-glass account

  
Created the same two ways any account is, with one hard rule on both paths: a break-glass account must have a local password.

  
    
    
  • Out of band — authadmin create (Chapter 2). How the first one is born. create defaults --break-glass=true and --role admin. Password from AUTHADMIN_PASSWORD.
    • 
    
  • Inside the system — POST /auth/admin/users with break_glass: true, by an existing admin (try it in Interactive 6).
    • 
  

  
The API rejects break_glass without a password; the reason is definitional — an account with no local credential could never exercise Power 1. Because these credentials bypass the switch, they are held to a higher bar: a 12-character minimum (minLocalPasswordLen). To revoke break-glass status, clear the column — there is no env var to unset, no infrastructure secret to rotate. It is data.


  
5.7 The audit trail

  
Every relevant action lands in iam.auth_events, the append-only security audit log: break_glass_login (distinct from login_success — the line a security review looks for: who used the break-glass account, when, from what IP?), local_auth_toggled (every flip, with direction and actor, so “turned local auth on … then off again” is a legible pair), and login_denied (the policy refusal). Two properties to rely on: the log is append-only, and audit writes are best-effort — a failure to write an audit row must never change the outcome of the action being audited. You would rather complete an emergency login and miss one audit row than have a flaky audit table block the emergency login; so the audit log is a strong-but-not-cryptographic record.


  
5.8 Operational discipline

  
    
    
  • Keep the holders few, and separate from daily admin. Owen’s break-glass account should be distinct from his everyday admin account, keeping routine work out of the break_glass_login stream.
    • 
    
  • Guard the password like an infrastructure secret. Store it where infrastructure secrets live — a sealed vault, an offline record — not alongside routine logins, and never in .env.
    • 
    
  • Consider the “cold” configuration. A break-glass account without the admin role can restore access while being authorized for nothing else — a smaller blast radius, at the cost of a second step to actually fix things once in.
    • 
    
  • Treat every break_glass_login as an event to explain. A break-glass login with no corresponding incident is a red flag; wire that event into alerting.
    • 
    
  • Rehearse the runbook before you need it. The SSO-outage recovery should be a written, tested procedure, not something worked out under pressure.
    •

    6.1 resetdata: the operator’s view ▶
    
  
    There are only a few moments when a factory reset is the right instrument, and all share a shape: the configuration is good, but the data is not, and you want to start the data over without rebuilding the system.

    Three weeks of pilot on the real deployment: the catalog is exactly what they want to keep; the pilot’s features, outages, attachments, and evaluator accounts are exactly what they want gone. A migrate-and-reseed would destroy the tuned configuration too.

    A bad bulk import or a test leaking into live tables, with a clean external source to reload from. Reset to an empty-but-configured system and reload rather than un-pick the damage.

    Handed to a different team: configuration (months of modelling) stays; operational data and everyone’s accounts go, leaving one controlled survivor to re-provision from.

    6.3 The authorization gate ∑

    1. Look up the user by (lowercased, trimmed) email. No row → fail.
      2. 
    
    2. Find that user’s local identity (provider = 'local'). No local identity, or a NULL password hash → fail. (A pure-SSO account cannot authorise a reset — and the reset path is exactly the path you take when SSO may be unavailable.)
      3. 
    
    3. Verify the supplied password against the stored Argon2id hash.
      4. 
    
    4. Require all of: password OK and user.BreakGlass and user.Status == "active".
      5. 
  
    
  
    Every failure returns the same opaque string — "break-glass authentication failed" — and the function returns the surviving user’s id.     6.5 The mechanics of the wipe ∑
    
  
    With --yes, the work happens in a strict order designed so that every partial-failure outcome is safe (recoverable by re-running) rather than corrupt. Assembling the targets: the fixed staticDataTables slice (~24 operational/audit tables) plus the dynamically discovered compiled feature tables. Each value read from physical_table is checked against a strict regex before it can reach a TRUNCATE:
    

    var gisTableRe = regexp.MustCompile(`^gis\.[a-z0-9_]+$`)
if !gisTableRe.MatchString(t) {
    return nil, fmt.Errorf("refusing to truncate suspicious physical_table %q", r.PhysicalTable)
}
if t == "gis.territories" || t == "gis.territory_levels" { continue }   // config, even though it lives in gis
    
  
    The transactional wipe. Everything destructive to the database happens inside a single RunInTx: either the database ends up wiped-and-reduced, or nothing changes. Three statements, in order:
    
  
      
    
    1. Truncate the data set: TRUNCATE TABLE <targets…> RESTART IDENTITY CASCADE. RESTART IDENTITY resets the bigserial counters. CASCADE is bounded: no KEEP (config) table has a foreign key referencing any table in the data set, so the cascade can only reach FK-children already in the target set. It physically cannot climb into configuration — the structural guarantee behind §6.2.
      2. 
    
    2. Release the one blocking FK: UPDATE iam.system_settings SET updated_by = NULL WHERE updated_by IS NOT NULL AND updated_by <> <survivor>. It is the single FK into iam.users on a kept table with no ON DELETE rule; if a doomed account last touched a setting, that reference would block the deletion below.
      3. 
    
    3. Reduce the accounts: DELETE FROM iam.users WHERE id <> <survivor>. CASCADE clears each deleted user’s identities, roles, tokens and territory grants; SET NULL detaches audit/manager references.
      4. 
  
    
  
    The object-store purge, deliberately last. Only after the DB transaction commits does the tool purge the blob store (store.Purge(ctx) lists the bucket recursively and removes every object). The ordering is a correctness argument: if the DB commit succeeds but the purge fails, the worst case is orphaned blobs — objects with no surviving row pointing at them — which a re-run clears. The reverse order could leave files.attachments rows pointing at deleted blobs. The tool chooses the recoverable failure mode, and its messages say exactly this: “data wiped, but object-store purge failed … (blobs may remain, re-run to finish)”. (Tick “purge fails” in the widget, then run with --yes twice.)

    6.8 uncompile: the surgical drop ▶∑
    
  
    uncompile drops one feature class’s physical table and returns that class to draft. Where resetdata clears all data and keeps all config, uncompile clears one class’s data and its compiled table, keeping the class’s definition so it can be rebuilt.
    
  
    Why it exists. The compiler is additive-only: it can ALTER TABLE ADD COLUMN a new field, but never rewrites the table. One blind spot: you cannot add a required (NOT NULL) field to a class that already has rows — Postgres rejects it (SQLSTATE 23502). The recovery is to drop the table and recompile fresh; uncompile is the “drop the table, keep the class” step so nobody hand-writes DROP TABLE, remembers the Martin tile function, and resets metadata columns by hand.     compiler.Uncompile does all of this in one transaction:

      •

Two differences from resetdata: uncompile has no break-glass gate (a metadata-admin recovery tool, run against DATABASE_URL like compile) and no dry run — its safety comes from being surgical and from printing the row count it discarded. The same operation is exposed in the running system at POST /admin/feature-classes/{code}/uncompile behind metadata:write.
    

  
    6.9 Discipline for both tools
    
  
      
    
    • Plan or count before you commit. For resetdata, always run the dry run and confirm your config tables are absent from it. For uncompile, read the row count in the output; if it surprises you, stop and back up.
      • 
    
    • Export anything that must survive. resetdata erases the audit trail and every non-survivor account; uncompile discards a class’s rows. Neither has an undo.
      • 
    
    • Treat access to these tools as access to destruction. Anyone who can reach a shell with DATABASE_URL (and, for resetdata, a break-glass password) can run them — which is why break-glass passwords are held by few, rotated, and monitored.

    The definitions that make VoltEdge this utility’s GIS — additive, then compile.
    
  
    Chapter 6 spent a lot of care describing what resetdata preserves. All of it is authored, day to day, by an administrator like Ada through one API surface and its matching admin screens.

    7.1 The one rule: additive, then compile ▶
    
  
    The metadata admin API is additive. You can add a subtype, a field, a domain value, a rule — and each addition is real and safe even on a class already compiled and holding thousands of rows. What you (mostly) cannot do is destructively rewrite: rename a field, change its data type, or edit/remove a subtype, because those would silently invalidate data sitting in the physical table. The package header states the doctrine precisely:
    
  
    Adding a subtype to an already-compiled class, a value to an already-referenced coded domain, or a new field to an already-existing class, is real and safe. Editing or deleting a subtype is still fully unsupported (no endpoint at all)… What’s still genuinely unsupported: renaming or retyping a field, and editing/removing a subtype.
    
  
    The reason is the compiler’s shape (Ch 2 §2.5, Ch 6 §6.8): it is additive-only DDL. So the admin API only exposes edits the compiler can carry out. This produces the two-step rhythm of catalog work:
    
  
      
    
    1. Change the metadata (add the field / subtype / domain value). Instant, transactional, touches only metadata.* — the physical gis.<code> table does not change yet.
      2. 
    
    2. Recompile the class (POST /admin/feature-classes/{code}/compile) to materialise the change — ADD COLUMN the new field, widen the domain CHECK, and so on.
      3. 
  
    
  
    Between the two steps the addition is authored but not enforced — the seam that lets an administrator stage several changes and compile once.     7.4 Evolving a compiled class ∑
    
  
    Once MV_RECLOSER is live and holds rows, changes obey the additive doctrine. The three real, safe evolutions:
    
  
      
    
    • Add a subtype — real on any status; recompile to enforce (the subtype CHECK widens on compile).
      • 
    
    • Add a field — real on any status; recompile to add the column. If the new field is required and the class already has rows, this is the one case the additive compiler cannot do — the uncompile/compile path from Chapter 6 (use the required field button above).
      • 
    
    • Edit a field in place — PATCH /feature-classes/{code}/fields/{name}. The subtle one.
      • 
  
    
  
    Which field edits are legal. updateField accepts changes only to properties that are read live from metadata.fields by whatever consumes them and are never baked into the physical column: domain_code, group_code, nullable, the three form-visibility flags, and required_for_subtypes. Because they are consulted at runtime, editing them in place is real and safe — and required_for_subtypes takes effect live, no recompile. What is absent from updateFieldRequest entirely is name and data_type: you cannot rename or retype a field. Those are the physical column. The endpoint doesn’t offer them — the impossibility is expressed as a missing capability, not a runtime error. If you truly must, the recovery is uncompile → re-author → compile. The header even documents one benign inconsistency: flip a field to nullable while the column still enforces NOT NULL and they disagree until a recompile — it fails safe: a genuinely-null write passes the Go check but Postgres rejects it (a raw 500), never silent data loss.
    
  
    What has no endpoint at all: editing or deleting a subtype. A subtype is woven into per-row data and per-field required-sets; no safe in-place rewrite exists. The absence of the endpoint is the safety guarantee.
    

  
    7.5 Domains and coded values ∑
    
  
    A domain is a reusable constraint — a coded list (OH_CONDUCTOR_MATERIAL = {ACSR, AAAC, COPPER}) or a numeric range — that any field on any class can point at.
    
  
      
    
    • Add a value — POST /domains/{code}/values. Safe even on a domain already referenced by compiled classes; recompile any class using it to enforce the widened CHECK. Until then the value is authored but the physical CHECK still rejects it.
      • 
    
    • Edit a value’s display — PATCH /domains/{code}/values/{value_code}. label / sort_order (and the material_spec_code link) is always safe with no recompile — pure display/link metadata, never part of the CHECK.
      • 
    
    • Delete a value — DELETE /domains/{code}/values/{value_code}. Authored the same way; recompile to narrow the CHECK. If existing rows use the deleted value, that recompile fails loudly rather than silently deleting real data — forcing you to deal with the affected rows first.
      • 
  
    
  
    Domains themselves: PATCH (name, or a range’s min/max), and DELETE guarded — refused if any field still references the domain. The guard-on-delete pattern recurs across the catalog: field groups, material specs, and symbology icons all refuse deletion while something points at them, so you can never orphan a reference by deleting its target.
    

  
    7.6 Field groups and material specs ∑
    
  
      
    
    • Field groups (/field-groups) are the section headings on the attribute panel — “Electrical”, “Construction”, “Inspection”. A field’s group_code (editable live) files it under one. Purely organisational; deletion is guarded.

    • Material specs (/material-specs) are the engineering data sheets — ACSR_50 with its resistance-per-km, ampacity, reactance. A coded domain value can carry a material_spec_code, so selecting “ACSR” on a conductor pulls in a whole sheet of numbers — the bridge between the catalog and the engineering studies: the power-flow and fault engines read these specs to turn a coded material into ohms.
      •

    7.11 Discipline for catalog work
    
  
      
    
    • Remember the seam: add, then compile. An added field/subtype/domain-value is authored the instant you save it, but not enforced until you recompile.     r.With(auth.RequirePermission(auth.PermFeaturesRead, auth.PermFeaturesRead)).Mount("/export", export.Routes(db, exportStore))

    8.4 Private drafts and pending edits ▶∑
    
  
    The subtlest data-lifecycle concern is not moving data but deciding who can see which version of it. VoltEdge has a two-phase model for private, in-progress work:
    
  
      
    
    • Phase A — never-published drafts. A feature that has never been public is private to its author and the author’s management chain: a viewer sees it only when its created_by is the viewer or one of the viewer’s subordinates. “Never been public” is status = 'draft' AND published_at IS NULL; the public test is status = 'published' OR published_at IS NOT NULL (belt-and-suspenders). This is a filter: a WHERE predicate that hides rows.
      • 
    
    • Phase B — pending edits over published features. A scoped user’s private edit or delete of an already-published feature is different in kind. The base gis.<code> row stays public and untouched; the author sees a different version, their pending change overlaid — an actor-dependent value substitution, not a filter. The overlay is display-only (v1): it shows in the author’s own reads but does not participate in WHERE/ORDER BY. Stored in runtime.feature_pending_edits, keyed by (feature_class_code, feature_id, author_id), with a patch envelope, optional changed geometry, an is_delete flag, and a base_version conflict token.
      • 
  
    
  
    A crucial scoping difference: Phase A visibility includes subordinates (a manager can see a report’s orphaned draft — recovery matters), whereas Phase B overlays the viewer’s own edits only — a pending edit is a private workspace over a row a manager already sees fine as its public version, and viewer-own-only sidesteps “two authors edited the same feature, whose overlay wins?” entirely.
    
  
    What the administrator controls. Both phases compose with — never replace — the Chapter 4 territory predicate: a private draft is visible only to an authorised author AND within the viewer’s territory scope. Both are gated by one rollout switch, private_drafts_enabled in iam.system_settings, which behaves exactly like the territory-enforcement flag: off by default (missing/unparseable = off; only "true" turns it on) and retroactive when flipped — turning it on privatises every never-published feature to its author chain at once. The switch lives at /private-drafts (features:read to view / metadata:write to flip).

    8.5 The audit trail ∑
    
  
    Every security-relevant authentication event lands in iam.auth_events, the append-only audit log. Two design properties matter: it’s best-effort and never blocks the audited action (logEvent ignores the write’s effect on control flow — a login succeeds even if the audit insert fails; a very good record, not a cryptographically guaranteed one), and the event vocabulary is a fixed constant set:
    
  
    
    
    EventMeaning

    login_failurewrong credentials (the generic-failure path from Chapter 3)
    
    
    login_deniedpolicy refusal: local auth is off and the account is not break-glass

    8.6 One more inbound path: the field-sync review queue
    
  
    Bulk import is not the only way data arrives. The Flutter field app syncs offline edits into ops.sync_inbox, and when a class is configured for review, those edits wait in a review queue an admin works before they become system-of-record. That surface is /sync-review, gated sync:review to view the queue and policy / sync:post to post, reject, or set a class’s policy — a distinct permission pair so reviewing and posting can be separated. It’s the QA face of field data; the field app and its sync model are the handbook’s territory, so this chapter only flags it as the third way (after interactive edits and ETL import) that features enter the system.
    

  
    8.7 Discipline for the data lifecycle
    
  
      
    
    • Deploy the workers, and tune their env. Imports and exports are inert without cmd/importworker and cmd/exportworker running alongside the API. Set EXPORT_RETENTION deliberately — the default reaps downloads after a week.
      • 
    
    • Dry-run every import; read the error report. The dry run writes nothing and runs the real validation. If a load reports failures, the capped per-row report (≤500) tells you which rows and why — fix the source, re-stage, re-run.
      • 
    
    • Treat the rollout switches as retroactive, one-way-feeling events. Flipping private_drafts_enabled (or territory enforcement) instantly changes what everyone sees. Announce it, and remember admins/break-glass read past both filters — so test visibility as a scoped user, not as yourself.
      • 
    
    • Export the audit trail before a factory reset. It is the one piece of history a reset destroys that you cannot reconstruct.
