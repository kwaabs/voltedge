VoltEdge guide · Deploying on Kubernetes & Coolify · beyond single-host Compose

Same images.
Different orchestra.

Two concrete ways to run the production stack once docker-compose.prod.yml on one host is no longer enough: Coolify, a self-hosted PaaS that wraps Compose, and Kubernetes, the stack decomposed into native objects with autoscaling, self-healing and operator-managed Postgres. This edition lets you run the arithmetic the manifests depend on: connection budgets, HPA and rolling-update timelines, probe timing against the real health endpoints, queue-depth autoscaling, and a bootstrap sequencer that refuses wrong orderings.

Use As in the top bar. Platform admin can build, apply, scale, roll back, exec and touch secrets. On-call can scale, roll back, exec and read, but not apply new manifests or edit secrets. Developer can build and push images and read, but cannot change the cluster. Auditor can only read. These are operator roles for this guide, not VoltEdge RBAC roles: VoltEdge’s own roles (for example the admin role that authadmin create assigns) live inside the application, while these personas model who holds cluster / Coolify access.

Who this is for

Platform and operations engineers taking VoltEdge past a single Docker host. Read the Production Setup Runbook first: the migrate, seed and first-admin logic is identical here, only the mechanics change. The Deployment & Scaling Guide explains why the numbers (pool sizes, replica counts) are what they are.

Both platforms build images (neither can bind-mount a host-built web/dist), so both use the portable web image (web/Dockerfile, bakes the SPA) and the migrate image (deploy/migrate/Dockerfile, bakes the migrations). The nginx config stays external (a mount on Coolify, a ConfigMap on Kubernetes) because the load-balancing strategy differs between the two.

Part A: Coolify
A self-hosted PaaS that wraps Docker Compose.

  
Coolify (v4) runs Docker Compose under the hood, so docker-compose.prod.yml is most of the work. This chapter walks the deployment end to end.

  
A1. How Coolify is organised

  
    
    
  • Server: a host Coolify manages over SSH (the one it runs on, plus any you add). Docker runs here.
    • 
    
  • Project → Environment: a grouping (project VoltEdge, environment production).
    • 
    
  • Resource: the deployable unit. Yours is a Docker Compose resource built from your Git repo. Databases can also be their own managed resources (A3).
    • 
    
  • The proxy: a Traefik (or Caddy) proxy per server that terminates TLS, provisions Let’s Encrypt certs and routes a domain to a service. You never touch cert files.
    • 
  

  
The flow: install Coolify → (optionally) create a managed Postgres resource → create the Compose resource from Git → set env + domains → deploy → bootstrap the DB → turn on backups and auto-deploy.

  
A2. Prerequisites & installing Coolify

  
    
    
  • A server: 8 vCPU / 16 GB / SSD is a sane start for a few hundred users (give Postgres the bulk). Fresh Ubuntu 22.04/24.04 works. Sizing is the guide’s recommendation; the repo does not benchmark it.
    • 
    
  • Two DNS A-records at the server’s IP: gis.example.com (app) and storage.example.com (presigned URLs, A8).
    • 
    
  • Install: curl -fsSL https://cdn.coollabs.io/coolify/install.sh | bash, then open http://<server-ip>:8000, create the admin account. The server registers itself as localhost; add others via Servers → Add Server. (Coolify steps are from the guide; not verifiable in this repo.)
    •

A4. Adapt the compose for Coolify (web image, no host mounts)

  
Coolify builds images; it will not run npm run build for a bind-mount, so ./web/dist would be empty. Create docker-compose.coolify.yml (it does not exist in the repo yet):

  
# docker-compose.coolify.yml -- overrides for Coolify (web image, Coolify proxy).
services:
  nginx:
    build:
      context: ./web          # bakes the SPA (web/Dockerfile)
      dockerfile: Dockerfile
    volumes: !override        # REPLACE the base list; a plain list MERGES by mount target
      - ./infra/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    ports: !reset []          # Coolify's proxy fronts this service

  
Correction to the original manual. The original override listed only the nginx.conf mount under volumes:. In Compose, multiple files merge volume lists by container mount path, so the base file’s ./web/dist:/usr/share/nginx/html:ro would survive and shadow the baked SPA with an empty directory. !override replaces the list; !reset/!override need a recent Compose v2 (2.24+). This follows the Compose merge rules; it was not run here. Try it in Interactive 3.

  
The base file also keeps image: nginx:1.27-alpine on that service; with build: added, Compose will tag the built image with that name on the build host. Add image: voltedge-web:coolify to the override if that bothers you. not verified

  
The infra/nginx/nginx.conf resolver trick uses Docker’s 127.0.0.11 DNS, which Coolify honours (it is Docker underneath), so the config works unchanged: the same /api strip, /tiles keep, SPA fallback and replica load-balancing as on raw Compose.

A6. Environment variables & secrets

  
Coolify → the resource → Environment Variables, stored encrypted; do not commit a .env. Paste, with production values:

  
# Postgres (Option 1: in-compose)
POSTGRES_PASSWORD=<openssl rand -base64 24>
POSTGRES_DB=postgres

# Object storage (RustFS)
RUSTFS_ACCESS_KEY=<strong>
RUSTFS_SECRET_KEY=<strong>
RUSTFS_BUCKET=voltedge-exports
RUSTFS_CORS_ORIGINS=https://gis.example.com
RUSTFS_PUBLIC_ENDPOINT=storage.example.com      # browser-reachable storage host (A8)
RUSTFS_PUBLIC_USE_SSL=1

# Auth / sessions  --  THESE MATTER
# Do NOT set AUTH_INSECURE_COOKIES (must be 0/unset in prod; Coolify gives HTTPS).
SESSION_IDLE_TIMEOUT=12h
SESSION_ABSOLUTE_MAX=720h

# Encryption for stored external-system credentials (only if you use external links)
EXTERNAL_SYSTEMS_ENCRYPTION_KEY=<openssl rand -base64 32>

# Logging
LOG_FORMAT=json
LOG_LEVEL=info

# PgBouncer sizing (the pgbouncer service in the base compose)
PGBOUNCER_POOL_SIZE=25
PGBOUNCER_MAX_CLIENT_CONN=1000

# Replica counts
API_REPLICAS=3
EXPORTWORKER_REPLICAS=1
WEBHOOKWORKER_REPLICAS=1
IMPORTWORKER_REPLICAS=1

# SSO (optional) -- redirect https://gis.example.com/api/auth/oidc/<provider>/callback
#OIDC_AZURE_TENANT_ID=
#OIDC_AZURE_CLIENT_ID=
#OIDC_AZURE_CLIENT_SECRET=

  
Correction to the original manual. A Coolify variable only reaches a container if the compose file references it. docker-compose.prod.yml wires POSTGRES_*, RUSTFS_ACCESS_KEY/SECRET_KEY/BUCKET/PUBLIC_ENDPOINT, RUSTFS_CORS_ORIGINS (into rustfs as RUSTFS_CORS_ALLOWED_ORIGINS), PGBOUNCER_* and the *_REPLICAS, but not RUSTFS_PUBLIC_USE_SSL, SESSION_*, EXTERNAL_SYSTEMS_ENCRYPTION_KEY, LOG_* or OIDC_*. The practical failure: without RUSTFS_PUBLIC_USE_SSL=1 inside the container, presigned URLs are signed for http:// and the browser blocks them as mixed content (the code reads os.Getenv("RUSTFS_PUBLIC_USE_SSL") == "1" in api/internal/export/storage.go). Add the missing ones to the override’s environment: blocks. Audit yours in Interactive 4. The OIDC provider key for Azure is azuread and its redirect URL comes from OIDC_AZURE_REDIRECT_URL (also add Google: OIDC_GOOGLE_CLIENT_ID/SECRET/REDIRECT_URL).

A7. Persistent storage

  
In Option 1 the postgres_data and rustfs_data named volumes carry your database and object store. Coolify preserves named volumes across redeploys, but confirm them under the resource’s Storage tab and mark them persistent. If you ever “Delete + redeploy” the resource, volumes can be removed: snapshot first.

  
A8. Domains & TLS

  
    
    
  1. On the nginx service set the domain https://gis.example.com. Coolify writes the Traefik labels, routes to nginx:80 and issues a cert. (Some versions expose SERVICE_FQDN_NGINX instead of a UI field.)
    2. 
    
  2. On the rustfs service set https://storage.example.com routing to port 9000: this is what presigned upload/download URLs hit (A6 set RUSTFS_PUBLIC_ENDPOINT to match).
    3. 
    
  3. Leave every other service without a public domain (api, workers, pgbouncer, postgres, bootstrap are internal; the SPA reaches the API through nginx’s /api). Note mcpserver and fieldsync publish host ports in the base file (3705, 3706); close those at the firewall unless devices need them.
    4. 
  

  
Result: two proxies by design: Coolify’s Traefik (TLS + domain) in front of our nginx (SPA + /api//tiles split + replica balancing). Because Coolify serves HTTPS, secure cookies work.

  
A9. Deploy, then bootstrap the database

  
    
    
  1. Deploy. Watch the log; wait until postgres is healthy and the stack is up (the api healthcheck is wget -qO- http://127.0.0.1:8080/healthz).
    2. 
    
  2. Migrate: Coolify Terminal into bootstrap: bash /workspace/migrations/apply.sh. It has psql, the repo and a direct connection to Postgres (DDL wants a stable session, not a pooled one). The script skips anything in ops.migration_log, so re-running is safe.
    3. 
    
  3. Seed: restore a validated dump (runbook §6b), not 100 hand-run seeds: pg_restore --no-owner -d "$DATABASE_URL" /workspace/seeded.dump. The runbook then says to re-run migrations to roll any newer ones forward. The runbook lists migrate before restore in its headings but says “then re-run 6a”; the safest order for a fresh install from a dump is restore, then migrate. not verified
    4. 
    
  4. First break-glass admin: Terminal into an api service: AUTHADMIN_PASSWORD='<strong>' authadmin create --email admin@example.com --name "Break-glass Admin". Then authadmin list, authadmin grant-role --email … --role …. (authadmin roles lists role keys; mint-token is for MCP tokens.)
    5. 
  

  
A10. Backups

  
    
    
  • Option 2: enable Coolify Scheduled Backups on the PostgreSQL resource (cadence + S3 destination).
    • 
    
  • Option 1: Coolify’s one-click backup targets managed DB resources, so add a Scheduled Task in the bootstrap container: pg_dump -Fc "$DATABASE_URL" -f /workspace/backups/voltedge-$(date +%F).dump, and ship it off-host. Either way back up rustfs_data separately (attachments/exports live only there) and test a restore.
    • 
  

  
A11. Scaling & resource limits

  
    
    
  • Replicas: *_REPLICAS env (A6); nginx load-balances across them. fieldsync is kept at 1 here by choice (fixed device port and a container_name, both of which block --scale); it is not a correctness singleton (see Interactive 1).
    • 
    
  • Limits: set per-service CPU/memory limits so one heavy analysis pod cannot starve the host.
    • 
    
  • Multi-node reality: one Coolify server scales up but not out with autoscaling. Coolify can deploy to several servers and has Docker Swarm support, but autoscaling + managed replica failover at the ~1,000-user tier is the Kubernetes path.
    • 
  

  
A12. Auto-deploy & rollbacks

  
    
    
  • Auto-deploy: connect the Git source (webhook); gate to a production branch/tag.
    • 
    
  • Deploy order on upgrade: run the migration step (A9.2) before new app code serves traffic; additive-first schema keeps old containers working. Breaking change: expand → migrate → deploy → contract across two releases (Scaling Guide §10).
    • 
    
  • Rollback: redeploy a prior build from the Deployments history. Roll code back, not schema: migrations are not reversed.
    • 
  

  
A13. Verify

  
  1. Every service healthy; api at your replica count; fieldsync at 1.
  2. Browse https://gis.example.com/, sign in as the break-glass admin.
  3. Map renders (confirms /tiles proxy + territory-scoped MVT).
  4. Create a feature, run a trace (write path + synchronous analysis path).
  5. Upload an attachment (confirms RustFS presign + the storage domain).

B3. Postgres via CloudNativePG (primary + replicas + pooler)

  
deploy/k8s/20-postgres.yaml:

  
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata: { name: voltedge-db, namespace: voltedge }
spec:
  instances: 3                                   # 1 primary + 2 streaming replicas
  imageName: ghcr.io/cloudnative-pg/postgis:15   # PostGIS-enabled Postgres 15
  storage: { size: 100Gi }
  bootstrap:
    initdb:
      database: voltedge
      owner: app
      secret: { name: voltedge-db-app }          # the app role credentials (B2)
      postInitApplicationSQL:
        - CREATE EXTENSION IF NOT EXISTS postgis;
        - CREATE EXTENSION IF NOT EXISTS citext;     # migration 0024 needs it
        - CREATE EXTENSION IF NOT EXISTS pgcrypto;   # optional: gen_random_uuid() is core since PG13
  # Optional but recommended: continuous backup / PITR to object storage.
  # backup:
  #   barmanObjectStore:
  #     destinationPath: "s3://voltedge-backups/pg"
  #     s3Credentials: { ... }
---
# Transaction-pooling pooler for WRITES + hot reads (the app's DATABASE_URL).
apiVersion: postgresql.cnpg.io/v1
kind: Pooler
metadata: { name: voltedge-db-pooler-rw, namespace: voltedge }
spec:
  cluster: { name: voltedge-db }
  instances: 2
  type: rw
  pgbouncer:
    poolMode: transaction
    parameters: { max_client_conn: "1000", default_pool_size: "25" }
---
# Read-only pooler against the REPLICAS -- route tile/read queries here once the
# app grows a read-only DB handle (scaling guide §5-6). Not yet wired by default.
apiVersion: postgresql.cnpg.io/v1
kind: Pooler
metadata: { name: voltedge-db-pooler-ro, namespace: voltedge }
spec:
  cluster: { name: voltedge-db }
  instances: 2
  type: ro
  pgbouncer: { poolMode: transaction }

  
Correction to the original manual. The migrations CREATE EXTENSION exactly two extensions: postgis (0015) and citext (0024). The original listed pgcrypto (not needed: 55 migrations use gen_random_uuid(), which is built in from Postgres 13) and omitted citext. citext is normally a “trusted” extension the database owner may create, but pre-creating it as the superuser is the safe move. The CNPG image name, the “trusted” status and CNPG defaults are not verified.

  
CNPG manages the pooler→Postgres auth for you (an auth_query), so the manual PgBouncer/SCRAM worry from the Compose stack (AUTH_TYPE: plain in the file) does not apply: the app presents the app credentials to the pooler. sslmode=require encrypts to the pooler; if pgdriver rejects the CNPG CA, mount the cluster CA and use verify-full, or keep require (encrypt without CA verification).

  
Direct vs pooled. CNPG also creates a read-write Service straight to the primary, named <cluster>-rw (so voltedge-db-rw) not verified. Compose runs migrations over a direct connection because DDL wants a stable session, not a transaction-pooled one. Chapter 4 applies that to the migrate Job. HPA rules used: desired = ceil(current × utilisation / target); no change within a 10% tolerance; scale-up at most +4 pods or +100% per 15 s (whichever is larger); scale-down uses the highest recommendation of the last 5 minutes. Those are Kubernetes defaults, not repo facts not verified. Utilisation is measured against the CPU request (500m), so 60% means an average of 300m per pod, not 60% of the 2-core limit. The load numbers in the simulator are illustrative; the repo has no per-user CPU measurement.

Correction to the original manual (B12). It credited “the rolling update + readiness probe + PDB” with keeping at least 2 API pods serving. A PodDisruptionBudget limits voluntary evictions (node drains); it does not constrain a Deployment’s rolling update. Availability during a rollout comes from maxUnavailable and readiness. With 3 replicas and the default 25%/25%, surge rounds up to 1 and unavailable rounds down to 0, so capacity never drops below 3; the simulator shows it. Corrections to the original manual. (1) The login rate limit would be shared by everyone. Behind the Ingress, $remote_addr in these web pods is the ingress controller’s pod IP, so limit_req_zone $binary_remote_addr puts every user in one 5 r/s bucket. Restore the real client address with the realip module (set_real_ip_from <ingress pod CIDR>; real_ip_header X-Forwarded-For;; the CIDR is cluster-specific and not verified) or rate-limit at the Ingress. (2) The compose config also sets Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto on each proxied location plus proxy_http_version 1.1, proxy_connect_timeout 5s and proxy_send_timeout 60s; the k8s version dropped them. The API’s audit code prefers the first X-Forwarded-For hop (api/internal/auth/service.go), so copy those proxy_set_header lines across for parity with infra/nginx/nginx.conf. (3) The app’s own per-IP limiters (api/internal/ratelimit) key on the TCP peer address and deliberately ignore X-Forwarded-For, so behind any proxy they see the proxy’s address: the edge limit is the real brake.

Correction to the original manual. The original query filtered status = 'pending'.
